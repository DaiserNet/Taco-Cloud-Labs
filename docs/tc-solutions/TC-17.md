# TC-17 — Etiquetas dietarias, alérgenos y nivel de picante

## Objetivo

Describir los ingredientes con etiquetas dietarias, alérgenos y nivel de picante. A partir de esos datos, el catálogo debe informar la clasificación de cada taco. Las etiquetas del taco no pueden provenir del cliente, porque una declaración incorrecta podría ocultar un alérgeno o atribuir una dieta que el producto no cumple.

## Problema encontrado

`Ingredient` conservaba nombre, tipo, precio y stock, pero no tenía información dietaria. `TacoController` devolvía la entidad del taco y aceptaba ingredientes completos en `POST /api/tacos`. Un cliente podía incluir propiedades de ingredientes que no coincidieran con el catálogo. La cotización de cupones sólo devolvía importes y no ofrecía una clasificación del taco consultado.

## Solución implementada

La solución fue añadir metadatos tipados al ingrediente. `DietaryTag`, `Allergen` y `SpiceLevel` son enums, por lo que la API no interpreta textos libres. El nivel `UNKNOWN` representa ingredientes sin dato de picante. El catálogo de desarrollo declara estos valores antes de guardar cada ingrediente.

```java
private Set<DietaryTag> dietaryTags = EnumSet.noneOf(DietaryTag.class);
private Set<Allergen> allergens = EnumSet.noneOf(Allergen.class);
private SpiceLevel spiceLevel = SpiceLevel.UNKNOWN;
```

`IngredientRequest` permite que ADMIN configure estos metadatos. `IngredientMapper` los copia a la entidad y los publica mediante `IngredientResponse` e `IngredientAdminResponse`. Si un PUT antiguo omite un campo nuevo, el mapper conserva el valor que ya existe. Esto evita borrar metadatos al actualizar sólo el nombre o el tipo.

`TacoClassificationService` usa los ingredientes actuales del repositorio. `concatMap` conserva el orden del diseño, `switchIfEmpty` identifica un ingrediente inexistente y `collectList` espera a que se resuelvan todos antes de clasificar.

```java
return Flux.fromIterable(references)
    .concatMap(reference -> {
      String id = reference == null ? null : reference.getId();
      if (!StringUtils.hasText(id)) {
        return Mono.<Ingredient>error(new ResponseStatusException(
            HttpStatus.UNPROCESSABLE_ENTITY,
            "Every taco ingredient must have an ID."));
      }
      return ingredientRepo.findById(id)
          .switchIfEmpty(Mono.error(new ResponseStatusException(
              HttpStatus.NOT_FOUND, "Unknown ingredient: " + id)));
    })
    .collectList()
    .map(ingredients -> {
      taco.setIngredients(ingredients);
      return taco;
    });
```

La política dietaria exige que todos los ingredientes tengan el atributo correspondiente. Un ingrediente `VEGAN` también cuenta como vegetariano. `GLUTEN_FREE` requiere que todos tengan esa etiqueta y que ninguno declare `GLUTEN` como alérgeno. Los alérgenos se unen sin votación ni mayoría. El nivel de picante es el máximo declarado. Si algún ingrediente tiene nivel `UNKNOWN`, el taco conserva `UNKNOWN`.

```java
vegan &= tags.contains(DietaryTag.VEGAN);
vegetarian &= tags.contains(DietaryTag.VEGAN)
    || tags.contains(DietaryTag.VEGETARIAN);
glutenFree &= tags.contains(DietaryTag.GLUTEN_FREE)
    && !declaredAllergens.contains(Allergen.GLUTEN);
allergens.addAll(declaredAllergens);
```

El resultado aparece en `GET /api/tacos/{id}/classification` y dentro de las respuestas del catálogo. La página de tacos recientes muestra etiquetas, alérgenos, picante y el aviso académico. Ese aviso explica que los metadatos no sustituyen controles reales de contaminación cruzada.

`POST /api/tacos` ahora recibe `TacoCreateRequest`: nombre e IDs de ingredientes. Su `@JsonAnySetter` rechaza una clasificación enviada por el cliente, también dentro de cada ingrediente. El servidor consulta los ingredientes reales antes de guardar y responder.

La cotización existente acepta un `tacoId` opcional. Si se proporciona, busca ese taco y adjunta su clasificación derivada. El cálculo del cupón conserva su comportamiento anterior. Una cotización sin `tacoId` mantiene la respuesta previa sin campo `classification`.

## Flujo

Catálogo: ID de taco -> buscar taco -> buscar ingredientes actuales -> componer etiquetas, alérgenos y picante -> responder clasificación.

Creación de catálogo: nombre e IDs -> validar campos -> buscar ingredientes del servidor -> guardar taco -> clasificar -> responder.

Cotización con taco: subtotal, cupón e ID de taco -> calcular cupón -> resolver taco e ingredientes -> adjuntar clasificación -> responder.

## Archivos principales

- `DietaryTag.java`, `Allergen.java` y `SpiceLevel.java`: definen valores cerrados de metadata.
- `Ingredient.java`, `IngredientRequest.java`, `IngredientResponse.java`, `IngredientAdminResponse.java` e `IngredientMapper.java`: guardan, reciben y publican los datos del ingrediente.
- `TacoClassificationService.java`: resuelve ingredientes confiables y aplica la política de composición.
- `TacoCreateRequest.java`, `TacoClassification.java` y `TacoResponse.java`: separan entrada y respuestas del catálogo.
- `TacoController.java`: ofrece el endpoint de clasificación y deriva las respuestas de catálogo.
- `OrderQuoteRequest.java`, `OrderQuoteResponse.java` y `CouponController.java`: añaden la clasificación opcional a la cotización.
- `DevelopmentConfig.java` y `recents.component.html`: proporcionan metadatos de ejemplo y los muestran en la UI.
