# TC-31 — Correlation ID de HTTP a evento y logs

## Objetivo

Relacionar una petición HTTP con los eventos de orden, el outbox y los logs mediante `X-Correlation-Id`. La API debe conservar un valor seguro recibido del cliente o generar uno nuevo, devolverlo en la respuesta y evitar que el contexto de una petición contamine otra.

## Problema encontrado

`OrderEventFactory` usaba el ID de la orden como `correlationId`. Una petición de confirmación podía producir un evento nuevo, pero no había forma de relacionarlo con el header HTTP ni con sus logs. Tampoco existía validación del valor recibido. En la cadena reactiva, el MDC del hilo HTTP no podía acompañar de forma fiable la suscripción que guarda el outbox.

## Solución implementada

La solución fue incorporar `CorrelationIdFilter` en el borde MVC. Acepta sólo caracteres alfanuméricos, punto, guion, guion bajo y dos puntos, con un máximo de 100 caracteres. Si el header falta, está duplicado o no cumple ese formato, genera un UUID. Guarda el ID como atributo de la petición para reutilizarlo durante el despacho asíncrono y lo devuelve en la respuesta.

```java
id = candidate != null && !headers.hasMoreElements()
    && candidate.matches("[A-Za-z0-9._:-]{1,100}")
    ? candidate : UUID.randomUUID().toString();
request.setAttribute(ATTRIBUTE, id);
response.setHeader(HEADER, id);
```

El filtro coloca el ID en MDC mientras se ejecuta el borde MVC y restaura el valor anterior en `finally`. Registra la recepción sin incluir el body. El patrón de logs muestra `correlationId` cuando existe.

Los endpoints que pueden crear una orden toman ese valor antes de devolver el `Mono`. `CorrelationContext.fromCurrentRequest` lo introduce en Reactor Context mediante `contextWrite`. El outbox lo recupera con `deferContextual`, de modo que no depende del hilo que ejecute la suscripción. Si un caso de uso sin petición HTTP crea un evento, se genera un UUID propio.

```java
return CorrelationContext.fromCurrentRequest(
    orderService.createOrder(order, authentication)
        .map(orderMapper::toResponse));

String correlationId = context.getOrDefault(
    CorrelationContext.CONTEXT_KEY, UUID.randomUUID().toString());
OrderEvent event = OrderEventFactory.created(saved, correlationId);
```

`OrderEventFactory` conserva el ID de la orden en el payload y utiliza el ID de petición sólo en el sobre. El JSON del evento queda guardado en el outbox. La ruta de retry y DLQ de cocina ya conserva la correlación validada del evento. El log de preparación del outbox establece MDC sólo durante esa llamada y lo limpia después. No se añadió el ID como etiqueta de métricas.

## Flujo

HTTP -> validar o generar correlación -> respuesta y MDC del borde -> Reactor Context -> guardar orden y evento en outbox -> log del evento con MDC acotado -> broker -> retry o DLQ con la misma correlación.

## Archivos principales

- `CorrelationIdFilter.java`: valida el header, lo devuelve y delimita el MDC de la petición.
- `CorrelationContext.java`, `OrderApiController.java` y `ReorderController.java`: pasan el valor del borde MVC a la cadena reactiva de creación.
- `OrderOutboxService.java` y `OrderEventFactory.java`: construyen el evento con la correlación de la petición y registran el evento sin datos sensibles.
- `application.yml`: incorpora la correlación al patrón de logs.
