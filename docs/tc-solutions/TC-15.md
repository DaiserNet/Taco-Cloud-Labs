# TC-15 — Motor de cupones con reglas y fecha de expiración

## Objetivo

Convertir el mapa simple de descuentos en un motor de cupones que pueda validar reglas comerciales. Un cupón debe admitir descuento porcentual o fijo, fecha inicial, fecha de expiración, compra mínima y un descuento máximo opcional. La orden debe guardar el resultado aplicado sin permitir que el cliente controle los importes.

También se necesita una operación de cotización que permita comprobar un cupón sin crear una orden. Esta operación no debe publicar la lista de códigos configurados ni revelar si un código existe, expiró o todavía no comienza.

## Problema encontrado

La configuración anterior sólo relacionaba un texto con un número entero. No representaba el tipo de descuento, las fechas ni las restricciones de compra. Además, estaba asociada a un módulo web que no forma parte de la aplicación principal que ejecuta la API.

El cálculo de TC-14 producía `subtotal` y `total`, pero ambos tenían el mismo valor. No existían campos para conservar el descuento aplicado ni una forma segura de recibir un cupón. Usar `LocalDate.now()` directamente también habría hecho que las pruebas de fechas dependieran del reloj real del equipo.

## Solución implementada

Se creó el paquete `tacos.pricing` dentro del módulo activo `tacocloud-api`. Allí se definieron la configuración, los tipos de cupón, el servicio de cálculo y el error funcional. La fecha se obtiene desde un `Clock` inyectable. Los importes se calculan con `BigDecimal`, se redondean a dos decimales y nunca producen un total negativo.

La solución fue:

### Reglas comerciales desde configuración

`CouponProperties` enlaza cada código con una regla completa. El código es la clave del mapa y los valores comerciales se cargan desde YAML o desde las propiedades externas de Spring.

```java
@Component
@ConfigurationProperties(prefix = "tacocloud.coupons")
@Validated
@Data
public class CouponProperties {

  @Valid
  private Map<String, CouponRule> codes = new LinkedHashMap<>();

  @Data
  public static class CouponRule {
    @NotNull
    private CouponType type;

    @NotNull
    @DecimalMin(value = "0.01")
    private BigDecimal value;

    @NotNull
    @DateTimeFormat(iso = DateTimeFormat.ISO.DATE)
    private LocalDate startsOn;

    @NotNull
    @DateTimeFormat(iso = DateTimeFormat.ISO.DATE)
    private LocalDate expiresOn;

    @NotNull
    @DecimalMin(value = "0.00", inclusive = true)
    private BigDecimal minimumSubtotal = BigDecimal.ZERO;

    @DecimalMin(value = "0.00", inclusive = true)
    private BigDecimal maximumDiscount;
  }
}
```

`CouponType` contiene `PERCENTAGE` y `FIXED`. Esto evita interpretar un número sin saber si representa un porcentaje o una cantidad monetaria. El constructor de `CouponService` también revisa fechas, valores y códigos duplicados después de normalizarlos.

La configuración utilizada por la aplicación sigue la misma estructura:

```yaml
tacocloud:
  coupons:
    codes:
      CLASS10:
        type: PERCENTAGE
        value: 10.00
        starts-on: "2020-01-01"
        expires-on: "2035-12-31"
        minimum-subtotal: 10.00
        maximum-discount: 20.00
```

`shouldProvideCouponEngineInActiveApiModule` comprueba que la configuración, el servicio y el controlador pertenecen al módulo activo.

### Fecha controlada mediante Clock

El reloj del sistema se registra como una dependencia de Spring:

```java
@Configuration
public class CouponClockConfiguration {

  @Bean
  public Clock couponClock() {
    return Clock.systemUTC();
  }
}
```

El servicio usa `LocalDate.now(clock)`. En las pruebas se entrega un `Clock.fixed`, por lo que el día evaluado es estable. Las fechas inicial y final son inclusivas. `shouldIncludeStartAndExpirationDays` comprueba ambos límites sin depender de la hora real.

### Cotización y validación reactiva

`quote` usa `Mono.defer` para ejecutar la validación cuando existe una suscripción. Primero normaliza el subtotal y el código. Después busca la regla y revisa sus fechas y compra mínima.

```java
public Mono<CouponQuote> quote(
    BigDecimal subtotal, String couponCode) {
  return Mono.defer(() -> {
    BigDecimal normalizedSubtotal = money(subtotal);
    if (normalizedSubtotal.signum() < 0) {
      return Mono.error(new CouponValidationException());
    }

    String normalizedCode = normalize(couponCode);
    CouponRule rule = rules.get(normalizedCode);
    LocalDate today = LocalDate.now(clock);
    if (rule == null || today.isBefore(rule.getStartsOn())
        || today.isAfter(rule.getExpiresOn())
        || normalizedSubtotal.compareTo(
            rule.getMinimumSubtotal()) < 0) {
      return Mono.error(new CouponValidationException());
    }

    BigDecimal discount = discount(rule, normalizedSubtotal);
    BigDecimal total = normalizedSubtotal.subtract(discount)
        .max(BigDecimal.ZERO)
        .setScale(2, RoundingMode.HALF_UP);
    return Mono.just(new CouponQuote(normalizedCode, currency,
        normalizedSubtotal, discount, total));
  });
}
```

`normalize` aplica `trim` y convierte a mayúsculas con `Locale.ROOT`. Por eso `save10`, `SAVE10` y una variante con espacios se evalúan igual. `shouldNormalizeCouponCodeWithoutChangingTheCalculation` comprueba el código normalizado y el importe exacto.

Los casos desconocido, expirado, no iniciado y compra mínima incumplida producen la misma `CouponValidationException`. `shouldReturnSameErrorForEveryInapplicableCoupon` verifica el código público `COUPON_NOT_APPLICABLE` y el mismo detalle para todos esos casos.

### Descuento porcentual, fijo y límites

El cálculo distingue el tipo configurado y aplica el descuento máximo cuando existe:

```java
private BigDecimal discount(
    CouponRule rule, BigDecimal subtotal) {
  BigDecimal calculated = rule.getType() == CouponType.PERCENTAGE
      ? subtotal.multiply(rule.getValue())
          .divide(ONE_HUNDRED, 6, RoundingMode.HALF_UP)
      : rule.getValue();
  if (rule.getMaximumDiscount() != null) {
    calculated = calculated.min(rule.getMaximumDiscount());
  }
  return calculated.min(subtotal)
      .max(BigDecimal.ZERO)
      .setScale(2, RoundingMode.HALF_UP);
}
```

`min(subtotal)` impide descontar más que el valor de la compra. `max(BigDecimal.ZERO)` protege el límite inferior. `shouldCalculateExactDiscountForEachCouponType` usa casos parametrizados para porcentaje, cantidad fija, descuento máximo y total igual a cero.

### Aplicación única sobre la orden

`TacoOrder` guarda el código normalizado, la marca de aplicación y el descuento. El código se oculta del JSON porque sólo es un dato interno de persistencia.

```java
@JsonIgnore
private String couponCode;

private boolean couponApplied;

private BigDecimal discount = new BigDecimal("0.00");
```

`CouponService.apply` no vuelve a calcular una orden que ya tiene el cupón aplicado. Si no se recibió código, conserva el total igual al subtotal.

```java
public Mono<TacoOrder> apply(TacoOrder order) {
  return Mono.defer(() -> {
    if (order.isCouponApplied()) {
      return Mono.just(order);
    }

    BigDecimal subtotal = money(order.getSubtotal());
    if (!StringUtils.hasText(order.getCouponCode())) {
      order.setCouponCode(null);
      order.setCouponApplied(false);
      order.setDiscount(money(BigDecimal.ZERO));
      order.setTotal(subtotal);
      return Mono.just(order);
    }

    return quote(subtotal, order.getCouponCode())
        .map(quote -> {
          order.setCouponCode(quote.getNormalizedCouponCode());
          order.setCouponApplied(true);
          order.setDiscount(quote.getDiscount());
          order.setTotal(quote.getTotal());
          return order;
        });
  });
}
```

`shouldApplyCouponToOrderOnlyOnce` encadena dos llamadas a `apply`. La segunda conserva el mismo objeto y los mismos importes.

### Contratos HTTP sin exponer el código aplicado

`OrderCreateRequest` recibe un único `couponCode` opcional. `OrderMapper` lo copia a la entidad. `OrderResponse` devuelve `couponApplied` y `discount`, pero no devuelve el código.

```java
@Size(max = 64, message = "must contain at most 64 characters")
@Pattern(regexp = "[A-Za-z0-9_-]+",
    message = "must be an alphanumeric code")
private String couponCode;
```

```java
response.setCouponApplied(order.isCouponApplied());
response.setDiscount(order.getDiscount());
```

`shouldPersistCouponOutcomeWithoutExposingAppliedCode` revisa los campos de entidad, entrada y respuesta. También comprueba que `couponCode` tiene `@JsonIgnore`.

### Endpoint de cotización

`CouponController` ofrece sólo `POST /api/orders/quote`. El cuerpo contiene subtotal y código. La respuesta contiene moneda, subtotal, descuento, total y la marca de aplicación.

```java
@PostMapping(path = "/quote", consumes = "application/json")
public Mono<OrderQuoteResponse> quote(
    @Valid @RequestBody OrderQuoteRequest request) {
  return couponService
      .quote(request.getSubtotal(), request.getCouponCode())
      .map(quote -> new OrderQuoteResponse(
          quote.getCurrency(), quote.getSubtotal(),
          quote.getDiscount(), quote.getTotal(), true));
}
```

El controlador no persiste ni publica. Tampoco declara un endpoint GET para enumerar códigos. `shouldQuoteCouponWithoutCreatingAnOrderOrExposingItsCode` comprueba los importes y la ausencia de `couponCode` y `codes`. `shouldNotExposeAReadableCouponCatalog` comprueba que el controlador no declara lecturas de catálogo.

### Integración después del cálculo de precios

La orden real no confía en el subtotal de la cotización. `OrderService` vuelve a calcular ingredientes y cantidades con TC-14. Después aplica el cupón y sólo entonces publica y guarda.

```java
.flatMap(payment -> orderPricingService.price(order)
    .flatMap(couponService::apply)
    .flatMap(pricedOrder -> {
      pricedOrder.setUser(user);
      pricedOrder.setPaymentBrand(payment.getBrand());
      pricedOrder.setPaymentLast4(payment.getLast4());
      return Mono.fromRunnable(
          () -> orderMessages.sendOrder(pricedOrder))
          .then(Mono.defer(() -> repo.save(pricedOrder)));
    }))
```

No hay `subscribe()` ni `block()`. El cupón forma parte de la misma composición reactiva. `shouldPersistAppliedCouponOutcomeWithoutExposingItsCode` en `OrderCouponControllerTest.java` crea una orden real, captura lo entregado al repositorio y comprueba el código normalizado, el descuento, el total y la respuesta pública.

### Error uniforme

El advice de TC-09 convierte la excepción funcional en un Problem Details con estado `422`:

```java
@ExceptionHandler(CouponValidationException.class)
public ResponseEntity<ApiProblem> handleCouponValidation(
    CouponValidationException error,
    HttpServletRequest request) {
  return problem(HttpStatus.UNPROCESSABLE_ENTITY,
      "Coupon not applicable", error.getMessage(),
      error.getCode(), Collections.emptyList(), request);
}
```

`shouldReturnGenericProblemForUnknownCoupon` comprueba el estado, el código y el detalle público.

## Flujo

Cotización: JSON -> validar request -> normalizar código -> leer regla -> consultar fecha mediante `Clock` -> validar compra mínima -> calcular descuento -> limitar descuento -> responder importes sin persistir.

Creación: request de orden -> autenticar usuario -> resolver pago -> calcular subtotal con catálogo -> aplicar un cupón como máximo -> guardar código normalizado e importes -> publicar -> persistir -> responder sin exponer el código.

Error: código desconocido, expirado, no iniciado o compra insuficiente -> `CouponValidationException` -> Problem Details `422` con `COUPON_NOT_APPLICABLE`.

## Archivos principales

- `CouponProperties.java`: define y valida las reglas cargadas desde configuración.
- `CouponType.java`: distingue descuentos porcentuales y fijos.
- `CouponService.java`: normaliza, valida y calcula el cupón de forma reactiva.
- `CouponQuote.java`: transporta el resultado interno del cálculo.
- `CouponClockConfiguration.java`: ofrece el reloj inyectable.
- `CouponValidationException.java`: representa el rechazo uniforme de un cupón.
- `CouponController.java`: publica la cotización sin crear una orden.
- `OrderQuoteRequest.java` y `OrderQuoteResponse.java`: separan entrada y salida de la cotización.
- `TacoOrder.java`: persiste código aplicado, marca y descuento.
- `OrderCreateRequest.java`, `OrderResponse.java` y `OrderMapper.java`: integran el cupón en el contrato de órdenes sin exponer el código guardado.
- `OrderService.java`: aplica el cupón después del cálculo TC-14 y antes de los efectos.
- `ApiExceptionHandler.java`: transforma el rechazo en Problem Details.
- `application.yml`: contiene las reglas comerciales activas.
