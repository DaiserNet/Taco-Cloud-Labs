# TC-34 — Idempotency-Key en creación de órdenes

## Objetivo

Evitar que un doble clic o un reintento cree dos órdenes, descuente inventario dos veces o genere dos eventos. Una petición repetida debe conservar la respuesta inicial.

## Problema encontrado

`POST /api/orders` iniciaba siempre una creación nueva. Cada ejecución reservaba ingredientes, guardaba otra orden y preparaba otro evento outbox. La UI no distinguía el primer envío de un reintento.

## Solución implementada

La solución fue aceptar `Idempotency-Key` en `POST /api/orders`. Admite entre 8 y 128 letras, dígitos, guiones o guiones bajos. Es opcional para clientes existentes. La UI la envía en cada compra, reutiliza clave y token de pago al reintentar e ignora otro clic mientras envía. No se usa en otras operaciones.

`OrderRequestFingerprint` calcula SHA-256 sobre los campos funcionales de `OrderCreateRequest`, con longitudes para evitar ambigüedades. Normaliza el cupón y ordena los IDs de ingredientes. No compara el texto del JSON.

```java
String hash = fingerprint.hash(request);
IdempotencyRecord claim = new IdempotencyRecord(
    UUID.randomUUID().toString(), user.getId(), key, hash,
    UUID.randomUUID().toString(), UUID.randomUUID().toString(),
    Instant.now(clock));
return mongo.insert(claim)
    .map(inserted -> true)
    .onErrorResume(DuplicateKeyException.class, error -> Mono.just(false))
    .flatMap(owner -> owner
        ? place(claim, request, authentication)
        : replay(user.getId(), key, hash));
```

MongoDB aplica un índice único a `(userId, key)`. Sólo quien inserta `IN_PROGRESS` crea la orden. Otro intento compara el hash. Si cambia, responde 409. Si coincide, devuelve la respuesta guardada o espera brevemente sin volver a reservar. Si agota la espera, responde 409 y permite reintentar con la misma clave.

El registro recibe los IDs de orden y reserva antes de tocar inventario. La orden, la aceptación, el outbox y la respuesta idempotente se confirman en la misma transacción MongoDB.

```java
return Mono.defer(() -> orders.save(order))
    .flatMap(saved -> inventory.accept(reservation.getId(), saved.getId())
        .then(Mono.deferContextual(context -> {
          String correlationId = context.getOrDefault(
              CorrelationContext.CONTEXT_KEY, UUID.randomUUID().toString());
          OrderEvent event = OrderEventFactory.created(saved, correlationId);
          return outbox.save(new OutboxEvent(event.getEventId(),
              serialize(event), event.getVersion(), Instant.now()))
              .doOnSuccess(ignored -> logStaged(event))
              .thenReturn(saved);
        })))
    .flatMap(saved -> Mono.defer(() -> afterOutbox.apply(saved))
        .thenReturn(saved))
    .as(transaction::transactional);
```

El registro completado conserva `OrderResponse` y expira en 24 horas mediante TTL. Un `IN_PROGRESS` no expira automáticamente. Tras un fallo, se retira el claim sólo si no existe orden y la reserva no existe o está liberada. Un resultado incierto permanece bloqueado para revisión.

## Flujo

UI envía orden y clave -> validar usuario y clave -> calcular hash -> insertar claim único -> cotizar y reservar -> transacción: guardar orden, aceptar reserva, guardar outbox y respuesta -> devolver 201. Reintento -> comparar hash -> devolver la misma respuesta o 409.

## Archivos principales

- `OrderIdempotencyService.java`, `IdempotencyRecord.java` y `IdempotencyRecordRepository.java`: gestionan el claim, el índice único, el estado y la respuesta conservada.
- `OrderRequestFingerprint.java`: calcula la huella canónica de los campos relevantes.
- `OrderApiController.java`, `OrderService.java` y `OrderOutboxService.java`: reciben la clave y coordinan la finalización con la transacción existente.
- `cart.component.ts`: evita el doble envío y mantiene clave y token en un reintento.
- `application.yml`: deja configurables la retención del resultado y la espera máxima de una petición concurrente.
