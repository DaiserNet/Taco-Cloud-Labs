# TC-13 — Catálogo con precio, disponibilidad y stock

## Objetivo

Convertir cada ingrediente en un recurso de catálogo que pueda indicar precio, disponibilidad y existencias. La lectura pública debe ofrecer la información necesaria para comprar. Las operaciones internas de stock, nivel de reposición y versión deben quedar reservadas a administradores. Las escrituras concurrentes deben detectar datos obsoletos en vez de sobrescribir cambios recientes.

## Problema encontrado

`Ingredient` sólo almacenaba ID, nombre y tipo. No era posible saber cuánto costaba un ingrediente, si podía venderse o cuántas unidades existían. Tampoco había una versión persistente para distinguir dos actualizaciones concurrentes.

El endpoint público utilizaba un DTO seguro, pero no mostraba información comercial. Las mutaciones existentes sólo estaban pensadas para los datos descriptivos. Usarlas para reemplazar stock habría permitido cambios absolutos difíciles de auditar y con riesgo de perder actualizaciones.

## Solución implementada

`Ingredient` incorpora `unitPrice` como `BigDecimal`, `available`, `stockOnHand`, `reorderLevel` y un campo `version` con `@Version`. El precio nunca usa `double` y se redondea a dos decimales con `RoundingMode.HALF_UP`. Las restricciones impiden valores negativos y una validación de dominio evita marcar como disponible un ingrediente sin stock.

La respuesta pública `IngredientResponse` añade sólo precio y disponibilidad. `IngredientAdminResponse` incluye además stock, nivel de reposición y versión. De esta forma el cliente común recibe datos de venta y el administrador obtiene los datos operativos.

`IngredientCatalogService` concentra las dos operaciones. `updateCatalog` permite cambiar precio, disponibilidad y nivel de reposición. `adjustStock` recibe una variación positiva o negativa, calcula el nuevo valor con `long` para detectar desbordamientos y desactiva la disponibilidad cuando el stock llega a cero. Ambas operaciones buscan primero el ingrediente, comparan `expectedVersion` y guardan dentro del mismo `Mono`.

La solución fue:

### Ajuste reactivo de existencias

```java
public Mono<Ingredient> adjustStock(
    String ingredientId, StockAdjustmentRequest request) {
  return findIngredient(ingredientId)
      .flatMap(ingredient -> {
        if (!matchesVersion(ingredient, request.getExpectedVersion())) {
          return Mono.error(new IngredientVersionConflictException());
        }
        long adjustedStock = (long) ingredient.getStockOnHand()
            + request.getAdjustment();
        if (adjustedStock < 0 || adjustedStock > Integer.MAX_VALUE) {
          return Mono.error(new IngredientCatalogValidationException(
              "INGREDIENT_STOCK_NEGATIVE",
              "Stock adjustment would produce an invalid stock value."));
        }
        ingredient.setStockOnHand((int) adjustedStock);
        if (adjustedStock == 0) {
          ingredient.setAvailable(false);
        }
        return ingredientRepo.save(ingredient);
      })
      .onErrorMap(OptimisticLockingFailureException.class,
          IngredientVersionConflictException::new);
}
```

`PATCH /api/admin/ingredients/{id}/catalog` actualiza los datos comerciales y `POST /api/admin/ingredients/{id}/stock-adjustments` registra variaciones de existencias. Spring Data MongoDB incrementa la versión y rechaza una escritura concurrente obsoleta. El manejo de errores transforma el stock inválido en `422` y los conflictos de versión en `409`. La configuración inicial asigna precios y existencias coherentes a todos los ingredientes de desarrollo.

### Modelo de catálogo y versión

`Ingredient` recibió los datos comerciales y operativos. `@Version` permite que Spring Data detecte escrituras realizadas sobre una versión antigua:

```java
@NotNull
@DecimalMin(value = "0.00", inclusive = true)
@Digits(integer = 10, fraction = 2)
private BigDecimal unitPrice = new BigDecimal("0.00");

private boolean available;

@Min(0)
private int stockOnHand;

@Min(0)
private int reorderLevel;

@Version
private Long version;

@AssertTrue(message = "available ingredients must have stock")
@JsonIgnore
public boolean isCatalogStateValid() {
  return !available || stockOnHand > 0;
}
```

`shouldModelPriceAvailabilityStockReorderLevelAndVersion` comprueba la forma del modelo. `shouldRejectAvailabilityWhenStockIsZero` verifica la regla que une disponibilidad y existencias.

### Respuesta pública y respuesta administrativa

La respuesta pública contiene sólo datos necesarios para diseñar y comprar un taco:

```java
public class IngredientResponse {
  private String id;
  private String name;
  private Type type;
  private BigDecimal unitPrice;
  private boolean available;
}
```

La respuesta administrativa añade la información operativa:

```java
public class IngredientAdminResponse {
  private String id;
  private String name;
  private Type type;
  private BigDecimal unitPrice;
  private boolean available;
  private int stockOnHand;
  private int reorderLevel;
  private Long version;
}
```

`shouldExposeSaleDataWithoutOperationalMetadata` comprueba que stock, nivel de reposición y versión no aparezcan en la respuesta pública. `shouldUpdateCatalogAndReturnOperationalMetadata` valida la respuesta administrativa.

### Actualización parcial del catálogo

La petición exige la versión esperada y permite cambiar sólo las propiedades enviadas:

```java
@NotNull(message = "must be provided")
@Min(value = 0, message = "must not be negative")
private Long expectedVersion;

@DecimalMin(value = "0.00", inclusive = true,
    message = "must not be negative")
@Digits(integer = 10, fraction = 4,
    message = "must contain at most 10 integer and 4 decimal digits")
private BigDecimal unitPrice;

private Boolean available;

@Min(value = 0, message = "must not be negative")
private Integer reorderLevel;
```

El servicio redondea el precio al guardarlo:

```java
ingredient.setUnitPrice(request.getUnitPrice()
    .setScale(2, RoundingMode.HALF_UP));
```

`shouldRoundPriceWithBigDecimalAndUpdateAtExpectedVersion` comprueba el redondeo y la versión. `shouldRejectStaleExpectedVersionBeforeSaving` verifica que una versión distinta produzca conflicto sin guardar.

### Controlador administrativo pequeño

El controlador sólo valida la entrada, delega la regla y transforma la entidad:

```java
@PatchMapping(path = "/{id}/catalog", consumes = "application/json")
public Mono<IngredientAdminResponse> updateCatalog(
    @PathVariable String id,
    @Valid @RequestBody IngredientCatalogUpdateRequest request) {
  return catalogService.updateCatalog(id, request)
      .map(ingredientMapper::toAdminResponse);
}

@PostMapping(path = "/{id}/stock-adjustments",
    consumes = "application/json")
public Mono<IngredientAdminResponse> adjustStock(
    @PathVariable String id,
    @Valid @RequestBody StockAdjustmentRequest request) {
  return catalogService.adjustStock(id, request)
      .map(ingredientMapper::toAdminResponse);
}
```

`IngredientAdminControllerTest.java` comprueba respuestas válidas y Problem Details para precio, stock y versión. Las pruebas de seguridad confirman que estas rutas sólo aceptan ADMIN con CSRF.

### Disponibilidad pública calculada

El mapper no anuncia como vendible un ingrediente sin existencias:

```java
public IngredientResponse toResponse(Ingredient ingredient) {
  return new IngredientResponse(
      ingredient.getId(), ingredient.getName(), ingredient.getType(),
      displayPrice(ingredient.getUnitPrice()),
      ingredient.isAvailable() && ingredient.getStockOnHand() > 0);
}
```

El precio se presenta con dos decimales y la disponibilidad pública combina el indicador con el stock real.

## Flujo

Lectura pública: GET -> repositorio -> `IngredientMapper` -> precio y disponibilidad -> JSON.

Actualización de catálogo: PATCH de ADMIN -> validar DTO -> buscar ingrediente -> comparar versión -> aplicar cambios -> guardar -> respuesta administrativa.

Ajuste de stock: POST de ADMIN -> validar DTO -> buscar ingrediente -> comparar versión -> calcular stock -> guardar -> respuesta administrativa. Si la versión cambió -> `409`. Si el stock sería negativo -> `422` sin guardar.

## Archivos principales

- `Ingredient.java`: almacena precio, disponibilidad, stock, nivel de reposición y versión.
- `IngredientCatalogService.java`: compone la búsqueda, validación y escritura reactiva.
- `IngredientAdminController.java`: publica las dos operaciones administrativas.
- `IngredientCatalogUpdateRequest.java` y `StockAdjustmentRequest.java`: definen entradas explícitas con versión esperada.
- `IngredientResponse.java` e `IngredientAdminResponse.java`: separan los datos públicos de los operativos.
- `IngredientMapper.java`: redondea el precio y construye cada respuesta.
- `SecurityConfig.java`: limita `/api/admin/**` a `ROLE_ADMIN`.
- `ApiExceptionHandler.java`: presenta errores de inventario y concurrencia como Problem Details.
- `DevelopmentConfig.java`: inicia un catálogo válido para desarrollo.

## Cambios realizados por otros TC

TC-14 usa `unitPrice`, disponibilidad y stock como fuente del cálculo de órdenes. El precio unitario del taco es la suma de sus ingredientes vendibles. La orden guarda una instantánea y por eso los cambios posteriores del catálogo no alteran compras históricas.
