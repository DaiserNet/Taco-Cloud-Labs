# TC-09 — Validación y errores tipo Problem Details

## Objetivo

Definir una respuesta uniforme para los errores HTTP y validar los cuerpos de entrada antes de ejecutar persistencia o mensajería. La API debe distinguir solicitudes mal formadas, datos inválidos, recursos inexistentes, accesos prohibidos, conflictos de estado y fallos internos mediante un contrato estable y sin exponer detalles técnicos.

## Problema encontrado

Los controladores devolvían algunos estados con `ResponseEntity` vacío y dejaban otros errores al manejo predeterminado de Spring. Por ejemplo, un ingrediente inexistente consultado con GET podía completar su `Mono` vacío sin producir un `404` estructurado. Los errores `403`, `404` y `409` tampoco compartían cuerpo ni código funcional.

Aunque TC-08 ya separaba DTOs y entidades, `OrderCreateRequest` y `EmailOrder` aceptaban campos obligatorios ausentes o colecciones incompletas. Eso permitía entrar al método del controlador y alcanzar repositorio o mensajería antes de detectar una entrada inválida. Los errores de infraestructura también podían revelar el mensaje original de la excepción.

## Solución implementada

Se creó `ApiProblem`, un DTO con `type`, `title`, `status`, `detail`, `instance`, `code` y `violations`. `ApiExceptionHandler`, mediante `@RestControllerAdvice`, traduce las excepciones a `application/problem+json`. Los errores de sintaxis producen `400`. Autorización, ausencia y conflicto producen `403`, `404` y `409`. Bean Validation y las excepciones de conversión de correo producen `422`. Los fallos de datos o inesperados producen `500` con mensajes públicos sanitizados.

Los DTOs incorporan `@NotBlank`, `@NotNull`, `@Size`, `@Pattern` y `@Email`. `@Valid` aplica validación en cascada a tacos e ingredientes anidados. Spring ejecuta estas restricciones antes del método del controlador, por lo que una petición inválida no puede guardar ni publicar.

Los controladores sustituyen respuestas vacías de error por `Mono.error(new ResponseStatusException(...))`. Así, la ausencia detectada con `switchIfEmpty`, la autorización y los conflictos continúan dentro de la composición reactiva y llegan al handler central cuando Spring se suscribe. Los casos exitosos conservan sus `map`, `flatMap`, `thenReturn` y el orden de efectos implementado previamente.

La solución fue:

### Construcción uniforme de Problem Details

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ApiProblem> handleValidation(
    MethodArgumentNotValidException error,
    HttpServletRequest request) {
  List<ApiProblem.Violation> violations = error.getBindingResult()
      .getFieldErrors().stream()
      .map(this::toViolation)
      .sorted(Comparator.comparing(ApiProblem.Violation::getField)
          .thenComparing(ApiProblem.Violation::getMessage))
      .collect(Collectors.toList());
  return problem(HttpStatus.UNPROCESSABLE_ENTITY,
      "Validation failed",
      "One or more request fields are invalid.",
      "VALIDATION_FAILED", violations, request);
}

private ResponseEntity<ApiProblem> problem(
    HttpStatus status, String title, String detail, String code,
    List<ApiProblem.Violation> violations, HttpServletRequest request) {
  ApiProblem body = new ApiProblem(
      "urn:tacocloud:problem:" + code.toLowerCase(Locale.ROOT)
          .replace('_', '-'),
      title, status.value(), detail, request.getRequestURI(), code, violations);
  return ResponseEntity.status(status)
      .contentType(MediaType.APPLICATION_PROBLEM_JSON)
      .body(body);
}
```

`handleValidation` ordena las violaciones para que la respuesta sea estable. `problem` construye el tipo URN, el estado, el código y la URI de la petición. `shouldReturnUnprocessableProblemWithMultipleViolationsBeforeEffects` comprueba esos campos y confirma que la entrada inválida no alcanza persistencia ni mensajería.

### Contrato público del error

`ApiProblem` se creó como un DTO separado. También contiene una lista simple para señalar cada campo inválido:

```java
@Data
@AllArgsConstructor
public class ApiProblem {
  private String type;
  private String title;
  private int status;
  private String detail;
  private String instance;
  private String code;
  private List<Violation> violations;

  @Data
  @AllArgsConstructor
  public static class Violation {
    private String field;
    private String message;
  }
}
```

`shouldSanitizeInternalDataAccessProblem` verifica que este contrato no incluya stack trace ni el mensaje técnico de la excepción original.

### Validación anidada antes del controlador

Los DTOs de TC-08 recibieron restricciones en sus colecciones y objetos internos:

```java
@NotNull(message = "must be provided")
@Size(min = 1, max = 50,
    message = "must contain between 1 and 50 tacos")
@Valid
private List<TacoItem> tacos;

public static class TacoItem {
  @NotBlank(message = "must not be blank")
  @Size(min = 5, max = 100,
      message = "must contain between 5 and 100 characters")
  private String name;

  @NotNull(message = "must be provided")
  @Size(min = 1, max = 20,
      message = "must contain between 1 and 20 ingredients")
  @Valid
  private List<IngredientItem> ingredients;
}
```

`@Valid` hace que Spring también revise cada taco y cada ingrediente. La prueba de múltiples violaciones demuestra que todas las fallas se reúnen en una sola respuesta `422`.

### Ausencias como señales reactivas

Los controladores dejaron de devolver un publisher vacío cuando faltaba un recurso:

```java
@GetMapping("/{id}")
public Mono<IngredientResponse> byId(@PathVariable String id) {
  return repo.findById(id)
      .map(ingredientMapper::toResponse)
      .switchIfEmpty(Mono.error(
          new ResponseStatusException(HttpStatus.NOT_FOUND)));
}
```

El error continúa dentro del `Mono` y llega al advice al suscribirse. `shouldReturnNotFoundProblemForMissingIngredient` comprueba el estado `404`, el tipo de contenido y el código funcional.

## Flujo

Petición HTTP -> deserializar -> validar DTO -> ejecutar controlador -> completar cadena reactiva. Si aparece un error, el advice determina estado y código -> construye `ApiProblem` -> responde con `application/problem+json`. Si la entrada falla validación, el controlador no se ejecuta.

## Archivos principales

- `ApiProblem.java`: define el contrato público y las violaciones por campo.
- `ApiExceptionHandler.java`: centraliza estados, códigos, media type y sanitización.
- `IngredientRequest.java`, `OrderCreateRequest.java`, `OrderPatchRequest.java` y `EmailOrder.java`: declaran restricciones simples y anidadas.
- `IngredientController.java` y `OrderApiController.java`: convierten resultados vacíos y reglas HTTP en señales reactivas de error.
- `ApiProblemControllerTest.java`: comprueba el contrato completo y la ausencia de efectos ante entradas inválidas.

## Pruebas

Las pruebas específicas verifican múltiples violaciones con `422`, JSON incompleto con `400`, ingrediente inexistente con `404`, orden ajena con `403`, estado incompatible con `409`, error funcional de conversión con `422` y fallo de acceso a datos con `500`. También comprueban `application/problem+json`, códigos estables, URI de instancia, ausencia de stack trace, sanitización del mensaje interno y que repositorio y mensajería no reciben interacciones cuando la validación falla.

| Concepto comprobado | Test | Archivo |
|---|---|---|
| Varias violaciones y ausencia de efectos | `shouldReturnUnprocessableProblemWithMultipleViolationsBeforeEffects` | `ApiProblemControllerTest.java` |

## Cambios realizados por otros TC

TC-10 aplicó Bean Validation al formulario de registro y añadió al manejo central la colisión de usuario o correo. Ese conflicto se presenta con el mismo formato `ApiProblem` definido aquí, estado `409` y código `USER_ALREADY_EXISTS`.

TC-11 añadió filtros de seguridad antes de los controladores. Los errores funcionales que alcanzan el advice conservan `ApiProblem`. Las denegaciones producidas directamente por Spring Security responden con `401` o `403` antes de ejecutar controlador, repositorio o mensajería.

TC-12 valida `paymentMethodId` al crear órdenes y PAN, expiración y CVV sólo en la petición transitoria de tokenización. Los errores conservan el contrato Problem Details.

TC-13 incorporó errores de catálogo al mismo contrato. Un ajuste que produciría stock negativo responde `422` con el código `INGREDIENT_STOCK_NEGATIVE`. Una versión obsoleta responde `409` con `INGREDIENT_VERSION_CONFLICT`.

TC-14 incorporó errores de cantidad y precio al mismo formato. Una regla de cálculo incumplida responde `422` con un código específico. Un total enviado por el cliente se rechaza como petición inválida antes de producir efectos.

TC-15 añadió el código `COUPON_NOT_APPLICABLE` al mismo formato Problem Details. Los cupones desconocidos, expirados, no iniciados o que no cumplen la compra mínima comparten estado `422` y un detalle público uniforme.

TC-16 añadió `INSUFFICIENT_STOCK` al mismo contrato. Una reserva que no puede descontar un ingrediente responde `409` e identifica su ID en el detalle. Un dato de reserva inválido responde `422`.

TC-18 añadió `TACO_DESIGN_INVALID` para un diseño rechazado antes de guardar, cotizar o reservar. La respuesta `422` conserva Problem Details y cada entrada de `violations` incluye el código estable de la regla incumplida.
