# TC-27 — Contrato único de eventos de orden

## Objetivo

Compartir un solo contrato de mensaje entre la API, los adaptadores noop, JMS, RabbitMQ y Kafka, y los receptores de cocina. El evento debe llevar una identidad propia, versión, fecha y correlación. Su contenido debe servir para preparar los tacos sin transportar una entidad Mongo ni información de usuario o pago.

## Problema encontrado

Cada adaptador declaraba su propia copia de `OrderMessagingService` y recibía `TacoOrder`. El contrato dependía así de la entidad persistente. Cocina mantenía copias de `TacoOrder`, `Taco` e `Ingredient` que podían separarse de las clases reales. La vista de recepción usaba dirección de entrega, un dato innecesario para preparar la orden. Un cambio en la entidad podía alterar el JSON de mensajería sin una decisión explícita de versión.

## Solución implementada

La solución fue añadir `tacocloud-order-contract`, que sólo requiere Java y anotaciones de Jackson. Contiene el puerto único y las clases `OrderEvent`, `OrderEventType` y `OrderEventPayload`. `OrderEvent` exige los campos del sobre. La fábrica genera un UUID por evento, fija la versión 1 y utiliza el ID persistido como `correlationId`.

```java
public interface OrderMessagingService {
  void sendOrder(OrderEvent event);
}

public static OrderEvent created(String correlationId, OrderEventPayload payload) {
  return new OrderEvent(UUID.randomUUID().toString(), OrderEventType.ORDER_CREATED,
      CURRENT_VERSION, Instant.now().toString(), correlationId, payload);
}
```

`OrderEventFactory` está en la API porque allí sí se conoce `TacoOrder`. Convierte las líneas a snapshots con nombre, cantidad e ingredientes identificados por ID, nombre y tipo. No coloca `User`, dirección, token de pago, precio ni referencias Mongo en el payload. La publicación permanece dentro de `Mono.fromRunnable` después de persistir y aceptar la reserva.

```java
return Mono.fromRunnable(() -> orderMessages.sendOrder(OrderEventFactory.created(order)))
    .thenReturn(order);
```

Los cuatro adaptadores implementan el mismo puerto. Los receptores JMS, RabbitMQ y Kafka, la vista simple de cocina y el convertidor JMS consumen `OrderEvent`. Se retiraron las copias de dominio de cocina que ya no tenían uso.

La política de evolución es conservar el significado de cada campo v1. Un campo nuevo en v1 debe ser opcional y los lectores v1 lo ignoran. Una eliminación, cambio de tipo o cambio de significado exige una versión nueva y su prueba de compatibilidad. El archivo `order-event-v1.json` es la instantánea del contrato: una diferencia no acordada hace fallar la prueba.

## Flujo

Orden aceptada y guardada -> construir snapshot seguro -> crear sobre v1 -> enviar mediante el puerto compartido -> adaptar al broker -> cocina lee tacos e ingredientes.

## Archivos principales

- `tacocloud-order-contract`: contrato único y prueba de JSON v1.
- `OrderEventFactory.java` y `OrderService.java`: proyección de la entidad y publicación reactiva.
- Módulos `tacocloud-messaging-*`: dependencia del contrato y envío del evento.
- `tacocloud-kitchen`: recepción del evento y vista sin datos de entrega.

## Cambios realizados por otros TC

TC-28 incorporó los cuatro adaptadores al runtime de la API y selecciona uno mediante `tacocloud.messaging.transport`. Todos siguen implementando el puerto y enviando el evento v1 definido en TC-27.

TC-29 guarda el evento v1 en un outbox junto con la orden. El envío deja de ocurrir en el caso de uso de creación y pasa al publicador de pendientes. El contrato seguro del evento conserva su forma.

TC-30 hace que el receptor RabbitMQ valide el tipo y la versión de ese contrato antes de registrar el evento en cocina. Conserva el mismo `eventId` en las entregas repetidas y en el replay.
