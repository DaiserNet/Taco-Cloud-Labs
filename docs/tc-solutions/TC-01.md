# TC-01 — Actualizar un ingrediente sin perder el publisher

## Objetivo

Implementar `PUT /api/ingredients/{id}` como una operación reactiva completa. La actualización debía respetar el identificador de la ruta, modificar un ingrediente existente y devolver respuestas HTTP claras: `200 OK` cuando se actualiza, `400 Bad Request` cuando el identificador del cuerpo contradice al de la ruta y `404 Not Found` cuando el recurso no existe.

## Problema encontrado

El controlador original devolvía `void` y llamaba a `repo.save(ingredient)` sin encadenar ni suscribirse al `Publisher`. En Reactor, construir un `Mono` no ejecuta la operación; por eso la escritura podía no realizarse. Además, un ID contradictorio producía una excepción genérica y la escritura directa podía convertir accidentalmente un `PUT` de actualización en una creación.

## Solución implementada

`updateIngredient` devuelve `Mono<ResponseEntity<Ingredient>>`. Primero compara el ID del cuerpo con el `@PathVariable`; si no coinciden, retorna inmediatamente un `Mono` con respuesta `400` y no consulta el repositorio. Para un ID válido usa `findById(id)` y `flatMap`: esta función es necesaria porque la siguiente operación, `save`, también devuelve un `Mono` y debe formar parte de la misma cadena.

Sobre la entidad encontrada se actualizan solamente `name` y `type`, conservando el ID ya persistido. Después, `map` transforma el ingrediente guardado en una respuesta `200`. Si `findById` termina vacío, `defaultIfEmpty` produce `404`. No hay `subscribe()` manual ni bloqueo; la capa web controla la suscripción.

## Flujo

Petición PUT → comparar IDs → buscar ingrediente → aplicar nombre y tipo → guardar → responder `200`. Si los IDs difieren → `400`. Si la búsqueda queda vacía → `404`.

## Archivos principales

- `IngredientController.java`: contiene la validación del ID y la composición `findById` → `flatMap(save)` → `map`.
- `IngredientControllerTest.java`: prueba el endpoint con `WebTestClient` y la cadena directamente con `StepVerifier`.
- `IngredientRepository.java`: proporciona las operaciones reactivas usadas por el controlador.

## Pruebas

La suite verifica una actualización válida y los campos enviados al repositorio, el rechazo de IDs distintos, la respuesta para un ingrediente inexistente y la suscripción real al `Mono` de guardado. `PublisherProbe` confirma que el publisher fue suscrito, solicitado y no cancelado; `StepVerifier` confirma la emisión y finalización de la respuesta.

## Cambios realizados por otros TC

TC-08 separó la entidad persistente del contrato HTTP mediante `IngredientRequest` e `IngredientResponse`. La composición reactiva implementada en TC-01 se mantiene sin cambios conceptuales: validar el ID, buscar, actualizar, guardar y transformar la respuesta dentro del mismo publisher.

TC-09 convirtió el ID contradictorio y el ingrediente inexistente en señales reactivas traducidas a Problem Details. Los estados siguen siendo `400` y `404`; ahora incluyen un cuerpo uniforme `application/problem+json`.
