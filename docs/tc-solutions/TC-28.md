# TC-28 — Elegir broker en runtime, no editando el POM

## Objetivo

Elegir noop, JMS, RabbitMQ o Kafka al arrancar Taco Cloud mediante una propiedad. La selección no debe exigir comentar dependencias ni recompilar. Sólo puede quedar activo un servicio de publicación y los datos de conexión deben configurarse fuera del código.

## Problema encontrado

La API dependía únicamente del adaptador noop. JMS, RabbitMQ y Kafka estaban comentados en el POM, por lo que cambiar de transporte exigía editar el proyecto y volver a construirlo. Las configuraciones JMS y RabbitMQ compartían el nombre completo `tacos.messaging.MessagingConfig`. Los emisores llevaban destinos escritos en Java. Varios YAML conservaban usuarios y contraseñas de ejemplo para Artemis. Activar todos los módulos sin condiciones habría creado varios beans de `OrderMessagingService`.

## Solución implementada

La solución fue incluir los cuatro adaptadores como dependencias normales de la API. Cada clase de envío usa `@ConditionalOnProperty`, de modo que Spring sólo registra la que coincide con `tacocloud.messaging.transport`. El mismo criterio protege los conversores JMS y RabbitMQ, ahora llamados `JmsMessagingConfig` y `RabbitMessagingConfig`. El caso de uso `OrderService` continúa inyectando el puerto único y no conoce el transporte concreto.

```java
@Service
@ConditionalOnProperty(name = "tacocloud.messaging.transport", havingValue = "jms")
public class JmsOrderMessagingService implements OrderMessagingService {
  private final JmsTemplate jms;
  private final String destination;

  @Autowired
  public JmsOrderMessagingService(JmsTemplate jms,
      @Value("${tacocloud.messaging.jms.destination}") String destination) {
    this.jms = jms;
    this.destination = destination;
  }

  @Override
  public void sendOrder(OrderEvent event) {
    jms.convertAndSend(destination, event, this::addOrderSource);
  }
}
```

`MessagingTransportGuard` revisa las definiciones de beans antes de crear los servicios. Rechaza valores distintos de `noop`, `jms`, `rabbitmq` y `kafka`, o una cantidad de adaptadores diferente de uno. También impide usar noop con `prod`, `production` y otros perfiles de despliegue como `staging`. En producción, JMS y RabbitMQ exigen usuario y contraseña externos.

```java
String[] beans = factory.getBeanNamesForType(OrderMessagingService.class,
    false, false);
if (beans.length != 1) {
  throw new IllegalStateException("Expected exactly one OrderMessagingService for "
      + "tacocloud.messaging.transport=" + value + ", found "
      + beans.length + ": " + Arrays.toString(beans));
}
```

Los destinos y temas se leen de propiedades, no de constantes en los emisores o receptores. El YAML principal acepta variables de entorno para transporte, destino, host, puerto y credenciales. No contiene contraseñas de broker. El modo local sin perfil activo, `dev` y `test` pueden usar noop. En los tests de contexto se proporcionan plantillas simuladas, por lo que seleccionar un transporte no contacta un servidor. La creación automática de tópicos Kafka y la declaración dinámica RabbitMQ quedan desactivadas al arrancar la API.

## Flujo

Configurar propiedad -> arrancar Spring -> validar valor y bean único -> inyectar el adaptador seleccionado -> publicar `OrderEvent` en el destino configurado.

## Archivos principales

- `tacocloud-api/pom.xml`: incluye los cuatro adaptadores.
- `MessagingTransportGuard.java`: valida valor, perfil y cantidad de beans.
- Adaptadores y configuraciones JMS/RabbitMQ: condiciones de activación y destinos externos.
- `tacocloud/src/main/resources/application.yml` y `tacocloud-kitchen/src/main/resources/application.yml`: parámetros de conexión y destinos mediante variables de entorno.
