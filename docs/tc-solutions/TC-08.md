# TC-08 — Separar DTOs de entrada, respuesta y persistencia

## Objetivo

Separar el contrato HTTP de las entidades MongoDB utilizadas por Taco Cloud. Los endpoints de órdenes e ingredientes deben recibir objetos diseñados para la entrada y devolver respuestas públicas explícitas, evitando que la estructura interna del dominio determine automáticamente qué propiedades puede enviar o recibir un cliente.

## Problema encontrado

`OrderApiController` recibía y devolvía `TacoOrder`. Esta entidad contiene el usuario completo, incluidos datos propios de `UserDetails`, y los campos completos de pago. Al serializarla se podía exponer más información de la necesaria. Al utilizarla como `@RequestBody`, Jackson también podía asignar propiedades administradas por el servidor, como el ID de la orden, `placedAt`, estado o usuario.

`IngredientController` presentaba el mismo acoplamiento con `Ingredient`: el documento persistido servía a la vez como request y response. Los controladores no expresaban de forma visible qué campos pertenecían al contrato público ni dónde se realizaba la transformación.

## Solución implementada

Se añadieron cuatro DTOs. `OrderCreateRequest` contiene los datos de entrega, pago de entrada y tacos necesarios para crear una orden. No declara ID de orden, fecha, estado ni usuario. Un `@JsonAnySetter` rechaza propiedades superiores no admitidas antes de ejecutar el controlador. Sus clases anidadas representan tacos e ingredientes mediante valores simples e identificadores.

`OrderResponse` contiene ID, fecha, estado, `userId`, dirección, los últimos cuatro dígitos del pago y una representación sencilla de los tacos. No contiene `User`, contraseña, authorities, número completo, expiración ni CVV. `IngredientRequest` mantiene ID, nombre y tipo con las validaciones ya utilizadas por TC-03, mientras que `IngredientResponse` define la forma pública equivalente.

`OrderMapper` crea una nueva `TacoOrder` desde el request. Al crear una instancia nueva se conservan los valores de servidor definidos por el dominio para fecha y estado. Los ingredientes de cada taco se convierten en referencias por ID. En sentido inverso, el mapper aplana el usuario a `userId`, calcula `paymentLast4` y transforma las listas de forma segura. `IngredientMapper` crea, actualiza y proyecta ingredientes sin consultar repositorios.

La solución fue:

### Transformación de órdenes

```java
public TacoOrder toEntity(OrderCreateRequest request) {
  TacoOrder order = new TacoOrder();
  order.setDeliveryName(request.getDeliveryName());
  order.setDeliveryStreet(request.getDeliveryStreet());
  order.setDeliveryCity(request.getDeliveryCity());
  order.setDeliveryState(request.getDeliveryState());
  order.setDeliveryZip(request.getDeliveryZip());
  order.setCcNumber(request.getCcNumber());
  order.setCcExpiration(request.getCcExpiration());
  order.setCcCVV(request.getCcCVV());
  order.setTacos(safe(request.getTacos()).stream()
      .map(this::toEntityTaco)
      .collect(Collectors.toList()));
  return order;
}

public OrderResponse toResponse(TacoOrder order) {
  OrderResponse response = new OrderResponse();
  response.setId(order.getId());
  response.setPlacedAt(order.getPlacedAt());
  response.setStatus(order.getStatus());
  response.setUserId(order.getUser() == null ? null : order.getUser().getId());
  response.setPaymentLast4(lastFour(order.getCcNumber()));
  response.setTacos(safe(order.getTacos()).stream()
      .map(this::toResponseTaco)
      .collect(Collectors.toList()));
  return response;
}
```

Los controladores mantienen sus cadenas Reactor y aplican `map` al final para convertir las entidades emitidas en DTOs. GET, POST, PUT, PATCH y creación desde correo devuelven `OrderResponse`. Los endpoints de ingredientes usan sus contratos dedicados. El adaptador de mensajería noop registra únicamente el ID de orden y la cantidad de tacos.

### Entrada sin campos administrados por el servidor

El DTO utilizado en TC-08 sólo declara datos que el cliente podía aportar en ese momento:

```java
public class OrderCreateRequest {
  private String deliveryName;
  private String deliveryStreet;
  private String deliveryCity;
  private String deliveryState;
  private String deliveryZip;
  private String ccNumber;
  private String ccExpiration;
  private String ccCVV;

  @Valid
  private List<TacoItem> tacos;

  @JsonAnySetter
  public void rejectUnknownField(String name, Object value) {
    throw new IllegalArgumentException(
        "Field not allowed in order creation: " + name);
  }
}
```

El fragmento conserva el contrato de TC-08, antes de la tokenización de TC-12. No contiene ID, fecha, estado ni usuario. `shouldRejectOrderServerOwnedFieldsWithoutEffects` envía uno de esos campos y verifica que no haya persistencia ni publicación.

### Respuesta pública limitada

La salida usa valores simples y no incluye el objeto `User`:

```java
public class OrderResponse {
  private String id;
  private Date placedAt;
  private OrderStatus status;
  private String userId;
  private String deliveryName;
  private String deliveryStreet;
  private String deliveryCity;
  private String deliveryState;
  private String deliveryZip;
  private String paymentLast4;
  private List<TacoItem> tacos;
}
```

`shouldNotSerializeSensitiveOrderOrEmbeddedUserFields` comprueba que la respuesta contiene el identificador del usuario y los últimos cuatro dígitos, pero no contraseña, authorities ni usuario embebido.

### Separación de ingredientes

`IngredientMapper` concentra la creación, actualización y respuesta sin consultar el repositorio:

```java
public Ingredient toEntity(IngredientRequest request) {
  return new Ingredient(
      request.getId(), request.getName(), request.getType());
}

public void updateEntity(
    IngredientRequest request, Ingredient ingredient) {
  ingredient.setName(request.getName());
  ingredient.setType(request.getType());
}

public IngredientResponse toResponse(Ingredient ingredient) {
  return new IngredientResponse(
      ingredient.getId(), ingredient.getName(), ingredient.getType());
}
```

`shouldMapIngredientRequestAndEntityToDedicatedContracts` comprueba las tres direcciones sin depender de HTTP ni MongoDB.

### Mensaje operativo reducido

El adaptador noop dejó de imprimir la entidad completa:

```java
public void sendOrder(TacoOrder order) {
  int tacoCount = order.getTacos() == null
      ? 0 : order.getTacos().size();
  log.info("Sending order to kitchen: orderId={}, tacoCount={}",
      order.getId(), tacoCount);
}
```

Así el log sólo conserva ID y cantidad. Esta decisión acompaña las pruebas de contrato que garantizan que los objetos públicos no exponen datos sensibles.

## Flujo

Creación de orden: JSON -> `OrderCreateRequest` -> `OrderMapper` -> `TacoOrder` -> repositorio -> `OrderResponse` -> JSON.

Consulta de orden: repositorio -> `Flux<TacoOrder>` -> `map(orderMapper::toResponse)` -> `Flux<OrderResponse>`.

Ingrediente: JSON -> `IngredientRequest` -> `IngredientMapper` -> `Ingredient` -> repositorio -> `IngredientResponse`.

## Archivos principales

- `OrderCreateRequest.java` y `OrderResponse.java`: contratos HTTP de órdenes.
- `IngredientRequest.java` y `IngredientResponse.java`: contratos HTTP de ingredientes.
- `OrderMapper.java` e `IngredientMapper.java`: transformaciones puras entre DTOs y dominio.
- `OrderApiController.java` e `IngredientController.java`: integración de DTOs dentro de los flujos existentes.
- `NoOpOrderMessagingService.java`: registro reducido a datos operativos.
- `ApiDtoContractTest.java`: pruebas específicas del contrato público.

## Pruebas

Las pruebas verifican que una respuesta de orden contiene `userId` y `paymentLast4`, pero no usuario embebido, contraseña, authorities ni datos completos de pago. También comprueban que un ID de orden enviado por el cliente produce `400` sin persistencia ni publicación, que el mapper no copia campos administrados por el servidor y que la respuesta contiene exactamente las propiedades documentadas. El contrato de ingredientes se prueba mediante la conversión request -> entidad -> response. Las suites anteriores se adaptaron a los nuevos tipos manteniendo sus verificaciones de suscripción, autorización, estados y persistencia.

| Concepto comprobado | Test | Archivo |
|---|---|---|
| Respuesta sin usuario ni datos sensibles | `shouldNotSerializeSensitiveOrderOrEmbeddedUserFields` | `ApiDtoContractTest.java` |
| Rechazo de campos administrados por el servidor | `shouldRejectOrderServerOwnedFieldsWithoutEffects` | `ApiDtoContractTest.java` |
| Request convertido sin copiar ID, fecha, estado o usuario | `shouldMapOrderRequestWithoutServerOwnedFields` | `ApiDtoContractTest.java` |
| JSON limitado al contrato documentado | `shouldMapEntityToDocumentedSafeResponseJson` | `ApiDtoContractTest.java` |
| Contratos separados para ingredientes | `shouldMapIngredientRequestAndEntityToDedicatedContracts` | `ApiDtoContractTest.java` |

## Cambios realizados por otros TC

TC-09 añadió Bean Validation a los DTOs de entrada creados en TC-08 y usa `ApiProblem` como contrato de error. Los DTOs de respuesta y los mappers continúan protegiendo los mismos campos. La validación ocurre antes de transformar o persistir la entrada.

TC-10 reforzó la protección del usuario persistente al impedir que su contraseña cifrada se serialice como JSON o aparezca en `toString`. El contrato `OrderResponse` de TC-08 no cambia: sigue exponiendo únicamente `userId` y nunca el objeto `User` completo.

TC-11 limitó el listado de órdenes. `ROLE_USER` recibe únicamente las propias y `ROLE_ADMIN` puede auditarlas todas. La selección ocurre antes de aplicar `OrderMapper`. Los DTOs y campos públicos definidos en TC-08 no cambiaron.

TC-12 usa `paymentMethodId` y expone marca y últimos cuatro. La separación DTO-entidad se mantiene.

TC-13 amplió `IngredientResponse` con `unitPrice` y `available`, que son datos útiles para comprar. El stock, el nivel de reposición y la versión se mantienen en `IngredientAdminResponse`. Así se conserva la separación entre respuesta pública, datos operativos y entidad persistente.

TC-14 cambió el contrato de creación a `items` con taco y cantidad. `OrderResponse` expone importes calculados e instantáneas de precio. La separación de TC-08 permanece y evita que el cliente controle `currency`, `subtotal` o `total`.

TC-15 añadió `couponCode` como entrada opcional y añadió `couponApplied` y `discount` a la respuesta. El código persistido no forma parte de `OrderResponse`. La separación entre entrada, respuesta y entidad continúa protegiendo los datos internos.

TC-23 separó el listado de órdenes del detalle. `GET /api/orders/me` y la auditoría ADMIN devuelven resúmenes paginados mediante `OrderSummaryResponse`. El detalle sigue utilizando el `OrderResponse` seguro definido en TC-08, sin `User` ni token de pago.

TC-25 añadió `version` y `statusHistory` a `OrderResponse`. El mapper convierte la auditoría persistida a un DTO de respuesta sin exponer el documento `User`, el método de pago ni secretos. `OrderCreateRequest` sigue sin aceptar un estado decidido por el cliente.

TC-26 añadió `KitchenOrderResponse` para la cola y el avance de cocina. Contiene identidad de orden, estado, versión, tacos, asignación y ETA. La dirección y el pago permanecen fuera de esta respuesta.

TC-35 publicó los DTO públicos de entrada y salida como esquemas separados en `openapi.yaml`. La separación entre entidad MongoDB y contrato HTTP definida aquí se mantiene.
