# TC-14 — Calcular precios y cantidades del lado servidor

## Objetivo

Permitir que una orden contenga líneas con taco y cantidad. El servidor debe calcular el precio unitario, el subtotal de cada línea y el total de la orden a partir del catálogo vigente. El cliente sólo puede indicar qué quiere comprar y cuántas unidades necesita. El precio aplicado debe persistirse para que una compra histórica no cambie cuando se actualice el catálogo.

## Problema encontrado

La orden recibía una lista de tacos sin cantidad. El carrito mostraba un precio fijo y no enviaba una estructura capaz de representar varias unidades del mismo taco. Tampoco existía una separación entre el precio actual del ingrediente y el precio que se aplicó al comprar.

Aceptar `subtotal` o `total` desde el navegador habría permitido alterar el importe. Calcular con `double` también podía introducir errores binarios en operaciones con decimales. La orden necesitaba líneas persistentes y una política monetaria controlada por el servidor.

## Solución implementada

`OrderCreateRequest` recibe `items`. Cada elemento contiene un taco formado por nombre e identificadores de ingredientes y una cantidad mínima de uno. Los campos monetarios no forman parte de la entrada. Un campo desconocido como `total` hace que la petición se rechace antes de consultar repositorios o publicar mensajes.

`OrderLine` guarda el taco, la cantidad, `unitPriceAtPurchase` y su subtotal. `OrderPricingService` resuelve cada ingrediente de forma reactiva con `concatMap`. Esta operación conserva el orden recibido y comprueba que el ingrediente exista, esté disponible, tenga stock y tenga un precio válido. El precio unitario es la suma de los ingredientes. La moneda se configura como `USD`, el redondeo usa dos decimales con `HALF_UP` y el máximo por línea se configura con `tacocloud.order-pricing.max-quantity`.

La solución fue:

### Modelo persistente de líneas e importes

Se creó `OrderLine` para guardar cada taco junto con su cantidad y los importes calculados en el momento de la compra.

```java
@Data
public class OrderLine implements Serializable {
  private Taco taco;
  private int quantity;
  private BigDecimal unitPriceAtPurchase = new BigDecimal("0.00");
  private BigDecimal subtotal = new BigDecimal("0.00");
}
```

`unitPriceAtPurchase` es una copia del precio aplicado. No es una consulta al precio actual del catálogo. Por eso una orden ya guardada conserva su valor aunque después cambie el precio de un ingrediente. Esta parte se comprueba con `shouldKeepPriceSnapshotWhenCatalogPriceChanges` en `OrderPricingServiceTest.java`.

`TacoOrder` se amplió para persistir las líneas y los totales de la orden.

```java
private List<OrderLine> items = new ArrayList<>();
private String currency = "USD";
private BigDecimal subtotal = new BigDecimal("0.00");
private BigDecimal total = new BigDecimal("0.00");

@JsonIgnore
private List<Taco> tacos = new ArrayList<>();
```

La lista anterior `tacos` se conserva para poder procesar órdenes creadas por los flujos existentes. Se oculta del JSON y se adapta a líneas con cantidad uno cuando no existen `items`. `shouldUseQuantityItemsWithoutClientOwnedMoneyFields` comprueba que la entidad tiene los nuevos campos y que la entrada HTTP ya no utiliza la lista anterior.

### Contrato de entrada controlado por el servidor

`OrderCreateRequest` permite enviar el taco y la cantidad. No declara campos monetarios.

```java
@NotNull(message = "must be provided")
@Size(min = 1, max = 50,
    message = "must contain between 1 and 50 items")
@Valid
private List<OrderItem> items;

@Data
public static class OrderItem {
  @NotNull(message = "must be provided")
  @Valid
  private TacoItem taco;

  @NotNull(message = "must be provided")
  @Min(value = 1, message = "must be at least 1")
  private Integer quantity;

  @JsonAnySetter
  public void rejectUnknownField(String name, Object value) {
    throw new IllegalArgumentException(
        "Field not allowed in order item: " + name);
  }
}
```

`@Min(1)` rechaza cero y cantidades negativas durante la validación del DTO. `@JsonAnySetter` impide introducir campos como `subtotal` o `unitPriceAtPurchase` dentro de una línea. El `@JsonAnySetter` de la petición completa hace lo mismo con un `total` enviado en la raíz.

`shouldRejectZeroQuantityBeforeAnyEffect` comprueba la cantidad mínima. `shouldRejectClientSuppliedTotalBeforeAnyEffect` comprueba que un total enviado por el cliente produce `400` y que no se consulta ningún repositorio.

Los ingredientes se reciben sólo por identificador:

```java
@NotNull(message = "must be provided")
@Size(min = 1, max = 20,
    message = "must contain between 1 and 20 ingredients")
private List<@NotBlank(message = "must not be blank")
    @Pattern(regexp = "[A-Za-z0-9_-]+",
        message = "must be an alphanumeric identifier") String> ingredientIds;
```

El cliente no envía objetos de catálogo completos. El servidor usa cada ID para obtener el nombre, el precio, la disponibilidad y el stock actuales.

### Contrato de respuesta con importes calculados

`OrderResponse` expone los valores calculados y las instantáneas que quedaron guardadas.

```java
private String currency;
private BigDecimal subtotal;
private BigDecimal total;
private List<OrderItem> items;

@Data
public static class OrderItem {
  private TacoItem taco;
  private int quantity;
  private BigDecimal unitPriceAtPurchase;
  private BigDecimal subtotal;
}
```

La entrada y la salida tienen responsabilidades distintas. La entrada expresa qué se quiere comprar. La salida informa cuánto calculó el servidor. `shouldExposeCalculatedMoneyAndPriceSnapshotsInResponse` comprueba que el JSON contiene `items`, `currency`, `subtotal` y `total`, y que ya no publica `tacos`.

### Conversión entre DTOs y dominio

`OrderMapper` convierte cada elemento recibido en una línea de dominio. Los ingredientes se crean primero como referencias por ID porque sus datos reales se resuelven después en el servicio de precios.

```java
order.setItems(safe(request.getItems()).stream()
    .map(this::toEntityLine)
    .collect(Collectors.toList()));

private OrderLine toEntityLine(OrderCreateRequest.OrderItem request) {
  OrderLine line = new OrderLine();
  if (request != null) {
    line.setTaco(toEntityTaco(request.getTaco()));
    line.setQuantity(
        request.getQuantity() == null ? 0 : request.getQuantity());
  }
  return line;
}
```

Al construir la respuesta, el mapper copia solamente los importes que ya están en la entidad.

```java
response.setCurrency(order.getCurrency());
response.setSubtotal(order.getSubtotal());
response.setTotal(order.getTotal());
response.setItems(responseLines(order).stream()
    .map(this::toResponseLine)
    .collect(Collectors.toList()));
```

El mapper no calcula precios. Esto evita que el mismo cálculo aparezca en varios lugares. `ApiDtoContractTest.java` comprueba la conversión y los campos exactos del contrato público.

### Cálculo reactivo de la orden

`OrderPricingService.price` espera a que todas las líneas estén resueltas antes de emitir la orden terminada.

```java
return Flux.fromIterable(requestedLines)
    .concatMap(this::priceLine)
    .collectList()
    .map(pricedLines -> {
      BigDecimal subtotal = pricedLines.stream()
          .map(OrderLine::getSubtotal)
          .reduce(BigDecimal.ZERO, BigDecimal::add)
          .setScale(2, RoundingMode.HALF_UP);
      order.setItems(pricedLines);
      order.setCurrency(currency);
      order.setSubtotal(subtotal);
      order.setTotal(subtotal);
      return order;
    });
```

`concatMap` procesa las líneas sin cambiar su orden. `collectList` reúne todas las líneas ya calculadas. El `map` final suma sus subtotales y coloca en la orden la moneda, el subtotal y el total. `shouldCalculateDecimalPricesAndMultiplyByQuantity` verifica que ingredientes de `1.10` y `0.35` formen un precio unitario de `1.45` y que una cantidad de dos produzca `2.90`.

Cada línea valida primero la cantidad. El límite superior se obtiene de configuración.

```java
if (line.getQuantity() < 1 || line.getQuantity() > maxQuantity) {
  return Mono.error(new OrderPricingException(
      "ORDER_QUANTITY_INVALID",
      "Quantity must be between 1 and " + maxQuantity + "."));
}
```

La validación ocurre antes de consultar los ingredientes. `shouldRejectQuantityAboveConfiguredMaximumBeforeCatalogAccess` usa Mockito para comprobar que el repositorio no recibe llamadas cuando la cantidad es inválida.

Después se resuelven todos los ingredientes de la línea y se calculan los importes con `BigDecimal`.

```java
return Flux.fromIterable(ingredientReferences)
    .concatMap(this::resolveSellableIngredient)
    .collectList()
    .map(ingredients -> {
      BigDecimal unitPrice = ingredients.stream()
          .map(Ingredient::getUnitPrice)
          .reduce(BigDecimal.ZERO, BigDecimal::add)
          .setScale(2, RoundingMode.HALF_UP);
      BigDecimal lineSubtotal = unitPrice
          .multiply(BigDecimal.valueOf(line.getQuantity()))
          .setScale(2, RoundingMode.HALF_UP);
      taco.setIngredients(ingredients);
      line.setUnitPriceAtPurchase(unitPrice);
      line.setSubtotal(lineSubtotal);
      return line;
    });
```

`BigDecimal` evita errores de representación binaria. `setScale(2, HALF_UP)` establece una regla clara para importes con más de dos decimales.

La consulta del catálogo distingue entre ingrediente desconocido, ingrediente no disponible y precio inválido.

```java
return ingredientRepo.findById(ingredientId)
    .switchIfEmpty(Mono.error(new OrderPricingException(
        "ORDER_INGREDIENT_NOT_FOUND",
        "Unknown ingredient: " + ingredientId)))
    .flatMap(ingredient -> {
      if (!ingredient.isAvailable() || ingredient.getStockOnHand() < 1) {
        return Mono.error(new OrderPricingException(
            "ORDER_INGREDIENT_UNAVAILABLE",
            "Ingredient is not available: " + ingredientId));
      }
      return Mono.just(ingredient);
    });
```

`shouldIdentifyUnknownIngredient` comprueba que el error incluye el ID solicitado. `shouldRejectUnavailableIngredient` comprueba que un ingrediente sin disponibilidad no permite terminar el cálculo.

### Integración en la creación de órdenes

`OrderService` inserta el cálculo en la composición que ya resuelve usuario y pago.

```java
return currentUser(authentication)
    .flatMap(user -> paymentMethodService
        .findOwned(order.getPaymentMethodId(), authentication)
        .flatMap(payment -> orderPricingService.price(order)
            .flatMap(pricedOrder -> {
              pricedOrder.setUser(user);
              pricedOrder.setPaymentBrand(payment.getBrand());
              pricedOrder.setPaymentLast4(payment.getLast4());
              return Mono.fromRunnable(
                  () -> orderMessages.sendOrder(pricedOrder))
                  .then(Mono.defer(() -> repo.save(pricedOrder)));
            })));
```

No se llama a `subscribe()` ni a `block()`. La suscripción HTTP activa una sola cadena. El repositorio recibe la misma orden que ya contiene líneas e importes. `shouldCreateOrderWithQuantityAndServerCalculatedTotals` captura el argumento de `save` y verifica que la instantánea `1.45` ya está presente antes de persistir.

El flujo de órdenes recibidas por correo también pasa por el mismo cálculo:

```java
.flatMap(orderPricingService::price)
.flatMap(repo::save)
```

Los tacos anteriores se convierten en líneas con cantidad uno dentro de `OrderPricingService`. Así se mantiene la conversión reactiva ya existente.

### Errores HTTP de cálculo

`OrderPricingException` conserva un código funcional y `ApiExceptionHandler` lo transforma en Problem Details.

```java
@ExceptionHandler(OrderPricingException.class)
public ResponseEntity<ApiProblem> handleOrderPricing(
    OrderPricingException error, HttpServletRequest request) {
  return problem(HttpStatus.UNPROCESSABLE_ENTITY,
      "Invalid order pricing", error.getMessage(), error.getCode(),
      Collections.emptyList(), request);
}
```

Una cantidad superior al máximo o un ingrediente no vendible responde con `422`. `shouldRejectQuantityAboveConfiguredMaximumWithoutSaving` comprueba el código `ORDER_QUANTITY_INVALID` y verifica que la orden no se guarda.

### Cantidad y vista previa en el carrito

`CartItem` calcula el precio visible a partir de los ingredientes recibidos del catálogo.

```typescript
get unitPrice() {
  const ingredients = this.taco && this.taco.ingredients
      ? this.taco.ingredients : [];
  const total = ingredients.reduce(
      (sum, ingredient) => sum + Number(ingredient.unitPrice || 0), 0);
  return Math.round(total * 100) / 100;
}

get lineTotal() {
  return Math.round(this.quantity * this.unitPrice * 100) / 100;
}
```

Esta operación sólo ofrece una vista previa. El servidor vuelve a consultar los precios y realiza el cálculo válido. `should keep a quantity greater than one and calculate its preview total` comprueba que tres unidades con precio unitario `1.45` muestran `4.35`.

La plantilla permite seleccionar cantidades de cero a diez y muestra el total de la línea.

```html
<select [(ngModel)]="item.quantity">
  <option [ngValue]="0">Remove</option>
  <option [ngValue]="1">1</option>
  <option [ngValue]="2">2</option>
  <option [ngValue]="3">3</option>
  <option [ngValue]="10">10</option>
</select>

<td align="right">{{item.lineTotal | currency}}</td>
```

Al enviar la orden, el componente crea `items` sin copiar los precios visibles.

```typescript
this.model.items = this.cart.getItemsInCart()
    .filter(cartItem => Number(cartItem.quantity) > 0)
    .map(cartItem => ({
      taco: {
        name: cartItem.taco.name,
        ingredientIds: cartItem.taco.ingredients
            .map(ingredient => ingredient.id)
      },
      quantity: Number(cartItem.quantity)
    }));
```

`should send quantity and ingredient IDs without client totals` inspecciona el segundo `POST`. Comprueba la cantidad, los IDs y la ausencia de `total`, `subtotal` y `tacos`.

### Configuración y conteo operativo

La moneda y el máximo por línea se dejaron en configuración.

```yaml
tacocloud:
  order-pricing:
    currency: USD
    max-quantity: 10
```

El servicio de mensajería suma las cantidades de las líneas para informar cuántos tacos contiene la orden.

```java
int tacoCount = order.getItems() == null ? 0 : order.getItems().stream()
    .mapToInt(item -> item == null ? 0 : item.getQuantity())
    .sum();
```

`shouldLogOperationalMetadataWithoutPaymentInformation` comprueba que una línea con cantidad tres registra `tacoCount=3` y que el mensaje continúa sin datos de pago.

## Flujo

Carrito -> seleccionar cantidad -> enviar `items` sin totales -> autenticar usuario -> resolver pago -> consultar ingredientes -> calcular precio unitario -> multiplicar por cantidad -> sumar subtotales -> guardar instantánea -> responder con importes calculados.

Si la cantidad es inválida -> `422` sin consultar catálogo ni guardar. Si el cliente envía un total -> `400` sin efectos. Si falta un ingrediente o no se puede vender -> `422` con un código funcional.

Para cada línea el flujo interno es: validar cantidad -> leer ingredientes por ID -> comprobar precio, disponibilidad y stock -> sumar precios -> redondear precio unitario -> multiplicar por cantidad -> guardar subtotal de línea.

## Cambios realizados por otros TC

TC-15 aplica el cupón después de que TC-14 calcula el subtotal desde el catálogo. `subtotal` conserva el valor original de las líneas y `total` pasa a representar el importe final después del descuento. Las instantáneas de precio y el cálculo del servidor no cambian.

TC-16 usa las líneas y cantidades calculadas por TC-14 para determinar cuántas unidades de cada ingrediente debe reservar. El cálculo de precio sigue ocurriendo primero. La orden no se guarda si la reserva atómica detecta stock insuficiente.
