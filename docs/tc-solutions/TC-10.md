# TC-10 — Registro reactivo con contraseñas protegidas

## Objetivo

Hacer que el registro de usuarios sea completamente reactivo y seguro: la contraseña debe persistirse mediante un hash adaptativo, el redireccionamiento sólo debe emitirse cuando el guardado termine y tanto el nombre de usuario como el correo deben ser únicos. Los datos sensibles tampoco deben aparecer accidentalmente en respuestas JSON ni registros de diagnóstico.

## Problema encontrado

La configuración utilizaba `NoOpPasswordEncoder`, por lo que la contraseña podía almacenarse sin protección. Además, el controlador invocaba `save` pero devolvía el redirect de forma independiente; al no componer el `Mono` del repositorio, no existía garantía de suscripción ni de que la persistencia hubiese concluido.

El registro tampoco protegía de forma consistente la unicidad de `username` y `email`. Una consulta previa por sí sola no evita que dos solicitudes concurrentes intenten insertar el mismo valor. Finalmente, el hash de `User` y la contraseña cruda de `RegistrationForm` podían aparecer al serializar o imprimir esos objetos.

## Solución implementada

`SecurityConfig` usa `PasswordEncoderFactories.createDelegatingPasswordEncoder()`. El formato resultante incluye el identificador `{bcrypt}`, permite comprobar la contraseña con `matches` y conserva la posibilidad de reconocer otros esquemas compatibles.

`RegistrationService` concentra el flujo. `Mono.defer` retrasa consultas, codificación y guardado hasta que alguien se suscribe. Primero asegura los índices únicos y luego combina con `Mono.zip` las consultas reactivas de usuario y correo, usando `hasElement` para obtener ambas respuestas sin bloquear. `flatMap` emite `RegistrationConflictException` si alguno ya existe o encadena exactamente un `userRepo.save` con la contraseña codificada. Si una carrera concurrente alcanza MongoDB, `onErrorMap` convierte `DuplicateKeyException` en el mismo conflicto funcional.

`UserIndexInitializer` crea índices únicos con nombre para `username` y `email` mediante `ReactiveMongoTemplate`. El `Mono` se guarda con `cache`, de modo que la inicialización completada se comparte en registros posteriores. El controlador devuelve `Mono<String>` y usa `thenReturn("redirect:/login")`; por ello el redirect sólo aparece después de completar el registro.

El formulario incorpora restricciones para usuario, contraseña y correo. `@JsonIgnore` y `@ToString.Exclude` protegen el hash de `User`, mientras que `RegistrationForm` excluye la contraseña cruda de su representación textual. Los duplicados se integran en el contrato `ApiProblem` con estado `409`.

## Flujo

Formulario HTTP → Bean Validation → asegurar índices únicos → consultar usuario y correo en paralelo → codificar contraseña → guardar usuario → completar persistencia → emitir redirect. Una coincidencia previa o una colisión del índice termina como conflicto `409`.

## Archivos principales

- `SecurityConfig.java`: configura el codificador adaptativo.
- `RegistrationController.java`, `RegistrationForm.java` y `RegistrationService.java`: validan, componen y ejecutan el registro reactivo.
- `UserIndexInitializer.java`: garantiza unicidad en MongoDB.
- `User.java`: evita exponer el hash.
- `RegistrationConflictException.java` y `ApiExceptionHandler.java`: representan duplicados como conflicto público.

## Pruebas

Las pruebas comprueban el prefijo bcrypt y `matches`, la ausencia de contraseñas en JSON y `toString`, y que el método POST devuelve un `Publisher`. `PublisherProbe`, `StepVerifier` y un `Sinks.One` demuestran que el guardado se suscribe y que el redirect espera su finalización. También se verifican usuario existente, correo existente y la carrera de índice sin guardar de más. Dos pruebas con MongoDB embebido recargan el hash persistido y comprueban los índices únicos reales. La prueba HTTP confirma el redirect y el contrato `409 application/problem+json` para registros duplicados.
