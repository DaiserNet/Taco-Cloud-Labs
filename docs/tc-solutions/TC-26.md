# TC-26 — Cola de cocina, claim atómico y tiempo estimado

## Objetivo

Mostrar las órdenes nuevas a cocina en un orden estable. Una estación debe poder reclamar la siguiente orden sin competir incorrectamente con otra estación. La respuesta debe indicar un tiempo estimado y contener sólo los datos necesarios para preparar los tacos.

## Problema encontrado

TC-25 introdujo `CREATED` y `ACCEPTED`, pero no había una cola operativa. Un avance normal de estado podía aceptar una orden sin asignar estación ni cocinero. La clase antigua `KitchenUI` sólo registraba el objeto recibido por mensajería. Tampoco existía una estimación de preparación ni una respuesta HTTP limitada para cocina.

## Solución implementada

La solución fue consultar en MongoDB las órdenes `CREATED` con orden ascendente por `placedAt` y `_id`. Este segundo campo decide de forma estable entre órdenes con la misma fecha. El índice `order_kitchen_fifo` acompaña esa consulta.

El claim usa `findAndModify` condicionado por `status=CREATED`. MongoDB selecciona y modifica una orden en una sola operación. El cambio guarda `ACCEPTED`, `stationId`, `cookId` y la entrada de auditoría. Ambos identificadores se obtienen del usuario autenticado. En esta implementación cada cuenta KITCHEN representa una estación: `cookId` es el nombre de usuario y `stationId` es ese nombre con el prefijo `station:`.

```java
Query next = Query.query(where("status").is(OrderStatus.CREATED))
    .with(Sort.by(Sort.Direction.ASC, "placedAt", "_id"));
Update claim = new Update()
    .set("status", OrderStatus.ACCEPTED)
    .set("stationId", stationId)
    .set("cookId", authentication.getName())
    .set("activeStationId", stationId)
    .push("statusHistory", change);
return mongo.findAndModify(next, claim,
    FindAndModifyOptions.options().returnNew(true), TacoOrder.class);
```

Un índice único parcial sobre `activeStationId` impide que la misma estación tenga dos órdenes activas, incluso si dos peticiones llegan al mismo tiempo. El campo se libera al marcar `READY` o al cancelar en `ACCEPTED`. La transición inicial `CREATED -> ACCEPTED` se realiza mediante claim, mientras los avances posteriores siguen en `OrderWorkflowService`. La ruta general de estado queda para ADMIN. Cocina utiliza una ruta propia que devuelve `KitchenOrderResponse`, sin dirección, pago ni objeto `User`.

La estimación usa factores configurables de base, cola anterior, unidades y complejidad. La complejidad cuenta ingredientes adicionales a los dos primeros por unidad. El cálculo es una función determinista de esos datos y no altera la orden.

```java
return Math.toIntExact(baseMinutes
    + Math.max(0, queuedAhead) * perQueuedOrderMinutes
    + units * perUnitMinutes
    + complexity * perExtraIngredientMinutes);
```

La vista protegida `/api/kitchen/ui` muestra la cola, permite reclamar y avanzar a `PREPARING` y `READY`. Envía la cookie CSRF en las escrituras. El receptor de mensajes anterior dejó de imprimir la orden completa en los logs.

## Flujo

KITCHEN autenticado -> consultar cola FIFO -> reclamar mediante `findAndModify` -> recibir orden segura y ETA -> iniciar preparación -> marcar lista -> liberar estación.

## Archivos principales

- `TacoOrder.java` y `OrderWorkflowService.java`: asignación, índice único, claim atómico y liberación de estación.
- `KitchenQueueService.java` y `KitchenEtaCalculator.java`: listado MongoDB, respuesta limitada y fórmula configurable.
- `KitchenQueueController.java`, `KitchenOrderResponse.java`, `KitchenUI.java` y `kitchen-ui.html`: API y vista operativa de cocina.
- `SecurityConfig.java` y `application.yml`: acceso KITCHEN, CSRF y factores de ETA.
- `tacocloud-kitchen/.../KitchenUI.java`: registro de notificaciones sin dirección completa.

## Cambios realizados por otros TC

TC-27 hizo que el receptor de mensajes de cocina lea un `OrderEvent` con ID de orden y snapshots de preparación. La cola protegida de TC-26 sigue consultando la orden persistida y su lógica de claim y ETA no cambió.
