# TC-02 — Eliminar de verdad y responder con semántica HTTP

## Objetivo

Implementar `DELETE /api/ingredients/{id}` de forma reactiva, devolviendo `204 No Content` únicamente cuando la eliminación haya terminado y `404 Not Found` cuando el ingrediente solicitado no exista.

## Problema encontrado

La versión inicial del endpoint devolvía `void` y sólo invocaba `repo.deleteById(id)`. Esa llamada construía un publisher, pero no quedaba unido al publisher de la respuesta ni existía una suscripción explícita. Como consecuencia, el método podía terminar sin que la base de datos ejecutara la eliminación. Tampoco diferenciaba entre un recurso existente y uno inexistente, y una respuesta `204` anticipada no demostraba que la operación asíncrona hubiese concluido.

## Solución implementada

`deleteIngredient` devuelve `Mono<ResponseEntity<Ingredient>>` y comienza con `repo.findById(id)`. La búsqueda previa permite decidir si realmente hay algo que borrar y evita tratar todos los IDs como eliminaciones exitosas.

Cuando se encuentra el ingrediente, `flatMap` encadena `repo.delete(existingIngredient)`. Se usa `flatMap` porque `delete` devuelve otro publisher. Así la eliminación queda dentro de la misma composición y recibe la suscripción iniciada por Spring. A continuación, `thenReturn` descarta la señal sin valor de `Mono<Void>` y emite la respuesta `204` sólo después de recibir su señal de finalización. Finalmente, `switchIfEmpty` transforma una búsqueda vacía en `404`.

La solución fue:

### Búsqueda y eliminación encadenadas

```java
@DeleteMapping("/{id}")
public Mono<ResponseEntity<Ingredient>> deleteIngredient(
    @PathVariable String id) {
  return repo.findById(id)
      .flatMap(existingIngredient -> repo.delete(existingIngredient)
          .thenReturn(ResponseEntity.noContent().<Ingredient>build()))
      .switchIfEmpty(Mono.just(ResponseEntity.notFound().build()));
}
```

No se usa `try/catch` síncrono para representar resultados asíncronos, no hay `block()` y no se realiza una suscripción manual. El estado HTTP depende directamente de las señales del repositorio.

### Verificación del repositorio

La prueba válida prepara un `Mono<Void>` que completa y después ejecuta el endpoint mediante `WebTestClient`:

```java
Mockito.when(repo.findById("FLTO"))
    .thenReturn(Mono.just(new Ingredient(
        "FLTO", "Flour Tortilla", Ingredient.Type.WRAP)));
Mockito.when(repo.delete(Mockito.any(Ingredient.class)))
    .thenReturn(Mono.empty());

testClient.delete().uri("/api/ingredients/FLTO")
    .exchange()
    .expectStatus().isNoContent();

Mockito.verify(repo, Mockito.times(1))
    .delete(Mockito.any(Ingredient.class));
```

El `204` sólo puede observarse después de que el publisher de `delete` complete. `shouldDeleteIngredient` comprueba este camino. `shouldReturnNotFoundForDeleteNonexistentIngredient` configura `findById` con `Mono.empty()` y verifica que `delete` no se invoque.

## Flujo

Petición DELETE -> buscar por ID -> si existe, borrar la entidad -> esperar la finalización -> responder `204`. Si la búsqueda no emite entidad -> responder `404`.

## Archivos principales

- `IngredientController.java`: contiene la cadena `findById` -> `flatMap(delete)` -> `thenReturn` y el caso vacío.
- `IngredientControllerTest.java`: verifica la eliminación válida y el recurso inexistente.
- `IngredientRepository.java`: expone `findById` y `delete` como operaciones reactivas.

## Pruebas

El caso válido configura la búsqueda con un ingrediente, hace que `delete` complete y comprueba `204`, además de verificar una invocación al repositorio. El caso inexistente configura `Mono.empty()`, espera `404` y confirma que `delete` nunca fue llamado.

| Concepto comprobado | Test | Archivo |
|---|---|---|
| Eliminación completada antes de responder `204` | `shouldDeleteIngredient` | `IngredientControllerTest.java` |
| Recurso inexistente y ausencia de llamada a `delete` | `shouldReturnNotFoundForDeleteNonexistentIngredient` | `IngredientControllerTest.java` |

## Cambios realizados por otros TC

TC-08 introdujo DTOs para los endpoints de ingredientes. DELETE conserva sus respuestas `204` y `404` y la cadena `findById` -> `flatMap(delete)` -> `thenReturn`. Únicamente su tipo de respuesta interna pasó a `ResponseEntity<Void>` porque no devuelve cuerpo.

TC-09 mantuvo el `204` posterior a la finalización del borrado y transformó el caso inexistente en un `404` con Problem Details. La suscripción y la espera por el publisher del repositorio no cambiaron.

TC-11 protegió DELETE de ingredientes con `ROLE_ADMIN` y CSRF. Una vez autorizada la petición, el flujo de TC-02 continúa esperando la finalización del publisher antes de responder `204`.
