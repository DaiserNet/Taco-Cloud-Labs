# TC-30 — Consumidor idempotente, retry limitado y DLQ

## Objetivo

Procesar los eventos de orden aunque RabbitMQ los entregue más de una vez. La recepción debe tener un efecto durable, reconocer el mensaje después de ese efecto, reintentar errores transitorios y apartar los definitivos en una cola de mensajes muertos.

## Problema encontrado

El listener RabbitMQ de cocina sólo mostraba el evento en un log. No guardaba qué `eventId` había procesado ni podía distinguir una entrega nueva de una repetida. Una caída después de recibir el evento podía perder la notificación. Tampoco había un límite de reintentos, DLQ o información operativa sobre los fallos.

## Solución implementada

La solución fue guardar `KitchenOrderReceipt` con estado `RECEIVED` y `ProcessedOrderEvent` en MongoDB. Este último usa `eventId` como `_id`, que MongoDB indexa de forma única. Almacena el resultado y la fecha. Al iniciar, el consumidor prepara ambas colecciones antes de recibir mensajes. Una transacción confirma juntos el estado recibido y la marca. Si el mismo evento llega otra vez, se devuelve `DUPLICATE` sin repetir el cambio. Dos eventos distintos de la misma orden mantienen dos marcas, porque la llave de idempotencia es el evento, no la orden.

```java
return transaction.execute(status -> {
  if (mongo.exists(Query.query(Criteria.where("_id")
      .is(event.getEventId())), ProcessedOrderEvent.class)) {
    return Result.DUPLICATE;
  }
  String orderId = event.getPayload().getOrderId();
  boolean exists = mongo.exists(Query.query(Criteria.where("_id")
      .is(orderId)), KitchenOrderReceipt.class);
  Instant now = Instant.now();
  mongo.insert(new ProcessedOrderEvent(event.getEventId(), orderId,
      exists ? "ALREADY_RECEIVED" : "RECEIVED", now));
  if (!exists) {
    mongo.insert(new KitchenOrderReceipt(orderId, event.getEventId(), now));
  }
  return Result.PROCESSED;
});
```

El listener reconoce con `basicAck` sólo cuando termina la transacción. Un evento repetido se reconoce igualmente. Los errores de acceso transitorio a Mongo se envían a una cola de retry con TTL por mensaje y backoff exponencial configurable. Cuando se agota el número de reintentos, o el evento tiene tipo o versión no admitidos, se publica en DLQ. El ack original ocurre después de confirmar el envío y comprobar que RabbitMQ no devolvió el mensaje por falta de ruta. Si esa publicación falla, se hace `basicNack` con requeue.

Los headers de DLQ llevan sólo un código de causa, número de reintentos, `eventId` y correlación validada. Un JSON desconocido se reemplaza por `{}`. La métrica `tacocloud.kitchen.event.delivery` usa únicamente la etiqueta `outcome`, con valores como `processed`, `duplicate`, `retry`, `dlq` y `route_error`. Se consulta en `/actuator/metrics/tacocloud.kitchen.event.delivery`.

`TACOCLOUD_KITCHEN_MONGODB_URI` debe apuntar a un replica set para permitir la transacción. El arranque falla si no puede preparar las colecciones necesarias.

Para un replay controlado, el operador inspecciona causa, versión y `eventId` en DLQ, corrige la causa y comprueba si la marca ya existe. Después republica el mismo contrato seguro en la cola principal conservando `eventId` y correlación. Si el JSON fue inválido y se sustituyó por `{}`, reconstruye el evento desde el outbox de origen. Verifica la marca, el recibo y la métrica antes de retirar la copia de DLQ. Una entrega repetida no crea otro recibo.

## Flujo

RabbitMQ -> validar evento -> transacción Mongo: guardar marca y recibo -> commit -> ack. Error transitorio -> retry con backoff -> nuevo intento o DLQ. Error permanente -> DLQ -> replay supervisado cuando se resuelve la causa.

## Archivos principales

- `KitchenEventProcessor.java`, `KitchenOrderReceipt.java` y `ProcessedOrderEvent.java`: validación y efecto durable idempotente.
- `OrderListener.java`: ack manual, clasificación de fallos, retry y DLQ.
- `KitchenDeliveryConfig.java`: transacciones Mongo y colas RabbitMQ.
- `application.yml` y `tacocloud-kitchen/pom.xml`: parámetros, métricas y dependencias de integración.

## Cambios realizados por otros TC

TC-31 envía el ID de correlación de la petición en el evento. El listener conserva ese valor validado en el mensaje de retry o DLQ, junto con `eventId` y el código de causa que ya utilizaba TC-30.

TC-32 mide el tiempo de los eventos procesados por primera vez. La métrica de entrega de TC-30 sigue contando `dlq` sólo después de confirmar la ruta y sin cambiar su política de retry o ack.
