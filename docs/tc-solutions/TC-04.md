# TC-04 — PATCH de órdenes con lista blanca y sin ZIP mutante

## Objetivo

Asegurar `PATCH /api/orders/{orderId}` para que sólo el propietario de la orden o un usuario con rol `ADMIN` pueda modificar los datos de entrega permitidos, sin exponer campos sensibles ni aceptar una orden inválida después del cambio.

## Problema encontrado

El controlador recibía una `TacoOrder` completa como parche. Esto permitía intentar cambiar usuario, pago u otros campos que no pertenecen a una edición de entrega. No había autorización por propietario, la orden inexistente no se traducía explícitamente a `404` y existía un error funcional: al actualizar `deliveryZip` se copiaba `deliveryState`. La persistencia tampoco validaba la entidad resultante.

## Solución implementada

Se creó `OrderPatchRequest` con únicamente cinco propiedades: nombre, calle, ciudad, estado y código postal de entrega. `@JsonAnySetter` rechaza cualquier campo adicional durante la deserialización; el DTO existe aquí por una razón de seguridad, no como abstracción general.

El endpoint comprueba primero que exista una autenticación no anónima. Luego usa `findById(orderId).flatMap(...)` para trabajar sobre la entidad persistida. `isOwnerOrAdmin` compara el nombre autenticado con `order.user.username` o busca `ROLE_ADMIN` entre las autoridades. Si no coincide devuelve `403` sin guardar.

`applyPatch` modifica sólo los valores no nulos y corrige el uso de `deliveryZip`. Después, el `Validator` revisa la orden completa; un conjunto de violaciones no vacío produce `422 Unprocessable Entity`. Una entidad válida se guarda una sola vez y `map(ResponseEntity::ok)` crea el `200`. `switchIfEmpty` cubre la orden ausente con `404`. `SecurityConfig` exige autenticación para el método PATCH antes de la regla general de órdenes.

## Flujo

PATCH → autenticar → buscar orden → comprobar propietario o ADMIN → aplicar sólo campos presentes → validar entidad completa → guardar → `200`. Las salidas alternativas son `401`, `403`, `404` y `422`.

## Archivos principales

- `OrderApiController.java`: autorización, aplicación del parche, validación y persistencia reactiva.
- `OrderPatchRequest.java`: lista blanca del contrato de entrada.
- `SecurityConfig.java`: protege la ruta PATCH.
- `User.java`: mantiene el usuario compatible con autenticación y persistencia.
- `OrderApiControllerTest.java`: cubre el comportamiento de TC-04.

## Pruebas

Las cuatro pruebas comprueban que cambiar el ZIP no altera el estado, que otro usuario recibe `403`, que una orden inexistente devuelve `404` y que un campo prohibido como `ccNumber` genera `400` antes de tocar el repositorio. También se verifica que el guardado ocurre exactamente una vez en el caso válido.

## Cambios realizados por otros TC

TC-08 mantuvo `OrderPatchRequest` como contrato de entrada y cambió únicamente la forma pública de la respuesta: la orden guardada se transforma en `OrderResponse`. La lista blanca, la autorización, la validación y la persistencia reactiva de TC-04 conservan su comportamiento.
