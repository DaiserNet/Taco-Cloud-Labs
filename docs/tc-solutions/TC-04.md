# TC-04 — PATCH de órdenes con lista blanca y sin ZIP mutante

## Objetivo

Asegurar `PATCH /api/orders/{orderId}` para que sólo el propietario de la orden o un usuario con rol `ADMIN` pueda modificar los datos de entrega permitidos, sin exponer campos sensibles ni aceptar una orden inválida después del cambio.

## Problema encontrado

El controlador recibía una `TacoOrder` completa como parche. Esto permitía intentar cambiar usuario, pago u otros campos que no pertenecen a una edición de entrega. No había autorización por propietario, la orden inexistente no se traducía explícitamente a `404` y existía un error funcional: al actualizar `deliveryZip` se copiaba `deliveryState`. La persistencia tampoco validaba la entidad resultante.

## Solución implementada

Se creó `OrderPatchRequest` con únicamente cinco propiedades: nombre, calle, ciudad, estado y código postal de entrega. `@JsonAnySetter` rechaza cualquier campo adicional durante la deserialización. El DTO existe aquí por una razón de seguridad, no como abstracción general.

El endpoint comprueba primero que exista una autenticación no anónima. Luego usa `findById(orderId).flatMap(...)` para trabajar sobre la entidad persistida. `isOwnerOrAdmin` compara el nombre autenticado con `order.user.username` o busca `ROLE_ADMIN` entre las autoridades. Si no coincide devuelve `403` sin guardar.

La solución fue:

### Flujo reactivo del PATCH

```java
@PatchMapping(path = "/{orderId}", consumes = "application/json")
public Mono<ResponseEntity<TacoOrder>> patchOrder(
    @PathVariable String orderId,
    @Valid @RequestBody OrderPatchRequest patch,
    Authentication authentication) {
  if (authentication == null
      || authentication instanceof AnonymousAuthenticationToken) {
    return Mono.just(ResponseEntity.status(HttpStatus.UNAUTHORIZED).build());
  }

  return repo.findById(orderId)
      .flatMap(order -> {
        if (!isOwnerOrAdmin(order, authentication)) {
          return Mono.just(ResponseEntity.status(HttpStatus.FORBIDDEN).build());
        }
        applyPatch(order, patch);
        Set<ConstraintViolation<TacoOrder>> violations = validator.validate(order);
        if (!violations.isEmpty()) {
          return Mono.just(ResponseEntity
              .status(HttpStatus.UNPROCESSABLE_ENTITY).build());
        }
        return repo.save(order).map(ResponseEntity::ok);
      })
      .switchIfEmpty(Mono.just(ResponseEntity.notFound().build()));
}
```

`applyPatch` modifica sólo los valores no nulos y corrige el uso de `deliveryZip`. Después, el `Validator` revisa la orden completa. Un conjunto de violaciones no vacío produce `422 Unprocessable Entity`. Una entidad válida se guarda una sola vez y `map(ResponseEntity::ok)` crea el `200`. `switchIfEmpty` cubre la orden ausente con `404`. `SecurityConfig` exige autenticación para el método PATCH antes de la regla general de órdenes.

### DTO con lista blanca

El contrato creado en TC-04 sólo contiene datos de entrega. Cualquier propiedad distinta provoca un error durante la lectura del JSON:

```java
@Data
public class OrderPatchRequest {
  private String deliveryName;
  private String deliveryStreet;
  private String deliveryCity;
  private String deliveryState;
  private String deliveryZip;

  @JsonAnySetter
  public void rejectUnknown(String name, Object value) {
    throw new IllegalArgumentException(
        "Field not allowed in order patch: " + name);
  }
}
```

`shouldRejectForbiddenPatchField` envía `ccNumber`. La prueba espera `400` y comprueba que el repositorio no guarde nada.

### Aplicación de campos presentes

El parche no reemplaza toda la entidad. Cada propiedad se copia sólo cuando fue incluida:

```java
private void applyPatch(TacoOrder order, OrderPatchRequest patch) {
  if (patch.getDeliveryState() != null) {
    order.setDeliveryState(patch.getDeliveryState());
  }
  if (patch.getDeliveryZip() != null) {
    order.setDeliveryZip(patch.getDeliveryZip());
  }
}
```

La asignación de `deliveryZip` corrige el error que antes copiaba el estado. `shouldPatchZipWithoutChangingState` verifica el nuevo ZIP, conserva el estado original y confirma una sola llamada a `save`.

### Propietario o ADMIN

La autorización del reto se aplicó sobre la orden recuperada:

```java
private boolean isOwnerOrAdmin(
    TacoOrder order, Authentication authentication) {
  boolean isOwner = order.getUser() != null
      && order.getUser().getUsername() != null
      && order.getUser().getUsername().equals(authentication.getName());
  boolean isAdmin = authentication.getAuthorities().stream()
      .anyMatch(a -> a.getAuthority().equals("ROLE_ADMIN"));
  return isOwner || isAdmin;
}
```

`shouldRejectPatchFromDifferentUser` comprueba que una orden ajena produce `403` y no llega a persistencia.

## Flujo

PATCH -> autenticar -> buscar orden -> comprobar propietario o ADMIN -> aplicar sólo campos presentes -> validar entidad completa -> guardar -> `200`. Las salidas alternativas son `401`, `403`, `404` y `422`.

- `OrderApiController.java`: autorización, aplicación del parche, validación y persistencia reactiva.
- `OrderPatchRequest.java`: lista blanca del contrato de entrada.

## Pruebas

Las pruebas comprueban que cambiar el ZIP no altera el estado, que otro usuario recibe `403`, que una orden inexistente devuelve `404` y que un campo prohibido como `ccNumber` genera `400` antes de tocar el repositorio. También se verifica que el guardado ocurre exactamente una vez en el caso válido.

## Cambios realizados por otros TC

TC-08 mantuvo `OrderPatchRequest` como contrato de entrada y cambió únicamente la forma pública de la respuesta: la orden guardada se transforma en `OrderResponse`. La lista blanca, la autorización, la validación y la persistencia reactiva de TC-04 conservan su comportamiento.

TC-09 añadió restricciones de longitud y contenido a los campos opcionales del parche. Los errores `403`, `404` y `422` se emiten ahora como Problem Details. La lista blanca y la única llamada a `save` permanecen iguales.

TC-11 trasladó la carga, autorización, aplicación de la lista blanca, validación y guardado de PATCH a `OrderService`. El contrato HTTP y el flujo reactivo de TC-04 permanecen iguales, pero la ruta requiere ahora `ROLE_USER` o `ROLE_ADMIN` y CSRF.

TC-12 eliminó PAN y CVV del dominio. `ccNumber` continúa siendo un campo prohibido y la lista blanca de PATCH conserva el mismo propósito.

TC-14 añadió líneas, cantidades e importes calculados a la orden. PATCH continúa limitado a datos de entrega, por lo que conserva sin cambios los precios y totales persistidos.
