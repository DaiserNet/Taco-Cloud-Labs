# TC-16 — Reservar y liberar inventario sin vender aire

## Objetivo

Reservar el stock necesario antes de aceptar una orden. Dos compradores no deben adquirir la misma unidad disponible. Si la reserva falla a la mitad, si la orden no puede guardarse o si una orden editable se elimina, el stock reservado debe regresar al catálogo.

La reserva también debe tener una identidad estable. Repetir la misma operación no puede descontar ni devolver las unidades por segunda vez.

## Problema encontrado

TC-13 añadió stock al catálogo y TC-14 comprobó que cada ingrediente tuviera unidades suficientes durante el cálculo. Esa comprobación era una lectura. Entre la lectura y el guardado de la orden, otra petición podía consumir las mismas unidades. Dos compradores podían ver stock 1 y los dos podían continuar.

La orden tampoco conservaba una referencia a una reserva. Sin esa identidad no era posible distinguir un reintento de una compra nueva ni liberar exactamente las unidades que una operación había descontado.

## Solución implementada

Se creó `InventoryService` en el módulo de datos. El servicio recibe la orden ya calculada, agrupa las cantidades por ingrediente y realiza cambios condicionales directamente en MongoDB. Toda la operación devuelve `Mono` y `Flux`. No usa `subscribe()` manual ni bloqueos.

La solución fue:

### Documento de reserva con estado

Cada intento guarda una `InventoryReservation` antes de modificar el catálogo. El documento conserva su ID, la clave de idempotencia interna, el ID de la orden, los elementos solicitados y los elementos que ya fueron descontados.

```java
@Document(collection = "inventoryReservation")
public class InventoryReservation {

  @Id
  private String id;
  private String idempotencyKey;
  private String orderId;
  private InventoryReservationStatus status;
  private List<InventoryReservationItem> items = new ArrayList<>();
  private List<InventoryReservationItem> reservedItems = new ArrayList<>();
}
```

Los estados `RESERVING`, `RESERVED`, `ACCEPTED`, `RELEASING` y `RELEASED` permiten saber qué cambios son válidos. `TacoOrder` guarda `inventoryReservationId` con `@JsonIgnore`. El dato se persiste para una cancelación posterior, pero no forma parte del contrato HTTP.

### Cantidades agrupadas en un orden estable

La cantidad de cada ingrediente se obtiene desde las líneas creadas por TC-14. Si una línea contiene tres tacos, cada ingrediente de ese taco necesita tres unidades. Un `TreeMap` agrupa IDs repetidos y deja un orden alfabético estable.

```java
private List<InventoryReservationItem> requestedItems(TacoOrder order) {
  Map<String, Long> quantities = new TreeMap<>();
  for (OrderLine line : safe(order.getItems())) {
    if (line == null || line.getTaco() == null || line.getQuantity() < 1) {
      throw invalid("Each order line must have a positive quantity.");
    }
    for (Ingredient ingredient : safe(line.getTaco().getIngredients())) {
      if (ingredient == null || !StringUtils.hasText(ingredient.getId())) {
        throw invalid("Every reserved ingredient must have an ID.");
      }
      quantities.merge(ingredient.getId(), (long) line.getQuantity(),
          Math::addExact);
    }
  }

  List<InventoryReservationItem> items = new ArrayList<>();
  quantities.forEach((id, quantity) -> items.add(
      new InventoryReservationItem(id, quantity.intValue())));
  return items;
}
```

El orden estable hace que una reserva parcial siempre intente los ingredientes en la misma secuencia. Esto vuelve predecible la compensación y simplifica las pruebas.

### Descuento atómico y condicionado

La reserva no lee el stock para restarlo después. `findAndModify` busca un ingrediente disponible cuyo `stockOnHand` sea mayor o igual que la cantidad solicitada. MongoDB evalúa la condición y aplica `$inc` como una sola operación atómica sobre ese documento.

```java
Query stockAvailable = Query.query(where("_id").is(item.getIngredientId())
    .and("available").is(true)
    .and("stockOnHand").gte(item.getQuantity()));
Update decrement = new Update().inc("stockOnHand", -item.getQuantity());

return mongo.findAndModify(stockAvailable, decrement,
        FindAndModifyOptions.options().returnNew(true), Ingredient.class)
    .switchIfEmpty(Mono.error(new InsufficientStockException(
        item.getIngredientId(), item.getQuantity())))
    .flatMap(ingredient -> recordReservedItem(reservationId, item)
        .then(ingredient.getStockOnHand() == 0
            ? markUnavailableIfEmpty(ingredient.getId())
            : Mono.empty()));
```

Si la condición no encuentra un documento, se emite `InsufficientStockException`. El error contiene `INSUFFICIENT_STOCK` y el ID del ingrediente. Como la resta sólo ocurre cuando existe stock suficiente, el valor nunca puede quedar negativo.

### Reserva secuencial y compensación

Los elementos se procesan con `concatMap`. Cada descuento correcto se registra en `reservedItems`. Si un ingrediente posterior falla, `onErrorResume` libera solamente lo que ya había sido reservado y después vuelve a emitir el error original.

```java
private Mono<InventoryReservation> reserveAll(
    InventoryReservation reservation) {
  return Flux.fromIterable(reservation.getItems())
      .concatMap(item -> reserveItem(reservation.getId(), item))
      .then(markReserved(reservation.getId()))
      .onErrorResume(error -> release(reservation.getId())
          .then(Mono.error(error)));
}
```

La liberación primero cambia el estado a `RELEASING` mediante una condición atómica. Sólo el proceso que obtiene ese estado incrementa el stock. Al final marca la reserva como `RELEASED`. Una segunda liberación encuentra el estado final y completa sin devolver unidades otra vez.

```java
public Mono<Void> release(String reservationId) {
  if (!StringUtils.hasText(reservationId)) {
    return Mono.empty();
  }
  return claimForRelease(reservationId)
      .flatMap(reservation -> Flux.fromIterable(
              safe(reservation.getReservedItems()))
          .concatMap(this::releaseItem)
          .then(markReleased(reservationId)))
      .switchIfEmpty(releasedAlready(reservationId));
}
```

### Reintento sin doble descuento

El ID de reserva se genera una vez y se guarda en la orden. La inserción del documento protege esa identidad. Si MongoDB informa una clave duplicada, el servicio lee la reserva existente. Sólo reutiliza una reserva `RESERVED` o `ACCEPTED` cuando sus elementos coinciden.

```java
return mongo.insert(reservation)
    .flatMap(this::reserveAll)
    .onErrorResume(DuplicateKeyException.class,
        error -> existingReservation(reservation));
```

Este control evita que un reintento con la misma identidad vuelva a descontar stock. También impide usar esa identidad para una lista distinta de ingredientes.

### Integración con la creación y eliminación de órdenes

`OrderService` integra la reserva en la misma cadena que ya calculaba precios, aplicaba el cupón, guardaba y publicaba. La orden se publica sólo después de guardar y aceptar la reserva.

```java
private Mono<TacoOrder> reserveSaveAndAccept(TacoOrder order) {
  return inventoryService.reserve(order)
      .flatMap(reservation -> saveReservedOrder(order, reservation));
}

private Mono<TacoOrder> saveReservedOrder(
    TacoOrder order, InventoryReservation reservation) {
  return Mono.defer(() -> repo.save(order))
      .onErrorResume(error -> releaseAndPropagate(reservation, error))
      .flatMap(savedOrder -> inventoryService
          .accept(reservation.getId(), savedOrder.getId())
          .thenReturn(savedOrder)
          .onErrorResume(error -> compensateUnacceptedOrder(
              savedOrder, reservation, error)));
}
```

Si falla el guardado, se libera la reserva. Si la orden se guardó pero no pudo aceptar la reserva, se borra la orden todavía no aceptada y después se libera el stock. `Mono.defer` retrasa cada efecto hasta su posición real dentro de la suscripción.

DELETE conserva las validaciones de propietario, rol y estado de TC-05. Después libera la reserva y sólo entonces borra la orden.

```java
public Mono<Void> deleteOrder(String orderId, Authentication authentication) {
  return findAuthorizedEditable(orderId, authentication)
      .flatMap(order -> inventoryService
          .release(order.getInventoryReservationId())
          .then(repo.deleteById(orderId)));
}
```

### Error HTTP identificable

El advice de TC-09 convierte `INSUFFICIENT_STOCK` en un Problem Details con estado `409`. El detalle indica qué ingrediente no pudo reservarse.

```java
@ExceptionHandler(InventoryReservationException.class)
public ResponseEntity<ApiProblem> handleInventoryReservation(
    InventoryReservationException error, HttpServletRequest request) {
  HttpStatus status = "INVENTORY_RESERVATION_INVALID".equals(error.getCode())
      ? HttpStatus.UNPROCESSABLE_ENTITY
      : HttpStatus.CONFLICT;
  return problem(status, "Inventory reservation failed",
      error.getMessage(), error.getCode(), Collections.emptyList(), request);
}
```

## Flujo

Creación correcta: request -> autenticar -> resolver pago -> calcular precios -> aplicar cupón -> crear reserva -> descontar cada ingrediente -> guardar orden -> aceptar reserva -> publicar -> responder.

Stock insuficiente: crear reserva -> descontar elementos anteriores -> falla un ingrediente -> reclamar liberación -> devolver unidades reservadas -> marcar `RELEASED` -> responder `409`.

Fallo de persistencia: reserva completa -> falla `save` -> liberar reserva -> propagar error sin publicar.

Fallo de aceptación: guardar orden -> falla `accept` -> borrar orden no aceptada -> liberar reserva -> propagar error sin publicar.

Cancelación permitida: buscar orden -> validar propietario o ADMIN -> validar estado editable -> liberar una sola vez -> borrar orden -> responder `204`.

## Pruebas

Se implementaron pruebas de integración con Spring Boot, `ReactiveMongoTemplate` y MongoDB embebido.

La prueba concurrente crea dos publishers que compiten por un ingrediente con una sola unidad. `Mono.zip` los suscribe en la misma operación. Sólo uno obtiene una reserva y el otro recibe `InsufficientStockException`. Después se consulta el documento real y se comprueba que el stock quedó en cero, nunca en un número negativo.

Las pruebas de compensación e idempotencia usan `StepVerifier` para suscribirse a toda la cadena. Luego leen la reserva y el ingrediente desde MongoDB. Esto demuestra cambios persistidos, no sólo llamadas simuladas.

Las pruebas de `OrderInventoryControllerTest` usan Mockito, `InOrder`, `StepVerifier` y `MockMvc`. Verifican el orden reserva -> guardado -> aceptación -> publicación. También comprueban que los fallos liberan el stock y que un rechazo de inventario impide guardar o publicar.
