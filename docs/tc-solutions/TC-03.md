# TC-03 — Construir Location sin localhost ni rutas rotas

## Objetivo

Corregir `POST /api/ingredients` para validar el ingrediente recibido, persistirlo mediante una cadena reactiva y devolver `201 Created` con un encabezado `Location` construido a partir del ID realmente guardado.

## Problema encontrado

El endpoint recibía un `Mono<Ingredient>` como cuerpo y construía manualmente una URL fija con host, puerto y una ruta que no correspondía al endpoint actual. Esa forma dificultaba que Bean Validation actuara directamente sobre el objeto de entrada y hacía que la ubicación dependiera del entorno de desarrollo. También era importante que el encabezado usara el resultado de `save`, porque el repositorio puede asignar o normalizar el identificador durante la persistencia.

## Solución implementada

El método recibe `@Valid @RequestBody Ingredient`. Las restricciones reales del dominio —`@NotBlank` para `id` y `name`, y `@NotNull` para `type`— se evalúan antes de ejecutar el controlador. Si fallan, Spring responde `400` y el repositorio no recibe ninguna llamada.

Para conservar un flujo explícito, el objeto se incorpora con `Mono.just(ingredient)`. `flatMap(repo::save)` encadena la persistencia porque `save` devuelve `Mono<Ingredient>`. Después, `map` trabaja con la entidad emitida por el repositorio y construye la URI mediante el `UriComponentsBuilder` suministrado por Spring: añade `/api/ingredients/{id}`, expande el ID guardado y crea `ResponseEntity.created(location).body(i)`.

La solución fue:

### Persistencia y construcción de Location

```java
@PostMapping
public Mono<ResponseEntity<Ingredient>> postIngredient(
    @Valid @RequestBody Ingredient ingredient,
    UriComponentsBuilder uriBuilder) {
  return Mono.just(ingredient)
      .flatMap(repo::save)
      .map(saved -> {
        URI location = uriBuilder
            .path("/api/ingredients/{id}")
            .buildAndExpand(saved.getId())
            .toUri();
        return ResponseEntity.created(location).body(saved);
      });
}
```

La URI deja de depender de `localhost` o de un puerto concreto. No se introduce un DTO porque en este reto el contrato de creación coincide con el modelo `Ingredient` y sus validaciones tienen una finalidad funcional directa.

### Validaciones del modelo usado en ese momento

TC-03 añadió las restricciones directamente a `Ingredient` porque esa entidad todavía era el contrato HTTP de creación:

```java
@Id
@NotBlank
private String id;

@NotBlank
private String name;

@NotNull
private Type type;
```

Spring evalúa estas anotaciones por el `@Valid` del controlador. `shouldReturnBadRequestForInvalidIngredient` envía ID y nombre vacíos con tipo nulo, espera `400` y verifica que `save` no reciba llamadas.

### Comprobación del ID persistido

La prueba de creación valida la ubicación generada y el cuerpo devuelto:

```java
testClient.post().uri("/api/ingredients")
    .bodyValue(ingredient)
    .exchange()
    .expectStatus().isCreated()
    .expectHeader().valueMatches(
        "Location", ".*/api/ingredients/PICK")
    .expectBody()
        .jsonPath("$.id").isEqualTo("PICK")
        .jsonPath("$.name").isEqualTo("Pickle")
        .jsonPath("$.type").isEqualTo("VEGGIES");
```

`shouldCreateIngredient` relaciona el ID emitido por `save` con el encabezado `Location`. Así se comprueba que no se usa una URL fija ni un valor anterior a la persistencia.

## Flujo

Petición POST -> deserializar y validar -> incorporar el ingrediente al `Mono` -> guardar -> tomar el ingrediente persistido -> construir `Location` -> responder `201`. Si la validación falla -> `400` sin guardar.

## Archivos principales

- `IngredientController.java`: implementa la composición de creación y la URI relativa al contexto.
- `Ingredient.java`: declara las restricciones de ID, nombre y tipo.
- `IngredientControllerTest.java`: prueba la creación válida y el rechazo de datos inválidos.

## Pruebas

La prueba válida comprueba `201`, un `Location` terminado en `/api/ingredients/PICK`, el cuerpo completo y una única llamada a `save` con los valores esperados. La prueba inválida envía ID y nombre vacíos y tipo nulo. Espera `400` y verifica que el repositorio no fue invocado.

| Concepto comprobado | Test | Archivo |
|---|---|---|
| Persistencia reactiva, cuerpo y `Location` con el ID guardado | `shouldCreateIngredient` | `IngredientControllerTest.java` |
| Bean Validation antes de acceder al repositorio | `shouldReturnBadRequestForInvalidIngredient` | `IngredientControllerTest.java` |

## Cambios realizados por otros TC

TC-08 sustituyó el cuerpo `Ingredient` por `IngredientRequest` y proyecta la entidad guardada como `IngredientResponse`. La validación, el guardado reactivo y la construcción de `Location` con el ID persistido permanecen iguales.

TC-09 amplió las restricciones de `IngredientRequest`. Una entrada semánticamente inválida responde ahora `422` con las violaciones por campo. El JSON mal formado continúa respondiendo `400`. La creación válida conserva el mismo flujo y `Location`.

TC-11 limitó la creación de ingredientes a `ROLE_ADMIN`, activó CSRF y centralizó CORS para `/api/**` mediante una lista configurable de orígenes. La construcción de `Location` y el guardado de TC-03 no cambiaron.

TC-13 amplió la entidad persistente con datos de catálogo. Los ingredientes creados mediante el endpoint de TC-03 comienzan con precio y stock en cero y con disponibilidad desactivada. Estos valores se administran después mediante los endpoints de catálogo protegidos.
