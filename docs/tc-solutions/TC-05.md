# TC-05 — PUT y DELETE de órdenes con identidad consistente

## Objetivo

Completar `PUT /api/orders/{orderId}` y `DELETE /api/orders/{orderId}` con búsqueda previa, autorización de propietario o `ADMIN`, control mínimo de estado y composición reactiva. El ID de ruta debe gobernar la operación y una orden inexistente nunca debe crearse accidentalmente.

## Problema encontrado

El PUT anterior recibía una orden completa y ejecutaba `save` sin buscarla. El cuerpo podía redirigir la escritura mediante su ID y reemplazar campos administrados por el servidor, como usuario, fecha, pago o tacos. El DELETE devolvía `void`, ignoraba el publisher de `deleteById` y trataba de capturar síncronamente una excepción de una operación asíncrona. Ninguno de los dos endpoints autorizaba al propietario ni impedía cambios sobre una orden que ya se estaba preparando.

## Solución implementada

Se añadió `OrderReplaceRequest`, un DTO pequeño con los cinco datos de entrega requeridos. Su `@JsonAnySetter` rechaza `id` y cualquier propiedad fuera de la lista blanca. Así el ID de ruta es el único identificador posible y `applyTo` no toca usuario, `placedAt`, datos de pago ni tacos.

PUT inicia con `findById(orderId)`, reutiliza la regla `isOwnerOrAdmin`, exige un estado editable y sólo entonces aplica el reemplazo y llama una vez a `save`. Emite `403`, `404` o `409 Conflict` sin escribir cuando corresponde.

DELETE usa la misma búsqueda, autorización y regla de estado. `repo.deleteById(orderId).thenReturn(...)` vincula el `Mono<Void>` del repositorio con la respuesta y sólo emite `204` después de completar. No contiene `void`, `subscribe()`, `block()` ni `try/catch` alrededor del publisher.

La solución fue:

### PUT y DELETE sobre la orden persistida

```java
@PutMapping(path = "/{orderId}", consumes = "application/json")
public Mono<ResponseEntity<TacoOrder>> putOrder(
    @PathVariable String orderId,
    @Valid @RequestBody OrderReplaceRequest replacement,
    Authentication authentication) {
  if (isUnauthenticated(authentication)) {
    return Mono.just(ResponseEntity.status(HttpStatus.UNAUTHORIZED).build());
  }

  return Mono.defer(() -> repo.findById(orderId)
      .flatMap(order -> {
        if (!isOwnerOrAdmin(order, authentication)) {
          return Mono.just(ResponseEntity.status(HttpStatus.FORBIDDEN).build());
        }
        if (!isEditable(order)) {
          return Mono.just(ResponseEntity.status(HttpStatus.CONFLICT).build());
        }
        replacement.applyTo(order);
        return repo.save(order).map(ResponseEntity::ok);
      }))
      .switchIfEmpty(Mono.just(ResponseEntity.notFound().build()));
}

@DeleteMapping("/{orderId}")
public Mono<ResponseEntity<Void>> deleteOrder(
    @PathVariable String orderId, Authentication authentication) {
  if (isUnauthenticated(authentication)) {
    return Mono.just(ResponseEntity.status(HttpStatus.UNAUTHORIZED).build());
  }

  return Mono.defer(() -> repo.findById(orderId)
      .flatMap(order -> {
        if (!isOwnerOrAdmin(order, authentication)) {
          return Mono.just(ResponseEntity.status(HttpStatus.FORBIDDEN).build());
        }
        if (!isEditable(order)) {
          return Mono.just(ResponseEntity.status(HttpStatus.CONFLICT).build());
        }
        return repo.deleteById(orderId)
            .thenReturn(ResponseEntity.noContent().build());
      }))
      .switchIfEmpty(Mono.just(ResponseEntity.notFound().build()));
}
```

El modelo incorpora únicamente `OrderStatus.PLACED` y `PREPARING`. `PLACED` es el valor inicial y `null` se acepta para órdenes históricas. No se construyó la máquina de estados futura. `SecurityConfig` exige autenticación para PUT y DELETE.

### Reemplazo limitado a datos de entrega

`OrderReplaceRequest` contiene los datos que PUT puede sustituir. `applyTo` no recibe ni modifica usuario, fecha, pago o tacos:

```java
@NotBlank
@Size(max = 100)
private String deliveryName;

@NotBlank
@Size(max = 20)
private String deliveryZip;

@JsonAnySetter
public void rejectUnknown(String name, Object value) {
  throw new IllegalArgumentException(
      "Field not allowed in order replacement: " + name);
}

public void applyTo(TacoOrder order) {
  order.setDeliveryName(deliveryName);
  order.setDeliveryStreet(deliveryStreet);
  order.setDeliveryCity(deliveryCity);
  order.setDeliveryState(deliveryState);
  order.setDeliveryZip(deliveryZip);
}
```

`shouldReplaceEditableOrderAndPreserveServerManagedFields` comprueba que sólo cambian los datos de entrega. `shouldRejectBodyIdBeforeRepositoryAccess` envía un ID en el cuerpo y verifica que la deserialización lo rechace antes de buscar la orden.

### Estado editable mínimo

La regla de TC-05 considera editable una orden nueva o histórica sin estado:

```java
private boolean isEditable(TacoOrder order) {
  return order.getStatus() == null
      || order.getStatus() == OrderStatus.PLACED;
}
```

PUT y DELETE llaman a esta misma función. `shouldRejectReplacementWhenOrderIsNotEditable` y `shouldRejectDeleteWhenOrderIsNotEditable` usan `PREPARING` y esperan `409` sin escritura.

### Espera real del DELETE

La prueba mantiene la eliminación pendiente con `TestPublisher`:

```java
TestPublisher<Void> deletePublisher = TestPublisher.createCold();
PublisherProbe<Void> deleteProbe = PublisherProbe.of(
    deletePublisher.mono());
when(repo.deleteById("ORDER1")).thenReturn(deleteProbe.mono());

StepVerifier.create(controller.deleteOrder(
        "ORDER1", userAuthentication("habuma")))
    .expectSubscription()
    .then(deleteProbe::assertWasSubscribed)
    .expectNoEvent(Duration.ofMillis(20))
    .then(deletePublisher::complete)
    .assertNext(response -> assertEquals(
        HttpStatus.NO_CONTENT, response.getStatusCode()))
    .verifyComplete();
```

`shouldWaitForDeleteCompletionBeforeReturningNoContent` demuestra que el `204` no aparece mientras el repositorio no haya completado su publisher.

## Flujo

PUT/DELETE -> autenticar -> buscar por ID de ruta -> comprobar owner/ADMIN -> comprobar `PLACED` -> reemplazar y guardar, o borrar y esperar completion -> responder. Ausente -> `404`. Ajena -> `403`. No editable -> `409`.

## Pruebas

Se cubren PUT válido y preservación de campos, ID prohibido, orden ausente, propietario incorrecto y estado incompatible. Para DELETE se cubren éxito, ausencia, propietario incorrecto, estado incompatible y permiso de ADMIN. `TestPublisher` mantiene el borrado pendiente y `PublisherProbe` demuestra la suscripción. No aparece `204` hasta completar el publisher.

## Cambios realizados por otros TC

TC-08 conservó `OrderReplaceRequest` y las reglas de búsqueda, propietario, estado y guardado de PUT. La respuesta exitosa se proyecta ahora como `OrderResponse`. DELETE mantiene el mismo contrato HTTP sin cuerpo y la misma espera por la finalización del repositorio.

TC-09 centralizó las respuestas de error de PUT y DELETE. Propietario incorrecto, orden inexistente y estado incompatible conservan `403`, `404` y `409`, pero ahora producen Problem Details mediante señales reactivas. Las rutas válidas siguen guardando o borrando una sola vez.

TC-11 movió las reglas compartidas de propietario, ADMIN y estado editable a `OrderService`. PUT y DELETE conservan sus publishers y respuestas, mientras la matriz global exige `ROLE_USER` o `ROLE_ADMIN` y CSRF para llegar al caso de uso.

TC-12 sustituyó los datos completos de tarjeta por `paymentMethodId`, marca y últimos cuatro dígitos. PUT preserva ahora ese resumen seguro. DELETE no cambió.

TC-14 añadió líneas, cantidades e importes administrados por el servidor. PUT continúa reemplazando sólo datos editables y conserva las líneas y la instantánea monetaria de la orden existente. DELETE mantiene su comportamiento.

TC-16 añadió la liberación de inventario al DELETE. Después de validar propietario, rol y estado, el servicio libera la reserva de la orden y sólo entonces encadena `deleteById`. El `204` continúa esperando la finalización de todos los publishers.

TC-25 reserva DELETE físico para órdenes históricas en `PLACED`. Las compras nuevas comienzan en `CREATED` y usan `POST /api/orders/{id}/cancel`, que registra `CANCELLED` y libera inventario sin borrar la orden. PUT sigue permitido sólo antes de avanzar desde `CREATED` o en `PLACED` histórico.
