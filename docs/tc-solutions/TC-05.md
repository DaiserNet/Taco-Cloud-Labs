# TC-05 — PUT y DELETE de órdenes con identidad consistente

## Objetivo

Completar `PUT /api/orders/{orderId}` y `DELETE /api/orders/{orderId}` con búsqueda previa, autorización de propietario o `ADMIN`, control mínimo de estado y composición reactiva. El ID de ruta debe gobernar la operación y una orden inexistente nunca debe crearse accidentalmente.

## Problema encontrado

El PUT anterior recibía una orden completa y ejecutaba `save` sin buscarla. El cuerpo podía redirigir la escritura mediante su ID y reemplazar campos administrados por el servidor, como usuario, fecha, pago o tacos. El DELETE devolvía `void`, ignoraba el publisher de `deleteById` y trataba de capturar síncronamente una excepción de una operación asíncrona. Ninguno de los dos endpoints autorizaba al propietario ni impedía cambios sobre una orden que ya se estaba preparando.

## Solución implementada

Se añadió `OrderReplaceRequest`, un DTO pequeño con los cinco datos de entrega requeridos. Su `@JsonAnySetter` rechaza `id` y cualquier propiedad fuera de la lista blanca. Así el ID de ruta es el único identificador posible y `applyTo` no toca usuario, `placedAt`, datos de pago ni tacos.

PUT inicia con `findById(orderId)`, reutiliza la regla `isOwnerOrAdmin`, exige un estado editable y sólo entonces aplica el reemplazo y llama una vez a `save`. Emite `403`, `404` o `409 Conflict` sin escribir cuando corresponde.

DELETE usa la misma búsqueda, autorización y regla de estado. `repo.deleteById(orderId).thenReturn(...)` vincula el `Mono<Void>` del repositorio con la respuesta y sólo emite `204` después de completar. No contiene `void`, `subscribe()`, `block()` ni `try/catch` alrededor del publisher.

El modelo incorpora únicamente `OrderStatus.PLACED` y `PREPARING`; `PLACED` es el valor inicial y `null` se acepta para órdenes históricas. No se construyó la máquina de estados futura. `SecurityConfig` exige autenticación para PUT y DELETE.

## Flujo

PUT/DELETE → autenticar → buscar por ID de ruta → comprobar owner/ADMIN → comprobar `PLACED` → reemplazar y guardar, o borrar y esperar completion → responder. Ausente → `404`; ajena → `403`; no editable → `409`.

## Archivos principales

- `OrderApiController.java`: implementa ambos flujos y comparte autorización/estado.
- `OrderReplaceRequest.java`: contrato seguro de reemplazo.
- `TacoOrder.java` y `OrderStatus.java`: estado mínimo requerido.
- `SecurityConfig.java`: autentica PUT y DELETE.
- `OrderPutDeleteControllerTest.java`: diez casos específicos de TC-05.

## Pruebas

Se cubren PUT válido y preservación de campos, ID prohibido, orden ausente, propietario incorrecto y estado incompatible. Para DELETE se cubren éxito, ausencia, propietario incorrecto, estado incompatible y permiso de ADMIN. `TestPublisher` mantiene el borrado pendiente y `PublisherProbe` demuestra la suscripción; no aparece `204` hasta completar el publisher.

## Cambios realizados por otros TC

TC-08 conservó `OrderReplaceRequest` y las reglas de búsqueda, propietario, estado y guardado de PUT. La respuesta exitosa se proyecta ahora como `OrderResponse`. DELETE mantiene el mismo contrato HTTP sin cuerpo y la misma espera por la finalización del repositorio.

TC-09 centralizó las respuestas de error de PUT y DELETE. Propietario incorrecto, orden inexistente y estado incompatible conservan `403`, `404` y `409`, pero ahora producen Problem Details mediante señales reactivas; las rutas válidas siguen guardando o borrando una sola vez.
