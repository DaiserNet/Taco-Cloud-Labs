# TC-23 — Historial paginado y privado de órdenes

## Objetivo

Ofrecer a cada usuario un historial de sus órdenes, paginado y ordenado por fecha de compra descendente con ID como desempate. El listado debe mostrar resúmenes y el detalle debe conservar un contrato seguro. ADMIN necesita una ruta propia para consultar el historial global con filtros.

## Problema encontrado

`GET /api/orders` mezclaba dos propósitos. Para USER consultaba órdenes por nombre de usuario y para ADMIN hacía `findAll()`. No ofrecía paginación ni un orden secundario estable. La misma respuesta extensa se utilizaba como listado y detalle. Esto dificultaba comprobar el aislamiento entre usuarios y hacía que la auditoría administrativa dependiera de un comportamiento implícito.

## Solución implementada

La solución fue reemplazar ese GET por `GET /api/orders/me` y `GET /api/orders/me/{id}`. ADMIN utiliza `GET /api/admin/orders` y `GET /api/admin/orders/{id}`. El listado administrativo acepta `userId` y `status` como filtros opcionales. `OrderHistoryService` resuelve al usuario autenticado en `UserRepository` y consulta MongoDB mediante su ID persistente. El detalle propio incluye ese mismo filtro en la consulta, por lo que una orden ajena responde 404 sin revelar si existe.

```java
return currentUser(authentication)
    .flatMap(user -> mongo.findOne(Query.query(owner(user.getId())
        .and("_id").is(orderId)), TacoOrder.class))
    .switchIfEmpty(notFound())
    .map(orderMapper::toResponse);
```

La página se construye en MongoDB con `skip` y `limit`. Se ordena por `placedAt` descendente y `_id` ascendente. El conteo utiliza los mismos filtros. `Mono.zip` reúne contenido y total antes de crear la respuesta. `page` empieza en cero, `size` debe estar entre 1 y el máximo configurable de 50. Una página posterior a la última devuelve HTTP 200 con `content` vacío y la metadata total conservada. Se añadieron índices para propietario, fecha, ID y los filtros administrativos principales.

```java
Query paged = Query.of(filter).with(HISTORY_SORT)
    .skip((long) page * size).limit(size);
return Mono.zip(mongo.find(paged, TacoOrder.class)
        .map(orderMapper::toSummary).collectList(),
    mongo.count(filter, TacoOrder.class));
```

`OrderSummaryResponse` contiene sólo ID, fecha, estado, total y moneda. El detalle reutiliza `OrderResponse`, que incluye datos de entrega y, del pago, sólo marca y últimos cuatro dígitos. No serializa `User`, contraseña ni token. `SecurityConfig` reserva las rutas `me` a `ROLE_USER`, las rutas `/api/admin/**` a `ROLE_ADMIN` y deniega los GET antiguos de `/api/orders`. PATCH, PUT y DELETE conservan su verificación previa de propietario o ADMIN. En esas acciones, la política existente responde 403 a otro propietario.

## Flujo

Historial propio: autenticación -> resolver usuario persistido -> filtrar por `user._id` en MongoDB -> ordenar y paginar -> convertir a resúmenes -> devolver metadata. Detalle propio: autenticación -> consultar por propietario e ID -> convertir a `OrderResponse` o responder 404. Auditoría: comprobar ADMIN -> aplicar filtros opcionales en MongoDB -> paginar y responder.

## Archivos principales

- `OrderHistoryService.java` y `OrderHistoryController.java`: consultas reactivas, identidad, paginación y rutas.
- `OrderSummaryResponse.java`, `OrderHistoryPageResponse.java` y `OrderMapper.java`: resumen, metadata y detalle seguro.
- `TacoOrder.java`: índices de MongoDB acordes al historial.
- `OrderApiController.java` y `OrderService.java`: retiran el listado global implícito sin alterar las acciones.
- `SecurityConfig.java` y `application.yml`: autorización explícita y tamaño máximo configurable.

## Pruebas

Las pruebas de datos usan MongoDB embebido para verificar filtros, orden, paginación e índices reales. Las pruebas HTTP inspeccionan el JSON. La regresión de acciones comprueba que las reglas de propietario continúan funcionando.

| Concepto | Test | Archivo |
|---|---|---|

| Fecha descendente, desempate y página vacía | `shouldOrderByPlacedAtThenIdAndReturnEmptyOutOfRangePage` | `OrderHistoryMongoTest.java` |

## Cambios realizados por otros TC

TC-24 reutiliza la consulta privada de detalle para obtener la orden de origen antes de cotizar o confirmar una recompra. `OrderHistoryService.findOwnedOrder` conserva el filtro por propietario e ID y el detalle de TC-23 sigue usando `OrderMapper.toResponse` para responder de forma segura.

TC-25 permite que el historial muestre los nuevos estados. El resumen conserva su tamaño reducido y el detalle seguro incorpora versión e historial de cambios. La paginación, los filtros de propietario y la auditoría ADMIN no cambiaron.
