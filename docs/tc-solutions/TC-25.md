# TC-25 — Flujo de estados de una orden

## Objetivo

Hacer que una orden avance por estados válidos y registre cada cambio. Cocina y administración actúan sólo en sus etapas. El propietario puede cancelar antes de la preparación. Los cambios concurrentes deben detectarse sin copiar datos sensibles a la auditoría.

## Problema encontrado

La entidad sólo conocía `PLACED` y `PREPARING`. La creación no registraba cómo nació la orden. No existía un servicio que decidiera qué transición era válida, quién podía ejecutarla o cuándo era demasiado tarde para cancelar. Dos escrituras podían partir de la misma versión sin comprobar concurrencia.

## Solución implementada

La solución fue incorporar `CREATED`, `ACCEPTED`, `PREPARING`, `READY`, `OUT_FOR_DELIVERY`, `DELIVERED` y `CANCELLED`. `PLACED` permanece para documentos históricos y para el contrato anterior de eliminación física, pero las compras nuevas comienzan en `CREATED`. `TacoOrder` tiene `@Version`, que Spring Data MongoDB usa al guardar para rechazar una copia obsoleta. `OrderResponse` entrega esa versión al cliente para enviarla como `expectedVersion` en la siguiente transición.

`OrderWorkflowService` contiene una matriz pequeña: KITCHEN o ADMIN pueden avanzar desde `CREATED` hasta `READY`, etapa por etapa. Sólo ADMIN puede pasar a reparto y entrega. USER no puede usar la ruta de avance. La matriz se consulta antes de guardar. Un salto de estado responde 409 y una transición existente solicitada por un rol no autorizado responde 403.

```java
OrderStatus previous = order.getStatus();
order.setStatus(target);
append(order, previous, target, authentication.getName(), role,
    role.equals(KITCHEN) ? "KITCHEN_API" : "ADMIN_API", reason);
return orders.save(order);
```

Cada entrada de `statusHistory` guarda estado anterior y nuevo, actor, rol, fecha, origen y razón. Se añade dentro del mismo documento que cambia de estado. La fecha de cada entrada es posterior a la anterior. La respuesta HTTP usa el mapper seguro y no incluye contraseña, tarjeta, token ni el objeto `User`. La entidad no serializa el historial en el mensaje directo de cocina.

`POST /api/orders/{id}/cancel` comprueba `ROLE_USER`, propietario y estado `CREATED` o `ACCEPTED`. Primero guarda `CANCELLED` con su auditoría y después libera la reserva mediante el servicio de inventario. Repetir la cancelación no crea otra entrada y vuelve a intentar una liberación pendiente. `PATCH /api/orders/{id}/status` recibe destino, razón y versión esperada. Repetir una transición ya completada devuelve el estado existente sin duplicar el historial.

```java
if (!canCancel(order.getStatus())
    || !Objects.equals(order.getVersion(), expectedVersion)) {
  return Mono.error(conflict());
}
return orders.save(order)
    .flatMap(saved -> inventory.release(saved.getInventoryReservationId())
        .thenReturn(saved));
```

## Flujo

Creación -> registrar `CREATED` -> reservar, guardar, aceptar inventario y publicar. Avance -> autenticar rol -> cargar orden -> comprobar matriz y versión -> añadir auditoría -> guardar. Cancelación -> verificar propietario y etapa -> guardar `CANCELLED` -> liberar inventario -> responder.

## Archivos principales

- `OrderStatus.java`, `OrderStatusChange.java` y `TacoOrder.java`: estados, auditoría embebida y versión de MongoDB.
- `OrderWorkflowService.java`: matriz, permisos, cancelación e idempotencia de repeticiones.
- `OrderWorkflowController.java`, `OrderStatusRequest.java` y `OrderCancelRequest.java`: rutas y entradas limitadas.
- `OrderService.java`: marca las órdenes nuevas como `CREATED` y registra el origen HTTP, correo o recompra.
- `OrderMapper.java` y `OrderResponse.java`: exponen versión e historial mediante el contrato seguro.
- `SecurityConfig.java` y `ApiExceptionHandler.java`: roles, CSRF y respuesta 409 por versión obsoleta.

## Cambios realizados por otros TC

TC-26 convirtió `CREATED -> ACCEPTED` en un claim atómico de la siguiente orden, reservado a KITCHEN. Cocina ya no usa la ruta general de estado, porque esa respuesta incluye datos de entrega. Avanza a `PREPARING` y `READY` por la ruta segura de cocina. La matriz, la auditoría y el bloqueo optimista de TC-25 siguen aplicándose. Al quedar `READY` o `CANCELLED`, se libera la asignación activa de la estación.
