# TC-18 — Taco Physics: reglas componibles de diseño

## Objetivo

Comprobar la composición de un taco antes de guardarlo, cotizarlo o reservar ingredientes. Las reglas deben poder ampliarse sin una cadena extensa de condiciones. La API debe informar todas las violaciones mediante códigos estables y mensajes comprensibles.

## Problema encontrado

`TacoCreateRequest` sólo comprobaba algunos campos. No impedía dos bases, ingredientes repetidos o una composición fuera de límites. `OrderPricingService` verificaba disponibilidad y precio, pero no compartía reglas de diseño con el catálogo ni con la cotización. Una orden podía llegar a la reserva con un taco inválido.

## Solución implementada

La solución fue definir `TacoDesignRule`. Cada regla examina un `TacoDesignContext` y devuelve una lista de `TacoDesignViolation`. La regla no guarda datos ni lanza una excepción genérica. `TacoDesignValidator` recibe la colección de reglas por inyección de Spring, las ejecuta y ordena las violaciones por código y mensaje. Así el orden de los componentes no cambia la respuesta.

```java
public interface TacoDesignRule {
  List<TacoDesignViolation> check(TacoDesignContext design);
}
```

Se añadieron reglas para exigir exactamente una base `WRAP` o `BOWL`, entre 2 y 12 ingredientes, IDs sin duplicados e ingredientes conocidos y disponibles. Dos reglas configurables completan la composición: un ingrediente `EXTREME` exige otro de un tipo configurado, por defecto `VEGGIES`, y un taco con `PROTEIN` exige otro de un tipo configurado, por defecto `SAUCE`. Cada una puede desactivarse mediante propiedades. Estas reglas usan tipos y nivel de picante, no IDs de productos codificados en la lógica.

El validador consulta cada ID distinto una sola vez. `concatMap` mantiene una secuencia predecible de consultas y `collectMap` espera la resolución completa. Después ejecuta todas las reglas, elimina violaciones idénticas y devuelve el taco con ingredientes canónicos sólo si es válido.

```java
return Flux.fromIterable(uniqueIds)
    .concatMap(id -> ingredientRepo.findById(id)
        .map(ingredient -> new FoundIngredient(id, ingredient))
        .defaultIfEmpty(new FoundIngredient(id, null)))
    .collectMap(found -> found.id)
    .map(found -> {
      Map<String, Ingredient> catalog = new HashMap<>();
      found.forEach((id, result) -> {
        if (result.ingredient != null) {
          catalog.put(id, result.ingredient);
        }
      });
      return evaluate(taco, ids, catalog);
    });
```

`POST /api/tacos/validate` devuelve `valid` y `violations` sin guardar. `POST /api/tacos` usa el mismo validador antes del repositorio. La cotización lo ejecuta cuando recibe un taco en línea o un `tacoId`. `OrderPricingService` valida antes de calcular importes. Como la reserva ocurre después del cálculo, un diseño inválido no llega a `InventoryService.reserve`. Los rechazos HTTP 422 conservan Problem Details y añaden los códigos de cada violación.

## Flujo

Entrada de diseño -> obtener IDs distintos -> consultar catálogo -> ejecutar todas las reglas -> ordenar violaciones -> responder o continuar.

Creación de orden -> validar diseño -> calcular precios -> aplicar cupón -> reservar inventario -> guardar orden.

## Archivos principales

- `Ingredient.java` y `DevelopmentConfig.java`: incorporan la base `BOWL` y un ejemplo de catálogo.
- `TacoDesignRule.java`, `TacoDesignContext.java`, `TacoDesignValidator.java` y las clases de reglas: componen la validación y consultan los ingredientes reales.
- `TacoDesignViolation.java`, `TacoDesignValidationResponse.java`, `TacoDesignException.java` y `ApiExceptionHandler.java`: transportan códigos y mensajes en la respuesta.
- `TacoController.java`, `TacoCreateRequest.java`, `CouponController.java` y `OrderQuoteRequest.java`: validan los diseños del catálogo y de la cotización.
- `OrderPricingService.java` y `OrderCreateRequest.java`: aplican las reglas antes del precio y la reserva.
- `SecurityConfig.java`: permite validar un diseño a USER o ADMIN sin abrir la creación del catálogo a USER.
