# TC-24 — Reordenar una compra anterior con reglas actuales

## Objetivo

Permitir que un usuario compre de nuevo a partir de una orden propia. La compra nueva debe tener identidad, fecha y estado propios. Antes de confirmarla se deben aplicar las reglas actuales de diseño, disponibilidad, precios, cupones, inventario y pago. El cliente debe ver los cambios de precio o ingredientes y confirmarlos expresamente.

## Problema encontrado

El historial de TC-23 permitía consultar compras anteriores, pero no convertirlas en una compra nueva. Guardar una copia del documento histórico también copiaría importes, estado y referencias de pago que ya no representan el catálogo actual. Además, dos confirmaciones de la misma petición podrían crear órdenes duplicadas.

## Solución implementada

La solución fue separar cotización y confirmación. `POST /api/orders/me/{sourceOrderId}/reorder/quote` busca la orden con el filtro de propietario de TC-23. `OrderMapper.toReorderRequest` toma sólo entrega, nombres de tacos, IDs de ingredientes y cantidades. El método de pago se elige de nuevo y `PaymentMethodService.findOwned` comprueba que pertenece al usuario. El cuerpo no acepta ID de orden, token ni datos de tarjeta.

```java
return history.findOwnedOrder(sourceOrderId, authentication)
    .flatMap(source -> prepare(source, request, authentication))
    .map(prepared -> prepared.quote);
```

`prepare` utiliza `OrderPricingService.price` y `CouponService.apply`. El primero vuelve a ejecutar Taco Physics con ingredientes del catálogo actual. Luego se suman las unidades necesarias por ingrediente y se comprueba el stock sin reservarlo. La respuesta compara el total histórico y el actual, informa cambios de nombre, precio unitario o metadata de ingredientes y devuelve una huella de la cotización. Esta operación no guarda ni publica una orden.

`POST /api/orders/me/{sourceOrderId}/reorder` exige la huella e `Idempotency-Key`. Primero se vuelve a preparar la cotización. Si cambió, responde 409. Una marca única en MongoDB asocia usuario, clave, petición y nueva orden. Después se crea una entidad nueva y se usa `OrderService.createOrder`, que vuelve a calcular el precio, comprueba la huella justo antes de reservar y ejecuta el flujo existente de reserva, guardado, aceptación y publicación.

```java
return Mono.defer(() -> beforeReservation.apply(pricedOrder))
    .then(Mono.defer(() -> reserveSaveAndAccept(pricedOrder)));
```

La segunda confirmación exitosa con la misma clave y petición devuelve la orden creada con HTTP 200 y `replayed=true`. La primera devuelve HTTP 201. Una clave reutilizada con otra petición responde 409.

## Flujo

Cotización: autenticar -> buscar orden propia -> construir petición nueva -> validar pago, diseño, cupón y stock -> comparar importes e ingredientes -> responder huella.

Confirmación: autenticar -> comprobar huella -> reclamar clave -> crear identidad nueva -> recalcular -> verificar huella -> reservar -> guardar -> aceptar -> publicar -> responder. Reintento completado -> leer la misma orden -> responder sin efectos nuevos.

## Archivos principales

- `ReorderController.java` y `ReorderService.java`: rutas, cotización, confirmación e idempotencia.
- `ReorderRequest.java`, `ReorderQuoteResponse.java` y `ReorderConfirmResponse.java`: contratos separados para elegir pago, presentar diferencias y distinguir creación de reintento.
- `ReorderAttempt.java`: conserva la relación entre clave idempotente y orden nueva.
- `OrderMapper.java`: reconstruye la petición con los datos reutilizables de la orden histórica.
- `OrderHistoryService.java`: expone la consulta filtrada por propietario.
- `OrderService.java`: permite comprobar la cotización después del cálculo y antes de la reserva.

## Cambios realizados por otros TC

TC-25 hace que la orden creada por recompra comience en `CREATED` y conserve una entrada inicial de auditoría con origen `REORDER`. La cotización, la nueva identidad y la idempotencia de TC-24 se mantienen.
