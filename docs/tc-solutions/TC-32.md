# TC-32 — Métricas y salud que explican el negocio

## Objetivo

Mostrar si las compras, el inventario, el outbox y cocina funcionan mediante métricas y señales de salud. La información operativa debe estar disponible sin exponer credenciales ni crear una serie distinta por usuario, orden o petición.

## Problema encontrado

La API sólo exponía `health` e `info`. El consumidor RabbitMQ contaba resultados de entrega, pero no medía el tiempo de procesamiento. No había contadores de compras ni una medida del backlog del outbox. `TacoCountInfoContributor` llamaba a `block()` durante la consulta de Actuator. Una respuesta lenta de Mongo podía bloquear el hilo que atendía esa consulta.

## Solución implementada

La solución fue añadir `OrderMetrics` al caso de uso de creación. Envuelve la cadena con `Mono.defer`, de modo que inicia el timer al suscribirse. Cuenta una compra sólo cuando la orden se confirma. Cuenta el cupón únicamente si esa compra terminada lo aplicó. Ante un error, registra el fallo y distingue `InsufficientStockException` como rechazo de stock. Las etiquetas `source`, `result` y `transport` se reducen a valores conocidos.

```java
return Mono.defer(() -> {
  Timer.Sample sample = Timer.start(registry);
  return operation
      .doOnSuccess(order -> {
        if (order == null) {
          failed(source);
          sample.stop(timer(source, "empty"));
          return;
        }
        registry.counter("tacocloud.orders.created", "source", source,
            "transport", transport).increment();
        if (order.isCouponApplied()) {
          registry.counter("tacocloud.coupons.applied", "source", source)
              .increment();
        }
        sample.stop(timer(source, "created"));
      })
      .doOnError(error -> {
        failed(source);
        if (error instanceof InsufficientStockException) {
          registry.counter("tacocloud.inventory.stock.rejected",
              "source", source).increment();
        }
        sample.stop(timer(source, "failed"));
      });
});
```

`OrderWorkflowService` incrementa `tacocloud.orders.cancelled` después de guardar por primera vez el estado `CANCELLED`. Repetir sólo la liberación de inventario no aumenta el contador. `OutboxHealthIndicator` consulta reactivamente cuántos documentos siguen en `NEW`, `FAILED` o `PUBLISHING`. Guarda la última muestra en memoria para que el gauge y health la lean sin bloquear. Health baja si la muestra falta, está vencida, falla la consulta o falla la entrega al broker. Publica únicamente códigos fijos de causa.

```java
return repository.countByStatusIn(PENDING)
    .doOnNext(count -> {
      pending.set(count);
      refreshedAt = Instant.now();
    })
    .doOnError(error -> problem = "BACKLOG_QUERY_FAILED")
    .then();
```

En cocina, `tacocloud.kitchen.processing` mide sólo eventos procesados por primera vez. El contador existente `tacocloud.kitchen.event.delivery` conserva el resultado `dlq` cuando RabbitMQ confirmó la ruta. `TacoCountInfoContributor` ahora devuelve una muestra actualizada por una tarea programada, sin `block()` en `contribute`.

Los contadores tienen unidad de eventos, los timers se consultan en segundos y `tacocloud.outbox.pending` representa documentos. Mongo participa en readiness mediante su indicador de Spring Boot. Liveness y readiness están habilitados. En la API, métricas e información exigen ADMIN y los detalles de health sólo se muestran a ese rol. En cocina, Actuator escucha por defecto sólo en `127.0.0.1:8082` y oculta los detalles de health.

## Flujo

Crear o cancelar orden -> confirmar efecto -> actualizar counter y timer. Sondeo del outbox -> contar pendientes en Mongo -> actualizar gauge y health. Cocina recibe evento -> procesa una vez -> registra tiempo o envía a retry/DLQ. Actuator lee muestras y aplica la política de acceso.

## Archivos principales

- `OrderMetrics.java`, `OrderService.java` y `OrderWorkflowService.java`: miden creación, fallo, cupón, stock y cancelación en los casos de uso.
- `OutboxHealthIndicator.java`, `OutboxRepository.java`, `OutboxPolling.java` y `OutboxPublisher.java`: obtienen el backlog y reflejan errores de consulta o entrega.
- `OrderListener.java`: registra el tiempo de procesamiento real en cocina.
- `TacoCountInfoContributor.java`, `SecurityConfig.java` y los archivos `application.yml`: lectura no bloqueante de info, probes y acceso operativo.
