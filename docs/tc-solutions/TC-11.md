# TC-11 — Autorización deny-by-default y roles útiles

## Objetivo

Sustituir la política global permisiva por reglas explícitas para `USER`, `ADMIN` y `KITCHEN`. El catálogo debe conservar lectura pública, mientras las órdenes, las mutaciones de catálogo, cocina, Data REST y Actuator deben aplicar autenticación, rol y propiedad del recurso. Cualquier ruta no declarada debe quedar cerrada automáticamente.

## Problema encontrado

`SecurityConfig` terminaba con `/** permitAll`. Esa regla permitía que usuarios anónimos crearan órdenes y que cualquier usuario modificara ingredientes, accediera a rutas de cocina o consultara infraestructura. CSRF estaba desactivado para toda la API. Además, `User.getAuthorities()` siempre devolvía `ROLE_USER`, por lo que los roles administrativos no podían persistirse.

La seguridad de órdenes era parcial. PUT, PATCH y DELETE comprobaban propietario, pero GET devolvía todas las órdenes. POST creaba una orden sin asociarla al usuario autenticado y el flujo de correo confiaba en el email recibido. Estas reglas estaban repartidas dentro del controlador.

## Solución implementada

`SecurityConfig` declara las rutas desde la más específica hasta la más general. GET de tacos e ingredientes es público. Sus mutaciones requieren `ADMIN`. Cocina requiere `KITCHEN`. Las órdenes requieren `USER` o `ADMIN`, con POST reservado a `USER`. Data REST y los endpoints de Actuator distintos de health requieren `ADMIN`. La cadena termina en `anyRequest().denyAll()`. Las peticiones anónimas a API e infraestructura reciben `401`. Un usuario autenticado sin permiso recibe `403`.

CSRF permanece activo para escrituras y CORS se centraliza en `ApiCorsConfiguration`, que acepta sólo los orígenes configurados. Actuator expone únicamente health e info y muestra detalles de salud sólo a ADMIN.

`User` persiste un conjunto de roles y los normaliza a authorities `ROLE_*`. El constructor utilizado por registro conserva `USER` como único rol inicial y los documentos antiguos sin roles adoptan ese mismo valor.

Se introdujo `OrderService` como punto único para autorización de órdenes. `Flux.defer` decide en la suscripción si consulta todas las órdenes para ADMIN o usa la query derivada por username para USER. La creación busca al usuario mediante `Authentication.getName()` y reemplaza cualquier propietario aportado por el cliente. El flujo de correo valida que el usuario convertido coincida con la identidad autenticada antes de guardar o publicar. PUT, PATCH y DELETE reutilizan allí las reglas de propietario, estado y errores ya existentes.

La solución fue:

### Matriz de rutas cerrada por defecto

```java
http
  .authorizeRequests()
    .antMatchers(HttpMethod.OPTIONS, "/**").permitAll()
    .antMatchers("/", "/login", "/register", "/images/**",
        "/styles.css", "/favicon.ico").permitAll()
    .antMatchers(HttpMethod.GET,
        "/api/tacos/**", "/api/ingredients/**").permitAll()
    .antMatchers("/api/ingredients/**", "/api/tacos/**").hasRole("ADMIN")
    .antMatchers("/api/kitchen/**").hasRole("KITCHEN")
    .antMatchers(HttpMethod.POST, "/api/orders/**").hasRole("USER")
    .antMatchers("/api/orders/**").hasAnyRole("USER", "ADMIN")
    .antMatchers("/api/favorites/**", "/api/ratings/**").hasRole("USER")
    .antMatchers("/data-api/**").hasRole("ADMIN")
    .antMatchers("/actuator/health").permitAll()
    .antMatchers("/actuator/**").hasRole("ADMIN")
    .anyRequest().denyAll();
```

El orden de las reglas es importante. Primero se permiten lecturas públicas concretas y después se protegen las rutas más amplias. `shouldDenyUnlistedRouteByDefault` comprueba el cierre final. Las pruebas de `SecurityAuthorizationTest.java` verifican además las combinaciones de usuario anónimo, USER, ADMIN y KITCHEN.

### Roles persistidos y normalizados

`User` dejó de devolver siempre `ROLE_USER`. Los roles se guardan con el usuario y se convierten en authorities de Spring Security:

```java
private final Set<String> roles;

public User(String username, String password, String fullname,
    String street, String city, String state, String zip,
    String phoneNumber, String email) {
  this(username, password, fullname, street, city, state, zip,
      phoneNumber, email, Collections.singleton("USER"));
}

@Override
public Collection<? extends GrantedAuthority> getAuthorities() {
  return roles.stream()
      .map(role -> role.toUpperCase(Locale.ROOT))
      .map(role -> role.startsWith("ROLE_")
          ? role : "ROLE_" + role)
      .map(SimpleGrantedAuthority::new)
      .collect(Collectors.toList());
}
```

El constructor usado por el registro conserva el mínimo privilegio. `shouldGiveNewRegistrationOnlyUserRole` comprueba ese valor. `shouldExposePersistedAdminAndKitchenRoles` prueba roles guardados y su normalización.

### Listado según la identidad autenticada

`OrderService` decide qué consulta ejecutar cuando existe una suscripción:

```java
public Flux<TacoOrder> findVisibleOrders(
    Authentication authentication) {
  return Flux.defer(() -> {
    if (!isAuthenticated(authentication)) {
      return Flux.error(
          new ResponseStatusException(HttpStatus.UNAUTHORIZED));
    }
    if (hasRole(authentication, "ROLE_ADMIN")) {
      return repo.findAll();
    }
    if (hasRole(authentication, "ROLE_USER")) {
      return repo.findByUserUsernameOrderByPlacedAtDesc(
          authentication.getName());
    }
    return Flux.error(
        new ResponseStatusException(HttpStatus.FORBIDDEN));
  });
}
```

`shouldListOnlyAuthenticatedUsersOrders` comprueba la consulta derivada por username. `shouldAllowAdminToAuditAllOrders` verifica que ADMIN usa `findAll`.

### Propietario impuesto por el servidor

La creación ignora cualquier propietario recibido y busca al usuario autenticado:

```java
public Mono<TacoOrder> createOrder(
    TacoOrder order, Authentication authentication) {
  return currentUser(authentication)
      .flatMap(user -> {
        order.setUser(user);
        return Mono.fromRunnable(
            () -> orderMessages.sendOrder(order))
            .then(Mono.defer(() -> repo.save(order)));
      });
}
```

`shouldReplaceClientOwnerWithAuthenticatedUserBeforeCreate` captura la orden y confirma que el usuario persistido proviene de `Authentication.getName()`.

### CORS limitado por configuración

Los controladores dejaron de declarar orígenes fijos. La configuración aplica sólo a la API:

```java
registry.addMapping("/api/**")
    .allowedOrigins(allowedOrigins)
    .allowedMethods(
        "GET", "HEAD", "POST", "PUT", "PATCH", "DELETE", "OPTIONS")
    .allowCredentials(true);
```

`shouldAllowConfiguredOriginForApiPreflight` y `shouldRejectUnconfiguredOriginForApiPreflight` comprueban que no se refleje cualquier origen recibido.

## Flujo

Petición -> filtro de seguridad -> autenticación -> rol y CSRF -> controlador -> `OrderService` -> comprobación de ownership -> repositorio/mensajería -> DTO de respuesta. Si una regla falla, las etapas posteriores no se ejecutan.

## Archivos principales

- `SecurityConfig.java` y `User.java`: matriz deny-by-default y roles persistidos.
- `OrderService.java`, `OrderApiController.java` y `OrderRepository.java`: autorización y consultas por propietario.
- `ApiCorsConfiguration.java` y `application.yml`: CORS y exposición limitada de Actuator.
- `SecurityAuthorizationTest.java`, `UserRolesTest.java`, `OrderAuthorizationServiceTest.java` y `ApiCorsConfigurationTest.java`: cobertura de filtros, roles, ownership y orígenes.

## Cambios realizados por otros TC

TC-12 protegió `/api/payment-methods/**` para `ROLE_USER` y CSRF. La creación de órdenes también comprueba que el método de pago pertenece al usuario autenticado, sin alterar la política de roles de TC-11.

TC-13 añadió las escrituras `/api/admin/ingredients/**`. Sólo `ROLE_ADMIN` puede actualizar el catálogo o ajustar stock y las dos operaciones requieren CSRF. La lectura pública de ingredientes se mantiene.

TC-14 mantiene la creación de órdenes bajo `ROLE_USER` y CSRF. La identidad autenticada y el método de pago se resuelven antes de aceptar la compra. El cliente no puede usar el nuevo contrato para modificar el propietario ni los importes.

TC-15 añadió `POST /api/orders/quote` bajo la ruta de órdenes ya protegida. Requiere `ROLE_USER` y CSRF como las demás escrituras. No existe una ruta de lectura que enumere los códigos configurados.

TC-22 añadió `PUT /api/tacos/{id}/rating` para `ROLE_USER` con CSRF. La lectura de `/api/tacos/top` es pública. Las demás escrituras del catálogo conservan su autorización administrativa y la denegación por defecto sigue activa.
