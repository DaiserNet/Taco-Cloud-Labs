# TC-35 — Versionar la API y publicar contrato OpenAPI

## Objetivo

Publicar un contrato HTTP verificable para que los clientes conozcan rutas, datos, respuestas, errores y permisos sin leer los controladores. Introducir `/api/v1` sin interrumpir a los clientes que todavía usan `/api`.

## Problema encontrado

La API tenía contratos de entrada y respuesta separados de las entidades, pero sus rutas no estaban versionadas ni reunidas en una especificación. La UI utilizaba `/api`. Un cambio de campo o estado podía pasar desapercibido para quien consumía la API. Tampoco había una señal HTTP que indicara la ruta sucesora del alias antiguo.

## Solución implementada

La solución fue publicar [openapi.yaml](../../tacocloud/tacocloud-api/src/main/resources/static/openapi.yaml) como recurso estático y añadir `/api/v1` a los mapeos existentes. Cada versión llega al mismo método y conserva la lógica funcional. Las reglas de seguridad tienen el mismo alcance en ambas rutas. El contrato declara los endpoints implementados de ingredientes, tacos, órdenes, favoritos, valoraciones, pagos, cocina y administración. Usa esquemas de petición y respuesta basados en los DTO, no en documentos MongoDB. Incluye estados HTTP, `ApiProblem`, autenticación, roles, CSRF, `Idempotency-Key` y `X-Correlation-Id` donde corresponden.

```java
@RequestMapping(path = {"/api/ingredients", "/api/v1/ingredients"})
```

`LegacyApiDeprecationFilter` marca sólo las peticiones del alias `/api`. Su cabecera `Link` señala la ruta equivalente en v1. La UI actual puede seguir usando ese alias durante la transición. El contrato explica esta compatibilidad y permite migrar clientes por separado. Antes de retirar el alias habrá que comprobar los consumidores y anunciar una fecha.

```java
if (path.startsWith("/api/") && !path.startsWith("/api/v1/")) {
  response.setHeader("Deprecation", "true");
  response.setHeader("Link", "<" + request.getContextPath()
      + "/api/v1" + path.substring(4)
      + ">; rel=\"successor-version\"");
}
```

La creación de ingredientes construye `Location` según la versión solicitada. Así una petición v1 no remite al cliente al alias antiguo.

En la prueba de integración se comprobó también que la página inicial debía entregar la cookie `XSRF-TOKEN` para que la UI pudiera escribir con CSRF. `SecurityConfig` la emite al servir `/` y mantiene la verificación de CSRF en las operaciones protegidas.

## Flujo

Cliente consulta el contrato -> elige `/api/v1` -> Spring aplica los mismos permisos y CSRF -> el controlador procesa la petición -> responde con el DTO y estado documentados. Cliente antiguo usa `/api` -> recibe la misma operación más `Deprecation` y `Link`.

## Archivos principales

- `openapi.yaml`: contrato versionado, ejemplos, cabeceras, errores y esquemas públicos.
- Controladores de `tacos.web.api`, anuncios y cocina: exponen los mapeos paralelos sin duplicar la lógica.
- `SecurityConfig.java`: replica las autorizaciones para v1, permite consultar el YAML y entrega la cookie CSRF de la página inicial. Conserva `denyAll` al final.
- `LegacyApiDeprecationFilter.java`: anuncia la ruta sucesora del alias.
- `IngredientController.java`: genera una cabecera `Location` coherente con la ruta usada.
- `tacocloud-api/pom.xml`: incorpora el validador OpenAPI sólo para pruebas.
