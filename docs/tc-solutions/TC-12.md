# TC-12 — Tokenizar pago y eliminar PAN/CVV del dominio

## Objetivo

Evitar que el número completo de tarjeta (PAN) y el CVV formen parte del dominio, la persistencia, las respuestas HTTP, los mensajes de cocina o los registros. La aplicación debe recibirlos sólo durante la tokenización, guardar una referencia opaca al método de pago y conservar únicamente los datos seguros necesarios para identificarlo: marca y últimos cuatro dígitos.

## Problema encontrado

`TacoOrder` y `PaymentMethod` contenían número, expiración y CVV. La creación de órdenes aceptaba esos valores directamente y `OrderResponse` calculaba `paymentLast4` desde el PAN almacenado. Como las órdenes también se publican al sistema de cocina, serializar la entidad podía extender los datos sensibles fuera del límite de pago. Los formularios web enviaban la tarjeta junto con la orden y los documentos antiguos podían conservar esos campos.

## Solución implementada

Se creó `POST /api/payment-methods/tokenize`. `PaymentTokenizeRequest` recibe PAN, expiración y CVV como datos transitorios validados y los transforma en `PaymentTokenizationCommand`. `PaymentGateway` define el límite con el proveedor. Su implementación local genera un token opaco y obtiene marca, últimos cuatro y expiración. `PaymentMethodService` resuelve reactivamente al usuario autenticado, compone la llamada al gateway con `flatMap` y persiste un `PaymentMethod` seguro. La respuesta sólo devuelve ID, marca y últimos cuatro.

`OrderCreateRequest` acepta ahora `paymentMethodId`. Antes de crear la orden, `OrderService` consulta el método mediante ID y username, con lo que comprueba propiedad sin cargar datos de otro usuario. Después copia a `TacoOrder` únicamente ID, marca y últimos cuatro. El token permanece en `PaymentMethod`, marcado con `@JsonIgnore` y excluido de `toString`. PAN y CVV ya no existen en las entidades. Los campos de referencia del pago en `TacoOrder` también usan `@JsonIgnore`, por lo que el mensaje de cocina no contiene información de pago.

El cliente Angular encadena tokenización y creación con `switchMap`: la segunda petición no comienza hasta recibir el ID. Para datos históricos se añadieron una migración reactiva explícita y un script MongoDB que eliminan los antiguos campos sensibles sin imprimir sus valores. La migración no se ejecuta automáticamente.

La solución fue:

```java
public Mono<PaymentMethod> tokenize(
    PaymentTokenizationCommand command,
    Authentication authentication) {
  return currentUser(authentication)
      .flatMap(user -> paymentGateway.tokenize(command)
          .map(payment -> new PaymentMethod(
              user,
              payment.getToken(),
              payment.getBrand(),
              payment.getLast4(),
              payment.getExpiration())))
      .flatMap(paymentMethodRepo::save);
}

public Mono<PaymentMethod> findOwned(
    String paymentMethodId, Authentication authentication) {
  return Mono.defer(() -> paymentMethodRepo
      .findByIdAndUserUsername(
          paymentMethodId, authentication.getName())
      .switchIfEmpty(Mono.error(
          new ResponseStatusException(HttpStatus.NOT_FOUND))));
}
```

## Flujo

Formulario -> tokenización -> gateway -> guardar método seguro -> devolver ID -> crear orden con ID -> comprobar usuario y propiedad -> copiar resumen seguro -> publicar y guardar orden -> responder con marca y últimos cuatro.

## Archivos principales

- `PaymentGateway.java`, `FakePaymentGateway.java` y `PaymentMethodService.java`: tokenización y persistencia segura.
- `PaymentTokenizeRequest.java`, `PaymentMethodResponse.java` y `PaymentMethodController.java`: contrato HTTP transitorio y respuesta limitada.
- `PaymentMethod.java`, `TacoOrder.java` y `OrderService.java`: modelo sin PAN/CVV y verificación de propiedad.
- `OrderCreateRequest.java`, `OrderResponse.java` y `OrderMapper.java`: contrato de órdenes basado en referencia segura.
- `LegacyPaymentDataMigration.java` y `TC12_remove_legacy_payment_fields.js`: limpieza explícita de documentos históricos.
- `cart.component.ts`: composición de las dos peticiones desde la interfaz.

## Pruebas

La fase roja ejecutó cuatro pruebas de contrato y las cuatro fallaron al detectar campos sensibles. Después se añadieron pruebas del gateway, servicio, controlador, serialización del mensaje, seguridad, migración y ausencia de PAN/CVV por reflexión y JSON. También se comprobó que un método ajeno no puede usarse.

La regresión final ejecutó 91 pruebas: 91 aprobadas, 0 fallidas, 0 errores y 0 omitidas. La construcción Angular y el empaquetado Maven finalizaron correctamente.
