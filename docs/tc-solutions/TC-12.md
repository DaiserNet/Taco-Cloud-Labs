# TC-12 — Tokenizar pago y eliminar PAN/CVV del dominio

## Objetivo

Evitar que el número completo de tarjeta (PAN) y el CVV formen parte del dominio, la persistencia, las respuestas HTTP, los mensajes de cocina o los registros. La aplicación debe recibirlos sólo durante la tokenización, guardar una referencia opaca al método de pago y conservar únicamente los datos seguros necesarios para identificarlo: marca y últimos cuatro dígitos.

## Problema encontrado

`TacoOrder` y `PaymentMethod` contenían número, expiración y CVV. La creación de órdenes aceptaba esos valores directamente y `OrderResponse` calculaba `paymentLast4` desde el PAN almacenado. Como las órdenes también se publican al sistema de cocina, serializar la entidad podía extender los datos sensibles fuera del límite de pago. Los formularios web enviaban la tarjeta junto con la orden y los documentos antiguos podían conservar esos campos.

## Solución implementada

Se creó `POST /api/payment-methods/tokenize`. `PaymentTokenizeRequest` recibe PAN, expiración y CVV como datos transitorios validados y los transforma en `PaymentTokenizationCommand`. `PaymentGateway` define el límite con el proveedor. Su implementación local genera un token opaco y obtiene marca, últimos cuatro y expiración. `PaymentMethodService` resuelve reactivamente al usuario autenticado, compone la llamada al gateway con `flatMap` y persiste un `PaymentMethod` seguro. La respuesta sólo devuelve ID, marca y últimos cuatro.

`OrderCreateRequest` acepta ahora `paymentMethodId`. Antes de crear la orden, `OrderService` consulta el método mediante ID y username, con lo que comprueba propiedad sin cargar datos de otro usuario. Después copia a `TacoOrder` únicamente ID, marca y últimos cuatro. El token permanece en `PaymentMethod`, marcado con `@JsonIgnore` y excluido de `toString`. PAN y CVV ya no existen en las entidades. Los campos de referencia del pago en `TacoOrder` también usan `@JsonIgnore`, por lo que el mensaje de cocina no contiene información de pago.

El cliente Angular encadena tokenización y creación con `switchMap`: la segunda petición no comienza hasta recibir el ID. Para datos históricos se añadieron una migración reactiva explícita y un script MongoDB que eliminan los antiguos campos sensibles sin imprimir sus valores. La migración no se ejecuta automáticamente.

La solución fue:

### Tokenización y persistencia segura

```java
public Mono<PaymentMethod> tokenize(
    PaymentTokenizationCommand command,
    Authentication authentication) {
  return currentUser(authentication)
      .flatMap(user -> paymentGateway.tokenize(command)
          .map(payment -> new PaymentMethod(
              user,
              payment.getToken(),
              payment.getBrand(),
              payment.getLast4(),
              payment.getExpiration())))
      .flatMap(paymentMethodRepo::save);
}

public Mono<PaymentMethod> findOwned(
    String paymentMethodId, Authentication authentication) {
  return Mono.defer(() -> paymentMethodRepo
      .findByIdAndUserUsername(
          paymentMethodId, authentication.getName())
      .switchIfEmpty(Mono.error(
          new ResponseStatusException(HttpStatus.NOT_FOUND))));
}
```

`currentUser` valida autenticación y rol antes de consultar al gateway. El primer `flatMap` conserva esa dependencia. El segundo encadena el `save` y garantiza que el método no se emita antes de persistirse. `shouldSubscribeToGatewayAndPersistOnlyTokenizedDataForCurrentUser` comprueba la suscripción y captura el documento guardado.

### Modelo sin PAN ni CVV

`PaymentMethod` guarda únicamente la relación con el usuario, el token opaco y el resumen seguro:

```java
@Document
@Data
public class PaymentMethod {
  @Id
  private String id;
  private final User user;

  @JsonIgnore
  @ToString.Exclude
  private final String paymentToken;

  private final String brand;
  private final String last4;
  private final String expiration;
}
```

`TacoOrder` guarda sólo la referencia y el resumen que necesita la aplicación:

```java
@JsonIgnore
private String paymentMethodId;

@JsonIgnore
private String paymentBrand;

@JsonIgnore
private String paymentLast4;
```

`shouldRemoveRawCardFieldsFromOrderDomain` y `shouldModelOnlyTokenizedPaymentData` revisan los campos por reflexión. `shouldSerializeKitchenOrderWithoutAnyPaymentInformation` serializa la orden y confirma que ni siquiera el resumen oculto llega al mensaje de cocina.

### Entrada transitoria de tokenización

PAN y CVV sólo existen en el DTO que cruza el límite de pago:

```java
@NotBlank(message = "must not be blank")
@Pattern(regexp = "[0-9]{12,19}",
    message = "must contain 12 to 19 digits")
@ToString.Exclude
private String pan;

@NotBlank(message = "must not be blank")
@Pattern(regexp = "[0-9]{3,4}",
    message = "must contain 3 or 4 digits")
@ToString.Exclude
private String cvv;
```

El DTO no se persiste. `PaymentMethodController` lo transforma de inmediato en un comando y devuelve una respuesta sin token:

```java
PaymentTokenizationCommand command = new PaymentTokenizationCommand(
    request.getPan(), request.getExpiration(), request.getCvv());
return paymentMethodService.tokenize(command, authentication)
    .map(payment -> new PaymentMethodResponse(
        payment.getId(), payment.getBrand(), payment.getLast4()));
```

`shouldReturnCreatedWithSafeSummaryOnly` comprueba el `201` y confirma que la respuesta sólo contiene ID, marca y últimos cuatro.

### Gateway reactivo

La implementación local genera el token al suscribirse:

```java
public Mono<TokenizedPayment> tokenize(
    PaymentTokenizationCommand payment) {
  return Mono.fromSupplier(() -> new TokenizedPayment(
      "tok_fake_" + UUID.randomUUID().toString().replace("-", ""),
      brandFor(payment.getPan()),
      payment.getPan().substring(payment.getPan().length() - 4),
      payment.getExpiration()));
}
```

`Mono.fromSupplier` evita crear el token antes de la suscripción. `shouldCreateOpaqueTokenAndKeepOnlySafeCardSummary` comprueba el prefijo opaco, la marca y los últimos cuatro.

### Composición del cliente

Angular tokeniza primero y usa `switchMap` para crear la orden después de recibir el identificador:

```typescript
this.httpClient.post<any>(
    'http://localhost:8080/api/payment-methods/tokenize',
    this.payment, {
      headers: new HttpHeaders()
          .set('Content-type', 'application/json')
          .set('Accept', 'application/json')
    }).switchMap(paymentMethod => {
      this.model.paymentMethodId = paymentMethod.paymentMethodId;
      return this.httpClient.post(
          'http://localhost:8080/api/orders', this.model, {
            headers: new HttpHeaders()
                .set('Content-type', 'application/json')
                .set('Accept', 'application/json')
          });
    }).subscribe(r => this.cart.emptyCart());
```

La segunda petición no incluye PAN ni CVV. Sólo lleva `paymentMethodId` junto con los datos de la orden.

### Limpieza de documentos anteriores

La migración usa `$unset` sin leer ni imprimir valores sensibles:

```java
Update removeRawCardData = new Update()
    .unset("ccNumber")
    .unset("ccExpiration")
    .unset("ccCVV");

return Mono.zip(
    mongo.updateMulti(
        legacyFieldsQuery(), removeRawCardData, ORDER_COLLECTION),
    mongo.updateMulti(
        legacyFieldsQuery(), removeRawCardData, PAYMENT_METHOD_COLLECTION));
```

`shouldRemoveSensitiveFieldsWithoutDeletingSafeData` prepara documentos históricos, ejecuta la migración y comprueba que sólo desaparecen los campos de tarjeta.

## Flujo

Formulario -> tokenización -> gateway -> guardar método seguro -> devolver ID -> crear orden con ID -> comprobar usuario y propiedad -> copiar resumen seguro -> publicar y guardar orden -> responder con marca y últimos cuatro.

## Archivos principales

- `PaymentGateway.java`, `FakePaymentGateway.java` y `PaymentMethodService.java`: tokenización y persistencia segura.
- `PaymentTokenizeRequest.java`, `PaymentMethodResponse.java` y `PaymentMethodController.java`: contrato HTTP transitorio y respuesta limitada.
- `PaymentMethod.java`, `TacoOrder.java` y `OrderService.java`: modelo sin PAN/CVV y verificación de propiedad.
- `OrderCreateRequest.java`, `OrderResponse.java` y `OrderMapper.java`: contrato de órdenes basado en referencia segura.
- `LegacyPaymentDataMigration.java` y `TC12_remove_legacy_payment_fields.js`: limpieza explícita de documentos históricos.
- `cart.component.ts`: composición de las dos peticiones desde la interfaz.

## Cambios realizados por otros TC

TC-14 usa el método tokenizado antes de calcular la orden. La petición sigue enviando únicamente `paymentMethodId`. Los mensajes de cocina cuentan las cantidades de las líneas y continúan sin exponer identificadores ni resúmenes de pago.

TC-27 sustituyó la serialización de la entidad por un evento con un snapshot de cocina. La separación de pago establecida en TC-12 se mantiene y ahora el contrato tampoco transporta el objeto `User`.
