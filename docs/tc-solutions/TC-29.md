# TC-29 — Outbox transaccional para no perder órdenes

## Objetivo

Guardar cada orden confirmada junto con un evento pendiente para cocina. Ambos documentos deben confirmarse en una misma transacción de MongoDB. Un proceso independiente debe enviar los eventos, reintentar los fallos y recuperar los pendientes tras un reinicio.

## Problema encontrado

`OrderService` guardaba la orden y después llamaba al broker. Si el proceso terminaba entre ambas operaciones, la orden quedaba confirmada sin aviso para cocina. Kafka además devolvía una confirmación asíncrona que el adaptador no esperaba. Un fallo posterior al inicio del envío podía pasar inadvertido.

## Solución implementada

La solución fue crear `OrderOutboxService`. Tras reservar inventario, guarda la orden, acepta la reserva y almacena un `OutboxEvent` con el JSON seguro de `OrderEvent` v1. `TransactionalOperator` hace que esas escrituras Mongo terminen juntas. Si la cadena falla, Mongo revierte la transacción y `OrderService` libera la reserva previa.

```java
return Mono.defer(() -> orders.save(order))
    .flatMap(saved -> inventory.accept(reservation.getId(), saved.getId())
        .then(Mono.defer(() -> {
          OrderEvent event = OrderEventFactory.created(saved);
          return outbox.save(new OutboxEvent(event.getEventId(),
              serialize(event), event.getVersion(), Instant.now()))
              .thenReturn(saved);
        })))
    .as(transaction::transactional);
```

El outbox conserva `eventId`, versión, payload, estado, intentos y tiempos de creación, actualización, próximo intento, claim y publicación. `OutboxPublisher` reclama cada registro con `findAndModify`. Esa operación atómica cambia `NEW` o `FAILED` a `PUBLISHING` y asigna un `claimId` y un vencimiento. También recupera claims vencidos. Sólo el propietario del `claimId` puede marcar el resultado.

```java
return mongo.findAndModify(query, update,
    FindAndModifyOptions.options().returnNew(true), OutboxEvent.class);
```

Un envío correcto termina en `PUBLISHED`. Un fallo deja `FAILED`, incrementa intentos y programa un reintento con backoff exponencial hasta el máximo configurado. Al agotar intentos, el registro permanece visible con el último error. El sondeo programado suscribe la cadena únicamente en el límite de infraestructura y evita superponer dos lotes locales. El puerto de mensajería añade `publish`, que devuelve `Mono<Void>`. En Kafka ese `Mono` espera la respuesta asíncrona del broker.

MongoDB debe ser un replica set, incluso de un solo nodo. En producción `TACOCLOUD_MONGODB_URI` debe incluir su nombre de replica set. Las colecciones e índices deben existir antes de la primera transacción. Los valores de lote, lease, backoff, máximo de intentos y frecuencia de sondeo se configuran por entorno.

## Flujo

Crear orden -> reservar inventario -> transacción: guardar orden, aceptar reserva y guardar outbox NEW -> responder al cliente -> reclamar evento -> enviar y esperar confirmación -> marcar PUBLISHED o FAILED -> reintentar cuando corresponda.

## Archivos principales

- `OrderService.java` y `OrderOutboxService.java`: separan creación del envío y delimitan la transacción.
- `OutboxEvent.java`, `OutboxRepository.java`, `OutboxPublisher.java` y `OutboxPolling.java`: almacenan y procesan los eventos pendientes.
- `OutboxTransactionConfig.java`: registra el gestor de transacciones reactivas.
- `OrderMessagingService.java` y `KafkaOrderMessagingService.java`: permiten observar la confirmación real del envío.
- `application.yml`: expone los parámetros operativos del outbox y la URI de replica set para producción.
