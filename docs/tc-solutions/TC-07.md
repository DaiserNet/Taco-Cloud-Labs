# TC-07 — Una sola suscripción para guardar y publicar

## Objetivo

Componer el procesamiento de `POST /api/orders/fromEmail` para convertir la entrada de TC-06, guardar la orden y publicarla hacia cocina con una sola suscripción reactiva. La respuesta `201 Created` sólo debe producirse después de terminar la secuencia, y un error debe impedir la ejecución de las etapas que todavía no hayan comenzado.

## Problema encontrado

El controlador guardaba el `Mono<TacoOrder>` de conversión en una variable, llamaba manualmente a `subscribe(orderMessages::sendOrder)` y después reutilizaba el mismo publisher para guardar. Como el flujo de TC-06 es frío, las dos suscripciones repetían la conversión y, con ella, las consultas de usuario, pago e ingredientes. La publicación también podía ocurrir antes de conocer si MongoDB aceptaba la orden. Además, el error de esa suscripción lateral quedaba fuera de la respuesta HTTP.

El parámetro `@RequestBody Mono<EmailOrder>` tampoco era apropiado para el runtime MVC efectivo del proyecto ya que el Jackson debe deserializar el JSON a `EmailOrder`, mientras que Reactor debe comenzar dentro de la lógica del endpoint.

## Solución implementada

`postOrderFromEmail` recibe ahora `@Valid @RequestBody EmailOrder` y adapta el objeto al contrato de TC-06 con `Mono.just(emailOrder)`. El resultado de `convertEmailOrderToDomainOrder` se encadena con `flatMap(repo::save)`. Se eligió la política guardar y después publicar donde si la conversión o el guardado fallan, mensajería no recibe ninguna orden.

La llamada existente `orderMessages.sendOrder` devuelve `void`. Para incorporarla se envuelve con `Mono.fromRunnable`. Este publisher ejecuta el envío únicamente cuando Spring se suscribe y convierte una excepción síncrona del adaptador en una señal `onError`. `thenReturn(savedOrder)` espera a que termine el envío y vuelve a emitir exactamente la entidad devuelta por `save`, incluyendo cualquier ID asignado por persistencia.

La solución fue:

### Una única cadena de efectos

```java
@PostMapping(path = "fromEmail", consumes = "application/json")
@ResponseStatus(HttpStatus.CREATED)
public Mono<TacoOrder> postOrderFromEmail(
    @Valid @RequestBody EmailOrder emailOrder) {
  return emailOrderService
      .convertEmailOrderToDomainOrder(Mono.just(emailOrder))
      .flatMap(repo::save)
      .flatMap(savedOrder -> Mono.fromRunnable(
          () -> orderMessages.sendOrder(savedOrder))
          .thenReturn(savedOrder));
}
```

`flatMap(repo::save)` espera la entidad persistida. El segundo `flatMap` crea el publisher que ejecuta mensajería y `thenReturn` vuelve a emitir la orden guardada. De esta forma la respuesta y el mensaje utilizan el ID asignado por el repositorio.

### Comprobación de una sola suscripción

La prueba envuelve la conversión fría con `PublisherProbe` y comprueba el orden mediante Mockito:

```java
PublisherProbe<TacoOrder> conversion = PublisherProbe.of(
    Mono.just(converted));
when(emailOrderService.convertEmailOrderToDomainOrder(any()))
    .thenReturn(conversion.mono());
when(repo.save(converted)).thenReturn(Mono.just(saved));

StepVerifier.create(controller.postOrderFromEmail(new EmailOrder()))
    .assertNext(order -> assertEquals("ORDER-ID", order.getId()))
    .verifyComplete();

assertEquals(1, conversion.subscribeCount());
InOrder interactions = inOrder(repo, messaging);
interactions.verify(repo).save(converted);
interactions.verify(messaging).sendOrder(saved);
```

`shouldSubscribeToColdConversionOnceAndPublishSavedOrderOnce` demuestra que la conversión no se repite y que la publicación ocurre después del guardado.

### Persistencia pendiente

Otra prueba mantiene `save` sin completar:

```java
TestPublisher<TacoOrder> save = TestPublisher.createCold();
when(repo.save(converted)).thenReturn(save.mono());

StepVerifier.create(controller.postOrderFromEmail(new EmailOrder()))
    .expectSubscription()
    .then(() -> verifyNoInteractions(messaging))
    .expectNoEvent(Duration.ofMillis(20))
    .then(() -> save.emit(saved))
    .assertNext(order -> assertEquals("ORDER-ID", order.getId()))
    .verifyComplete();
```

`shouldWaitForSaveBeforePublishing` relaciona directamente la finalización del repositorio con el inicio de mensajería.

## Flujo

JSON de correo -> deserializar a `EmailOrder` -> convertir con TC-06 -> guardar `TacoOrder` -> publicar la orden guardada -> volver a emitirla -> responder `201`.

Si la conversión falla -> no guardar ni publicar. Si el guardado falla -> no publicar. Si el envío falla -> propagar el error sin completar la respuesta como exitosa.

## Archivos principales

- `OrderApiController.java`: elimina la suscripción manual y contiene la única cadena conversión -> guardado -> publicación.
- `OrderFromEmailControllerTest.java`: controla suscripciones, orden de efectos, errores y binding HTTP.
- `EmailOrderService.java`: se reutiliza sin cambios adicionales. Continúa siendo responsable únicamente de la conversión implementada en TC-06.

## Pruebas

Las pruebas comprueban que un publisher frío de conversión recibe una sola suscripción, que `save` y `sendOrder` se invocan una vez y en ese orden, y que se publica la entidad persistida. También cubren error de conversión, error de guardado, espera por un `TestPublisher` de persistencia y propagación de una excepción de mensajería. La comprobación con `MockMvc` verifica que el JSON se enlaza a `EmailOrder`, que el procesamiento es asíncrono y que el cuerpo HTTP contiene el ID asignado durante el guardado.

| Concepto comprobado | Test | Archivo |
|---|---|---|
| Una suscripción y una publicación de la orden guardada | `shouldSubscribeToColdConversionOnceAndPublishSavedOrderOnce` | `OrderFromEmailControllerTest.java` |
| Error de conversión sin efectos posteriores | `shouldNotSaveOrPublishWhenConversionFails` | `OrderFromEmailControllerTest.java` |
| Error de persistencia sin publicación | `shouldNotPublishWhenSaveFails` | `OrderFromEmailControllerTest.java` |
| Orden guardar antes de publicar | `shouldWaitForSaveBeforePublishing` | `OrderFromEmailControllerTest.java` |
| Propagación del fallo de mensajería | `shouldPropagatePublishFailureInsteadOfCompletingSuccessfully` | `OrderFromEmailControllerTest.java` |
| Respuesta HTTP con la entidad persistida | `shouldReturnCreatedWithThePersistedOrder` | `OrderFromEmailControllerTest.java` |

## Cambios realizados por otros TC

TC-08 añadió una proyección final a `OrderResponse` después de guardar y publicar. La secuencia de TC-07 continúa siendo conversión -> persistencia -> publicación. El mapper sólo transforma la entidad ya procesada antes de serializar la respuesta HTTP.

TC-09 valida la orden de correo antes de iniciar esa secuencia y representa sus errores mediante Problem Details.

TC-11 trasladó la orquestación a `OrderService` y añadió la comprobación de propietario antes del guardado. Tras autorizar, se conserva exactamente la secuencia conversión -> persistencia -> publicación y la única suscripción de TC-07.

TC-12 impidió que el mensaje de cocina serialice datos de pago. El flujo conversión -> persistencia -> publicación no cambió y la cocina sigue recibiendo la orden necesaria.

TC-14 añadió el cálculo reactivo antes de persistir. En el flujo de correo la secuencia es conversión -> autorización -> cálculo -> persistencia -> publicación. La única suscripción y el orden de los efectos de TC-07 permanecen iguales.
