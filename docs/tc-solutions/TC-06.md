# TC-06 — Convertir órdenes de correo sin carreras ni nulls sorpresa

## Objetivo

Convertir `Mono<EmailOrder>` en `Mono<TacoOrder>` mediante una sola composición reactiva. La orden sólo puede emitirse después de resolver usuario, forma de pago, todos los tacos y todos sus ingredientes, conservando el orden de entrada y comunicando explícitamente las referencias ausentes.

## Problema encontrado

`EmailOrderService` reutilizaba el mismo `Mono<User>` dentro de un `zip`, lo que podía consultar al usuario dos veces. Más grave, recorría los ingredientes con bucles y ejecutaba `subscribe()` dentro del servicio para mutar una lista compartida. El `TacoOrder` podía emitirse antes de que esas suscripciones asíncronas terminaran, produciendo tacos incompletos. Un usuario, pago o ingrediente inexistente terminaba como flujo vacío o dato faltante sin una causa identificable.

## Solución implementada

La entrada se valida y se continúa con `flatMap(this::convertOrder)`. La consulta del usuario usa `switchIfEmpty` para producir `EmailOrderUserNotFoundException`. Dentro de ese mismo `flatMap` se consulta el pago una sola vez y se transforma su ausencia en `EmailOrderPaymentMethodNotFoundException`.

Los tacos se convierten con `Flux.fromIterable(emailTacos).concatMap(this::convertTaco).collectList()`. `concatMap` conserva el orden y espera cada conversión. Cada taco repite el patrón para sus IDs de ingrediente: consulta `ingredientRepo.findById`, convierte un resultado vacío en `EmailOrderIngredientNotFoundException` que conserva el ID y reúne los resultados con `collectList`. Sólo entonces `map` construye el taco. Cuando la lista completa está disponible, otro `map` crea la orden, copia usuario, dirección y los campos de pago que ya usa este proyecto, asigna la fecha y establece todos los tacos.

La solución fue:

### Resolución encadenada de usuario, pago y tacos

```java
private Mono<TacoOrder> convertOrder(EmailOrder emailOrder) {
  return userRepo.findByEmail(emailOrder.getEmail())
      .switchIfEmpty(Mono.error(new EmailOrderUserNotFoundException()))
      .flatMap(user -> paymentMethodRepo.findByUserId(user.getId())
          .switchIfEmpty(Mono.error(
              new EmailOrderPaymentMethodNotFoundException()))
          .flatMap(payment -> convertTacos(emailOrder.getTacos())
              .map(tacos -> buildOrder(user, payment, tacos))));
}

private Mono<List<Taco>> convertTacos(List<EmailTaco> emailTacos) {
  return Flux.fromIterable(emailTacos)
      .concatMap(this::convertTaco)
      .collectList();
}

private Mono<Taco> convertTaco(EmailTaco emailTaco) {
  return Flux.fromIterable(emailTaco.getIngredients())
      .concatMap(ingredientId -> ingredientRepo.findById(ingredientId)
          .switchIfEmpty(Mono.error(
              new EmailOrderIngredientNotFoundException(ingredientId))))
      .collectList()
      .map(ingredients -> {
        Taco taco = new Taco();
        taco.setName(emailTaco.getName());
        taco.setIngredients(ingredients);
        return taco;
      });
}
```

Se añadieron excepciones pequeñas con códigos estables para entrada inválida, usuario, pago e ingrediente ausentes. 

### Validación reactiva de la entrada

El servicio comprueba el publisher y transforma una entrada vacía en un error explícito antes de iniciar consultas:

```java
public Mono<TacoOrder> convertEmailOrderToDomainOrder(
    Mono<EmailOrder> emailOrder) {
  if (emailOrder == null) {
    return Mono.error(new InvalidEmailOrderException(
        "Email order publisher is required"));
  }

  return emailOrder
      .switchIfEmpty(Mono.error(new InvalidEmailOrderException(
          "Email order is required")))
      .flatMap(this::convertOrder);
}
```

`shouldFailWithTypedErrorForEmptyEmailOrderPublisher` comprueba el `switchIfEmpty`. La prueba confirma que un publisher vacío no termina silenciosamente.

### Construcción posterior a todas las consultas

La orden se crea sólo cuando usuario, pago y lista de tacos ya están disponibles:

```java
private TacoOrder buildOrder(
    User user, PaymentMethod paymentMethod, List<Taco> tacos) {
  TacoOrder order = new TacoOrder();
  order.setUser(user);
  order.setCcNumber(paymentMethod.getCcNumber());
  order.setCcCVV(paymentMethod.getCcCVV());
  order.setCcExpiration(paymentMethod.getCcExpiration());
  order.setDeliveryName(user.getFullname());
  order.setDeliveryStreet(user.getStreet());
  order.setDeliveryCity(user.getCity());
  order.setDeliveryState(user.getState());
  order.setDeliveryZip(user.getZip());
  order.setPlacedAt(new Date());
  order.setTacos(tacos);
  return order;
}
```

Este fragmento refleja el dominio existente en TC-06, cuando los datos de tarjeta todavía pertenecían a `PaymentMethod` y `TacoOrder`. `shouldConvertMultipleTacosWithAllIngredientsInOrder` verifica la orden resultante y el orden de sus tacos e ingredientes.

### Errores funcionales identificables

Las excepciones comparten un código estable:

```java
public abstract class EmailOrderConversionException
    extends RuntimeException {
  private final String code;

  protected EmailOrderConversionException(
      String code, String message) {
    super(message);
    this.code = code;
  }

  public String getCode() {
    return code;
  }
}
```

`shouldFailWhenUserDoesNotExist`, `shouldFailWhenPaymentMethodDoesNotExist` y `shouldFailWhenIngredientDoesNotExist` comprueban que cada ausencia termina con su error específico. El caso de ingrediente también conserva el ID desconocido.

## Flujo

Mono de email -> validar -> buscar usuario -> buscar pago -> recorrer tacos en orden -> recorrer ingredientes de cada taco en orden -> reunir listas -> construir `TacoOrder` -> emitir una sola vez. Cualquier ausencia corta el flujo con un error explícito.

## Archivos principales

- `EmailOrderService.java`: contiene toda la composición sin suscripciones internas.
- `EmailOrderConversionException.java` y sus cuatro subtipos: describen fallos funcionales de conversión.
- `EmailOrderServiceTest.java`: valida resultados, orden, errores y señales reactivas.

## Pruebas

Las pruebas cubren múltiples tacos e ingredientes en orden, una sola suscripción a la búsqueda de usuario, ingrediente desconocido con su ID, usuario ausente, pago ausente, publisher de entrada vacío y colección de ingredientes nula. El caso con `TestPublisher` mantiene pendiente un ingrediente y confirma que no se emite ninguna orden hasta que esa consulta finaliza.

## Cambios realizados por otros TC

TC-08 no cambió el contrato interno `Mono<EmailOrder> -> Mono<TacoOrder>` de `EmailOrderService`. Cuando la conversión se usa desde el endpoint HTTP, la orden terminada se transforma en `OrderResponse` después de completar las etapas posteriores.

TC-09 añadió Bean Validation al modelo de entrada `EmailOrder` y traduce las excepciones tipadas de conversión a respuestas `422` con su código funcional. La resolución reactiva de usuario, pago, tacos e ingredientes no cambió.

TC-11 conservó la conversión `Mono<EmailOrder> -> Mono<TacoOrder>`, pero el endpoint que la consume exige un usuario autorizado y comprueba que la orden convertida pertenezca a la identidad autenticada antes de persistirla.

TC-12 tokenizó `PaymentMethod`. La conversión mantiene la resolución reactiva y copia a la orden únicamente el identificador, la marca y los últimos cuatro dígitos.

TC-14 calcula el precio de la orden convertida después de resolver todos sus tacos e ingredientes. Cada taco de correo se adapta a una línea con cantidad uno. La composición reactiva de TC-06 se mantiene.
